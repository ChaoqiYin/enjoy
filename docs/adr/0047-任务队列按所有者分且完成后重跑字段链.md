# 任务队列按所有者分且完成后重跑字段链

用户的原话：

> 任务不应该写进JSON文件里，应该是写到数据库里才对呀。

> 倒不如在主内核里面就维护一个队列功能，并提供给所有插件：如何插入任务，以及完成任务时通知。

> 还是在顶部加一个任务的切换栏吧。将现在的扫描改成异步任务，归并到里面。

> 按丙1吧，虽然是插件，但是设计上应该像平时做软件一样，对于后台异步队列就是单开线程单独维护。

> 不应该是打开详情页才会触发，应该是任务执行完就会触发。

这几句把三件事拆开了：任务住在哪、谁来跑、干完之后结果怎么进库。0046 是这三件事之前的一版草案，它假设任务只活在内存里、结果由内核事后**再问一遍 `video.fields`** 才落库，这两条都已被实现取代；本条目是落地后的版本。

## 一、任务是一张表，不是插件的 JSON 文件

`tasks` 表随数据库版本 9 落地（`repository/schema.rs`），内核自己的扫描、缩略图、单条刷新和插件的刮削都在同一张表里。理由有三条，每条都单独就能否掉「插件自己写 JSON」：

- **任务页要跨所有者列一张表。** 插件各写一份 JSON，界面就得知道每个插件的文件在哪、什么格式，那正是「内核不认识具体插件」要避免的。
- **状态机只有一份实现。** 排队、领取、暂停请求、取消请求、重试、终态清理、启动恢复，写一遍已经够多；每个插件各写一遍就是每个插件各错一遍。
- **进程退出不是业务失败。** 启动时把 `running` 一律改回 `pending`，重跑是安全的（扫描是增量的，刮削是幂等的）。JSON 文件没有事务，写到一半被杀就是一条读不出来的任务。

**去重**在事务里按 `(plugin, space_id, video_id, kind)` 查非终态行，有就返回那一行，不用唯一索引：单进程写，事务足够，而且内核任务与插件任务的去重键本来就不同。

## 二、队列按所有者分，不全局串行

内核一条队列（`plugin IS NULL`），每个插件一条（`plugin = '<自己>'`）。串行只发生在所有者内部：

- 三个媒体任务仍然一个接一个，保留原来「同一时刻只跑一个媒体任务」的语义；
- 一个插件抓得慢，不挡另一个插件，也不挡扫描；
- 领取者的身份由实例绑定的插件 id 决定，不是参数——插件借任务 id 碰不到别人的任务，也伪造不了 `plugin`。

**被否决的：一条全局队列。** 那会让一个站点的慢请求成为整个应用的后台进度，正是把扫描从模态框里放出来要解决的问题。

## 三、后台实例由「导出 `run`」触发，不在清单里声明

运行体导出 `run` 函数即表示「我需要后台」：`WasmBody::load` 检查导出表，有 `run` 就再实例化一个 `Store`、起一条线程调用它。两个实例不共享线性内存，共享插件数据目录与内核设施（任务表、日志、`fetch`）。

**为什么不是清单里写 `"background": true`：** 清单说「我是谁、我能要什么」，导出表说「我实际实现了什么」。两处都要写的事，一定会有只改一处的时候；那时清单说它有后台，模块却没有 `run`，内核只能要么加载失败、要么静默当它不存在。导出表是模块自己的事实，不会与模块不一致。

`run()` 正常返回 = 后台结束；trap 或 panic = 记一行日志、后台停掉、**不自动重启**，前台照常。停用插件时先唤醒所有 `task_wait` 等待、再停线程。

## 四、任务完成后由内核重跑字段链（乙方案）

`task_done` 只标完成并把字段交给落地线程（`plugins/landing.rs`），落地按五步进行：

1. 字段转成 `VideoField`，来源补成插件 id，集合外的键丢弃；
2. `cover` 是地址就由内核下载（`cover::settle`，20 秒、8 MiB；失败保留旧图）；
3. `save_fields` 写一次，刚抓到的值立即落库；
4. **重跑 `video.fields` 链**（`PluginHost::video_fields`），把结果再 `save_fields` 一次；
5. 发 `library-changed`；任务行在 `task_done` 返回前已置 `done` 并发 `task-changed`。

第 4 步是用户选的「乙方案」：**顺序在任务完成时就生效**，而不是等下一次打开详情页。若用户把另一个插件排在刚完成这个插件之前，第 4 步会把更靠前的答案写回去；`save_fields` 是 upsert 且不删除未提到的键，所以第 3 步写的值不会被这一轮问空。

**代价如实记：** 落地是异步的，因此 `library-changed` 比 `task_done` 的返回晚一点；界面在这条缝里读到的是第 3 步之后、第 4 步之前的库。它是一致状态（链上每轮都整批写），只是不是最终状态。若落地写库失败，只记日志——插件的工作确实完成了，任务保持 `done`，因此用户看不到这条失败；这是 spec #96 记下的盲区。

**被否决的：让插件直接写库。** 运行体没有数据库能力，也不应该有：封面必须由内核下载到本机（窗口的 CSP 没有远端 `img-src`），字段键必须是封闭集，写库必须是 upsert。这些规则只能待在插件拿不到的那一侧。

## 五、任务失败不计入「五次停用」

插件在任务里失败（`task_fail`）是**它干的那件活的结果**，不是它作为插件坏掉了。挂载点上的失败之所以累计五次就停用，是为了避免「通知每渲染一次来一条」；任务失败已经有任务页那一行写着原因，再拿它停用插件，会让「站点今天挂了」变成「插件被停用」。

越权调用（碰别人的任务）同理：返回 `-1` 并记日志，不算一次失败——插件被告知了「不」，它没有抛错。
