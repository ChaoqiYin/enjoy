# 运行体是常驻的 WASM 实例

用户的原话：

> 45。插件分为前端部分和后端部分。后端应该不是js的

> 后端不是rust的吗，为什么后端要写成js

> 能不能不用WASM，而是动态引入

「后端」这个词在这里指的是**插件干活的那一半**，本条按 [ADR 0043](0043-插件系统的形态.md) 的口径改称**运行体**。为什么不能是页面里的 JS、以及为什么不是动态引入，是这一条要回答的全部问题。

## 一、跑在 WebAssembly 里

运行体是一个编译到 `wasm32` 的模块，由内核用 wasmtime 实例化，**在内核进程里**跑。

**被否决的：页面里的 JS。** 它省事得多——活对象、没有消息传递、公开一个下午就能写一个插件。但换来的是一个**要堵一长串**的环境边界：`fetch`、`WebSocket`、`EventSource`、`importScripts`、嵌套 worker、`SharedWorker`、`ServiceWorker`、`IndexedDB`。这份清单**由浏览器决定，而且只会越来越长**——每一次引擎更新都可能多一样，而我们的边界不会自动跟着变。

WebAssembly 的处境正好相反：它**没有任何环境权限**，能做什么完全由内核导入给它的东西决定。要加一样能力得有人显式写一行。这不是「更严」，是**边界的形状不同**：一个是我们列黑名单，一个是默认什么都没有。

**被否决的：`import()` 一个动态模块。** 「动态引入」只解决加载，不解决权限——引入进来的还是页面里的 JS，上面那一长串一样在。

**如实记下代价**：插件作者的门槛高了一个量级。写一个爬封面的插件要装 Rust 工具链、要交叉编译到 `wasm32`，而不是写一个 `.js` 文件丢进去。而这正是决定「插件到底会不会被写出来」的东西。它现在付得起，因为第一步只按「作者自己写」来立规矩（见「谁写插件」一节）；**哪天要放开第三方，先重开的就是这一条**。

## 二、常驻，不是每次调用起一个

每个插件一个**专用线程** + 一个**常驻的 `Store`**，随插件的启停而生死。

**被否决的：每次调用新起一个实例。** 它换来的是调用之间天然隔离，代价是插件没法保留任何内存里的状态（连接池、解析好的索引、抓取进度），每一次调用都要重新建立。而「插件按自己的计划干活、把更新推给界面」正是设计里要的形态，它需要状态活着。

常驻的代价必须用**强制的限额**来抵，这也是本节后半段的全部内容：一个常驻的实例如果没人管，它就是内核进程里一块可以无限长的东西。

## 三、一个入口，内核不解释

运行体只暴露一个入口：`handle(method, payload)`。内核**只转发和计量，从不解释 `method`**——`method` 是什么、`payload` 里有什么，是插件与它自己的挂载点调用方之间的事。

这一条买到的是**内核不必随插件演进而改**：插件加一个新的 `method` 不需要内核发版。

## 四、限额

- **CPU**：epoch（`Config::epoch_interruption` + `Engine::increment_epoch` + `Store::set_epoch_deadline`）与 fuel（`Config::consume_fuel` + `Store::set_fuel`）两道。epoch 的价值在于「webassembly 代码绕不开这个截止检查」。
- **内存**：`Store::limiter` + `StoreLimitsBuilder::memory_size`。

## 五、宿主函数是异步的

`Linker::func_wrap_async` + `Func::call_async`。

理由是**中断**：插件取一个网址可能要等好几秒，如果宿主调用是同步的，那段等待期间插件整个卡住，而「插件卡住」在内核看来与「插件死了」没有区别。异步宿主函数让这段等待是**可被中断的**，因而限额能真的生效。

**异步是单向门**：一旦用了任何异步 API，整个 `Store` 都必须是异步的。这条是代价，写在前面。

## 六、已接受的盲区（如实记）

- **epoch 与 fuel 对阻塞在宿主调用里的 wasm 无济于事**：限额作用在插件自己的指令上，插件在等内核返回时不在执行指令。第五节把等待改成异步是为了让这段时间可中断，但它并没有让「插件自己在宿主函数里死循环」变成可拦的——那要靠宿主函数自己守时。
- **bulk memory 操作在开始时只检查一次 epoch**，一个巨大的 `memory.copy` 因此可能超出截止时间一截。
- **与 Winch 后端不兼容**。
- **线程栈耗尽会让进程直接 abort**，不是可以接住的 trap。这条决定了宿主函数的栈预算要按插件能给的输入算，不能只看内核自己的调用深度。

## 七、谁写插件

第一步只按「作者自己写」立规矩：v1 不做网络安装、不做市场。结构上给第三方留门（清单里有作者与能力声明、能力要显式授予、运行体本来就没有环境权限），但**不假装已经有一套信任模型**——把别人的 wasm 装进来还缺的东西（签名、来源、升级与回滚）是另一件事，不在这一条里。

**安全模式现在就要有**：一个能让应用**不加载任何插件**就起来的入口，做法是纯文件系统恢复——把插件启用状态那份记录改名成带时间戳的备份、恢复到默认停用全部插件、**保留已安装的插件目录**。理由是插件目录躺在一个用户不一定会想到去删的地方，而「应用起不来」这件事没有别的自助出路。

## 它推翻了什么

没有推翻已落地的代码。它约束的是将来：**内核进程里不得出现没有限额的插件代码**，以及**插件不得拿到任何未在清单里声明并获授的能力**。

## 实施状态

**已实施。** 常驻实例与限额在 `src-tauri/src/plugins/wasm/`：一个插件一个 `Store`，挂在后台线程上常驻；模块名 `enjoy` 下导入**四样能力**（`fetch`／`storage`／`log`／`video`），今日共十二个函数：`fetch`／`storage_read`／`storage_write`／`log`／`now_ms`／`video_info`，加任务队列的六个 `task_*`（`wasm/imports.rs`；后者见 [0047](0047-任务队列按所有者分且完成后重跑字段链.md)）；限额是 `CALL_DEADLINE` 5 秒、`EPOCH_TICK` 10 毫秒、`FUEL_PER_CALL` 10⁹、`MEMORY_LIMIT` 16 MiB、`FETCH_LIMIT` 8 MiB（`wasm/mod.rs`、`wasm/imports.rs` 各一个 `const`）。宿主函数是异步的，调用跨线程回到内核。

**有一件事要说清楚，因为它很容易和后一句并成一句。** 在 #89 之前，**没有任何生产代码构造过 `WasmBody`**：运行时在、限额在、测试在（`wasm/tests.rs` 与 `wasm/imports_tests.rs`，模块由 WAT 文本就地组装——本仓库不为 `wasm32` 构建，见该文件的说明），但「从盘上读到一个插件、把它的运行体建起来、让它进轮转」这条线**没有接**，`PluginHost` 的插件集恒为空。接线是 #89 做的：`plugins/loading.rs` 读插件目录 → 四条清单校验并读启用记录 → `WasmBody::load` 建运行体 → 启用，由 `app::initialize_backend` 在 `app.manage` 之前调一次，且返回 `()`（没有 `Result` 可漏，失败只写日志）。今天 `WasmBody::load` 只有两个调用点：`plugins/loading.rs:113` 与测试夹具 `wasm/fixture.rs:27`。

**§7 的安全模式已落地**（#86）：启用记录改名成带时间戳的备份、恢复默认全关、插件目录一个都不动。它比运行体早落地，因为「应用起不来」这条自助出路不该等到插件真能跑起来才给。
