# 关窗由销毁承担，而侦听只在服务运行时挂着

> **已被 [ADR 0015](0015-关窗的决定在后端而界面只回答确认.md) 取代。** 这一篇记的两条平台事实（挂着侦听器就关不掉、确认之后必须用销毁）仍然成立，但它们是「把决定放在界面层」的产物：决定挪到后端之后，这个形状和绕开它的办法都不再存在。留在这里是因为它把两条陷阱写清楚了，也因为一年后再有人想「从界面关自己的窗口」时，该先读它。

共享服务运行时点关闭，要先问用户一句「正在共享，确定关闭吗」。这一篇记的是实现它的两条取舍：窗口最后**怎么**关，以及那个「问一句」的侦听器**什么时候**挂着。两条都是 0.2.0 与 0.2.1 上「点关闭没反应」的来处。

## 平台事实：有侦听器，就关不掉

Tauri 在 `manager::window::on_window_event` 里对每一次关闭请求都是这么处理的：

```rust
WindowEvent::CloseRequested { api } => {
  if window.has_js_listener(WINDOW_CLOSE_REQUESTED_EVENT) {
    api.prevent_close();
  }
  window.emit_to_window(WINDOW_CLOSE_REQUESTED_EVENT, &())?;
}
```

`has_js_listener` 问的是**此刻**有没有 JS 侦听器登记在这个窗口的这个事件上（注销即不再算数）。所以：

- 有侦听器 → 这一次关闭**已经**被拦下，事件只是通知。处理器里做什么都放不过这一关，包括什么都不做——`event.preventDefault()` 与否不影响它，那是 JS 侧的另一件事。
- 从 JS 里调 `close()` 同样没用：它发出的就是这么一个请求，到了这一层又被拦下，等于原地打转。
- 唯一不经过这一步的是 `destroy()`（Rust 侧文档原话：*does not emit any events and force close the window*）。

还有一处容易漏：**Tauri 自己的 `onCloseRequested` 在没有 `preventDefault()` 时会替调用方 `destroy()`**。也就是说，只要订阅过，`core:window:allow-destroy` 就是必需的，哪怕你自己一次都没调过销毁。

## 取舍一：确认之后用销毁，不用关闭

确认时那一次关闭**就是**用户刚刚同意的那一次，没有第二个问题要问，因此也不该再走一遍「发请求 → 被自己拦下」。用 `destroy()`，一次调用，一个权限（`core:window:allow-destroy`），且不依赖 Tauri 包装层的行为。

被否掉的替代：**先注销侦听器再 `close()`**。它能成（`has_js_listener` 看的是当下），但把「关得掉」这件事挂在了「注销的 IPC 与关闭的 IPC 谁先到」上，而这两次调用之间还隔着一次 `await`。销毁不参与这场竞争。

`frontend/src/shared/api.ts` 里那个方法仍叫 `close`——调用方要的是「把窗口关掉」——而它的注释写明了为什么里面必须是销毁。表中没有 `close()` 这一项，见下。

## 取舍二：侦听器只在服务运行时挂着

上面那条平台事实的另一面是：**挂着侦听器，窗口就再也关不掉了**。0.2.0 与 0.2.1 的 `ShareProvider` 在挂载时就订阅（它在最外层，等于整个应用生命周期都在），于是任何一次点关闭都被拦下、交给一个「没在共享、于是什么都不做」的处理器——窗口看起来就是死的。不共享时的那条早退分支解决不了这件事：它返回之后，Tauri 包装层的 `destroy()` 才轮到，而 0.2.0/0.2.1 都没有授销毁权限。

因此订阅跟着「有没有东西可打断」走：

- 服务没在跑 → **不订阅**。关闭走窗口自己的原生路径，不需要任何权限、不过 JS、不做版本相关的绕行。
- 服务在跑 → 订阅；服务一结束（无论是从窗口关的还是从页面上停的）就注销。注销由 `ShareProvider` 的那个 effect 的清理函数承担，`asking = share.port !== null`。

被否掉的替代：**永远订阅，在处理器里按「有没有在共享」分流**。它同样能工作（不共享时由包装层销毁），代价是应用**每一次**关窗都要过一遍 JS，而这条路上任何一处抛错都是一个再也关不掉的窗口——一个用户只能靠任务管理器收场的状态。让「没事可问」的关闭根本不进入这条路，比在这条路上写对更重要。

## 代价与不变量

- 订阅期间点关闭不会关窗（这是功能本身）。取消之后窗口留着、服务继续跑；要关就再点一次。
- 处理的是**关闭请求**，不是「关闭」。取消、重开对话框、确认，都只是这一条路上的分支。
- 任何将来再加的关窗询问，都必须 follow 这两条：订阅跟着「有话要说」的窗口期走，确认之后用销毁。`scripts/check-permissions.mjs` 会在漏授销毁权限时把提交拦下，但它拦不住「又有人在挂载时就订阅」——那一条只有上面的理由和 `ShareProvider.test.tsx` 里「没有服务时不订阅」那条用例在守。
