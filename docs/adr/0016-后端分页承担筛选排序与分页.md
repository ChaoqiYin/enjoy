# 后端分页承担筛选、排序与分页

界面原型画了分页控件，我们据此放弃了虚拟滚动（见[列表三态视图与废除虚拟滚动](0017-列表三态视图与废除虚拟滚动.md)）。分页一旦成立，**筛选与排序就必须跟着搬进后端**：界面手里只有一页记录，在它上面做本地筛选只作用于这一页，总页数会跟着算错。这不是附带条件，是分页这个词能不能在两处都成立的问题。

## 现状

`list_videos` 收一个空间 id，交给仓库层一条写死的查询：`WHERE space_id=?1 ORDER BY created_at DESC, id DESC`，没有筛选、没有 `LIMIT`。全量回到界面，由界面自己排序、筛选、虚拟滚动。

## 决定

`list_videos` 收一个查询描述，返回一页记录与总数。两个数都要有——原型 `_8` 的底栏文案是「显示第 1 至 6 个结果 • 共 12 项本地记录」。

```ts
type VideoQuery = {
  spaceId: number;
  search?: string;
  folder?: string;
  only?: 'favorite' | 'shared' | 'played';
  sort?: 'added' | 'played' | 'name' | 'size';
  direction?: 'asc' | 'desc';
  offset: number;
  limit: number;
};

type VideoPage = { items: Video[]; total: number };
```

## 它推翻了什么

`SharePage` 里有一段注释说明了收藏页与共享页为什么不需要后端命令：**标记随记录走**——`favorite` 与 `shared` 是记录上的字段，清单就是「全集加一个筛选」，因此在界面里过滤即可，后端不必知道「清单」这个概念。

分页之后这句话不成立了：界面只有一页记录，「全集加一个筛选」失去载体。**后端从此必须认识三个维度**——收藏、共享、有没有播放历史。这不是副作用，是这次决定的主要代价，写在这里免除后来的困惑。

代价的另一半在接缝上。`check-seam.mjs` 要求 `shared/api.ts` 里每个导出类型都在对照表登记、字段名与 Rust 侧逐一相等。而该文件已 482 行、上限 500，新增类型前必须先拆它；能拆的只有类型，`invoke` 必须留在原处——`check-commands.mjs` 规定只有这一个文件可以 import Tauri 运行时。

## 为什么改造 `list_videos`，而不是新增命令

`check-commands.mjs` 有双向规则：注册了但无人调用报错，调用了但未注册也报错。多一条命令就多一处必须维护的登记。而收藏页、共享页、最近播放页本质都是「同一个合集加一个筛选条件」，一条命令带参数最贴合现有「命令名即接口」的风格。命令名不变，检查脚本只看名字，签名变化对它不可见。

## 排序维度

- **最近添加**（`created_at` 降序）：视频库与收藏的默认
- **最近播放**（`last_played_at` 降序）：最近播放页的默认
- **文件名** A-Z
- **文件体积**从大到小

原型 `_8` 的排序下拉里「最近打开（降序）」与「打开时间（升序）」是同一个字段的两个方向，合并为一项、由方向参数表达，不保留两套文案。

## 后果

- `界面原型.md` 中「搜索、目录筛选与排序**只作用于本地已索引数据**」一句作废
- 界面侧的查询缓存键、扫描完成后的失效路径全部改写
- 后端新增计数查询；七个窄接口中 `useVideos` 的签名与装配跟着变

## 实施状态

未实施。它是界面迁移的前置工作：集成层组件的参数直接吃「一页记录 + 总数」，契约必须先落。
