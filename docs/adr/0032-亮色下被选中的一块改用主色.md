# 亮色下被选中的一块改用主色

用户看着亮色主题下运行的实际界面，问了两句：

> 亮色主题下如果是带有主色背景的比如按钮、切换栏、菜单选择栏，那么此时内部的文字应该是白色的
> 并且非禁用时的主色背景不要做修改，为什么这里都变成粉红了

两句指的是同几处控件：设置页左列的当前行、主题分段条的选中块、工具栏视图模式的选中段，外加这一屏的「检查更新」按钮。用户看到的粉底黑字，要的是主色红底白字。

## 一、粉是从哪来的

**不是这一轮改的，也不是缺陷回归。** 这三处从 [ADR 0023](0023-设置页改用-shadcn-的-sidebar-与-rubber-segment.md) §五 起就取 `--secondary`（`surface-container-high`），亮色下是 `#fecdd3`；在那之前它们取 `--accent`（`#ffe4e6`），也是粉。粉一直是粉。

变的是**它们底下的那一层**。ADR 0029 把亮色的 `--background` 从微紫白 `#faf8ff` 换成了中性灰 `#f5f5f5`，并把这件事作为一个**当时没有处理的代价**写进了那一篇的 §四：

> 亮色调色板是带粉的……原先压在一层微紫白的底上，彼此是一路的；现在底变成中性灰，这几个粉与新底之间**没有色相关系**，粉会更跳。设置页那条主题分段条的滑块（`--secondary`）是立刻能看出来的一处。……它是一个**本轮没有处理的变化**，如实记在这里。

用户问的这一处，就是那一句点名的滑块。所以这一轮还的是上一轮的账——ADR 0029 的「本轮没有处理」到这一轮被处理掉了。

## 二、改了什么

新增一对语义槽 `--selection` / `--selection-foreground`，**两套主题给不同的值**：

| | 亮色 | 暗色 |
|---|---|---|
| `--selection` | `--primary` = `#e11d48` | `--secondary` = `#2a2d33`（不变） |
| `--selection-foreground` | `--primary-foreground` = `#ffffff` | `--secondary-foreground` = `#edeef2`（不变） |

四处落点改用它：

| 落点 | 改动 |
|---|---|
| 设置页左列的当前行（`shared/ui/sidebar.tsx`） | `data-[active=true]` 的两条由 `bg-sidebar-accent` / `text-sidebar-accent-foreground` 改为 `bg-selection` / `text-selection-foreground`；角标那行跟着改。**悬停仍是 `--sidebar-accent`** |
| 主题分段条的选中块（`theme/ThemeSetting.tsx`） | `thumbColor` / `activeTextColor` 传 `--selection` 那一对 |
| 工具栏视图模式的选中段（`shared/ui/toggle-group.tsx`） | `data-[state=on]` 的两条改为 `bg-selection` / `text-selection-foreground` |
| 「检查更新」按钮（`features/update/UpdateSetting.tsx`） | `variant` 由 `secondary` 改为 `primary` |

**只有亮色三处改，是因为用户这么选的。** 提问时把「暗色要不要一起改」摆出来，用户选了「只改亮色」，同时选了「悬停保持浅色」。

**为什么暗色不动。** 暗色下这三块是页面之上的一档灰（`#2a2d33` 对 `#111317` 的页，差 25 级），没有任何指针也读得出来，用户没有报过它；改成 `--primary` 会是一整行 `#ff334b`，白字压在上面只有 3.4:1，而那一大块红会盖过一屏唯一那个着力的动作。两套主题在这一槽上因此**故意不同值**——这与 `--primary` 两边不同值是两回事：那是调色板本身的差别，这里是同一个语义在两个主题下的取舍。

**`--selection` 而不是把那三处直接写成 `bg-primary`。** 直写就只有亮色对、暗色错；写死成一对亮暗不同的字面值又会把颜色散到三个文件里。一个语义槽、一处声明，正是本仓放这类分歧的地方（同 `--field`、`--glow-*`）。

## 三、实测（无头 Chrome，1440 视口，验收夹具 `acceptance/web-acceptance.html`）

两套主题各读一遍、各出一张设置页截图：

| 落点 | 亮色 | 暗色 |
|---|---|---|
| 左列当前行 | `rgb(225,29,72)` 底 / `rgb(255,255,255)` 字 | `rgb(42,45,51)` 底 / `rgb(237,238,242)` 字（**没动**） |
| 主题条滑块 | `rgb(225,29,72)` / 白 | `rgb(42,45,51)` / `rgb(237,238,242)`（**没动**） |
| 视图模式选中段（亮色） | `rgb(225,29,72)` / 白 | — |
| 「检查更新」 | `rgb(225,29,72)` / 白，`data-variant="primary"` | `rgb(255,51,75)` / 白 |
| 左列悬停行（亮色，另测） | `rgb(254,205,211)` 底 / `rgb(15,23,42)` 字（**没动**） | — |

亮色下白字对 `#e11d48` 是 **4.9:1**，过 AA。

## 四、代价

**「检查更新」在暗色下也跟着变红了，而用户只要求亮色。** `Button` 的变体是类名，切不了主题，而它是这屏唯一的按钮、也是这块唯一的动作，`primary` 是它该有的语义。它与全站的主色按钮同色（设置页的「添加目录」、更新的「下载」与「立即重启」在暗色下都是 `#ff334b` 配白字），所以并不突兀；但那块红确实是这一轮多出来的。若哪一轮要收回，最省的收法是给它一个走 `--selection` 的按钮变体——暗色随之回到灰上，亮色不变。

**「每屏一个红按钮」在一种状态下不成立。** 设置页真的查到新版本时，「检查更新」与「下载」/「立即重启」会同时出现在「更新」这一组里。这与上一条同源（按钮取主色），是可接受的一种状态，但它确实让那条立场多了一个例外。

**左列的悬停行仍是粉的（`--secondary`，`#fecdd3`）。** 用户明确选了「悬停保持浅色」：只有当前行是红的，指针扫过的行不该跟着泛红。代价是亮色下这一列现在同时有红块与粉块。

**下拉菜单里指针划过的那一项没有跟着改**（`dropdown-menu.tsx` 的 `focus:bg-secondary`）。它与悬停是同一类——指针扫过时的水洗，不是「被选中」——按用户对悬停的选择保持一致。

## 它推翻了什么

- **「被选中／当前的那一块全仓统一取 `--secondary`，不取 `--primary`」**（[ADR 0023](0023-设置页改用-shadcn-的-sidebar-与-rubber-segment.md) §五、`界面通用组件清单.md` §2.5）——**亮色那一半推翻，暗色那半照旧**，并记进 §7。ADR 0023 §五 的论证本身没有被推翻：那里「`--accent` 在暗色下只是一层悬停水洗、读不出来」仍然成立，被推翻的只是它顺带为两套主题一起定下的取值。§五 末尾那句「亮色下结果仍是同一色系的粉块……要不要收回去由用户定」，到这里由用户收了。
- **`UpdateSetting` 的「检查更新」是 `secondary` 变体**（`features/update/UpdateSetting.tsx`）——改为 `primary`。这不是一条成文的决定，是那一行代码自己的选择；改动只落在组件与它那条测试断言上，本清单没有为它记过行。
