# 最大化按钮接回系统的贴靠布局

用户的原话：

> 为什么你做的最大化按钮鼠标悬浮时和我在其他app上悬浮的效果不同，没有这个

（配了一张 Windows 11 贴靠布局飞出菜单的截图。）

> 贴靠布局效果你不要自己手搓样式实现，要去找怎么使用tauri提供的来激活

> https://github.com/Hyph-M/tauri-plugin-snap-layout 可以看看这个库

## 一、Tauri 自己没有这个开关

先把「tauri 提供的」查清楚，因为查完才知道这条路只有一条。

**没有 API。** `tauri 2.11.5`、`tao 0.35.3`、`tauri-runtime-wry 2.11.4` 三个 crate 的全部源码里，`HTMAXBUTTON` 一次也不出现；`tauri-utils` 的窗口配置里没有相关字段，`tauri` 的 feature 表里没有，`src-tauri/gen/schemas/` 展开出的窗口命令只有 `maximize` / `unmaximize` / `toggle-maximize` / `is-maximized` 那一组。

**Tauri 唯一自己做的命中测试**是 `tauri-runtime-wry/src/undecorated_resizing.rs`：无边框窗口的八向缩放边框（`HitTestResult` 到 `HTLEFT` / `HTRIGHT` / … 的映射）。它不对外，也不含 `HTMAXBUTTON`。

**Tauri 真正提供的那一个**是 `window.set_theme()`。tao 在 Windows 上顺着它调 `DwmSetWindowAttribute(DWMWA_USE_IMMERSIVE_DARK_MODE)` 并重画标题栏（`tao-0.35.3/src/platform_impl/windows/dark_mode.rs:162` 的 `refresh_titlebar_theme_color`）——也就是说，**保留原生装饰**，贴靠布局、系统菜单、圆角投影、双击最大化全部白拿，主题也跟得上。ADR 0039 §一 写过这条路，用户当时用「按钮要和默认一致」把它排除了，今天也没有回头选它。

于是结论是：**无边框窗口要贴靠布局，只有「对那个点回 `HTMAXBUTTON`」一条路**（微软文档写明的唯一触发方式），没有可以「激活」的开关。剩下的问题只是这段代码谁写。

## 二、改了什么

### 选的是插件，不是自己写

`tauri-plugin-snap-layout` 1.0.9（MIT，crates.io，`Hyph-M`）。

它的手法和 ADR 0039 §四 里猜的「在 Rust 侧再挂一层窗口子类」不一样，而且更好：它不碰主窗口的窗口过程，而是 `CreateWindowExW` 造一个 `Static` 子窗口盖在按钮上，只给**那个子窗口**装子类（`src/snap.rs` 的 `update_snap_bounds` 与 `child_subclass_proc`），由子窗口回 `HTMAXBUTTON`。主窗口的消息链——拖动区、四条缩放边、tao 自己的命中测试——一个字节没动。

**这恰好是 Tauri 自己在无边框窗口上用的手法**：§三 的探针列出的子窗口里，除了覆盖层与 `WRY_WEBVIEW`，还有一个 `TAURI_DRAG_RESIZE_BORDERS`（就是 `undecorated_resizing.rs` 造的那个）。插件只是把同一手法用在按钮上。

依赖上几乎白送：它的四个依赖 `raw-window-handle` 0.6.2、`thiserror` 2.0.20、`windows-version` 0.1.7、`windows-sys` 0.61.2 **全都已经在树上**（`Cargo.lock` 里有），所以 `Cargo.toml` 里多的是它自己一行。

### 接线

- `src-tauri/src/main.rs` —— `.plugin(tauri_plugin_snap_layout::init().button_id("window-maximize").build())`。
- `src-tauri/capabilities/main.json` —— 加 `snap-layout:default`：插件注入的那段脚本要调 `update_snap_bounds` / `detach_snap_bounds`。
- `frontend/src/app/WindowControls.tsx` —— 中间那颗按钮加 `id="window-maximize"`，其余不动。
- `frontend/src/components.css` —— 一条 `#window-maximize.is-hovered { background-color: var(--hover) }`。

### 悬停那一笔为什么变成两处

Windows 11 上那个矩形不再是网页的：`HTMAXBUTTON` 意味着 shell 把这个点收走了，webview 在那里收不到任何鼠标消息，`:hover` 不会触发。插件因此在指针进入／离开时给按钮加／去一个 `.is-hovered` 类，`components.css` 里那条就把它画成水洗。

按钮自己的 `hover:bg-hover` **留着**，不是没删干净：Windows 11 以下插件什么都不做，矩形也没被收走，页面自己的 `:hover` 才是活的那一条。两处说的是同一个颜色，任何时候只有一条会亮。

### `scripts/check-seam.mjs` 多守一条暗号

`window-maximize` 这个 id 在 `main.rs` 与 `WindowControls.tsx` 各写一次，两个语言互相看不见。这与那份检查本来的题目（跨接缝的形状）只差一步，所以并了进去：读 `main.rs` 的 `button_id("…")`，要求 `WindowControls.tsx` 里有一个元素带着同一个 id。红绿两向实测过——把 Rust 侧改成 `window-maximise`，检查立刻红并点名（`main.rs aims the snap layout at "window-maximise", and no element in WindowControls.tsx carries that id`），改回来立刻绿。

## 三、实测

### Win32 探针（不是合成输入）

本机 125%（`GetDpiForWindow` = 120）。探针用 `FindWindowW` / `GetPropW` / `ChildWindowFromPointEx` / `SendMessageW`，**没有动鼠标**。读数都是 CSS 像素——探针进程不是 DPI 感知的，读回的正是逻辑像素。

| 量 | 读数 |
|---|---|
| 窗口 | `1214×808`（= ADR 0039 记的 1518×1010 物理 ÷ 1.25） |
| webview | `(263,257)-(1463,1057)`，1200×800 |
| 覆盖层 | `GetPropW(hwnd, "TauriSnapChild")` → 一个 `Static` 子窗口，`(1371,257)-(1417,289)`，**46×32** |
| 它在哪儿 | 距视口右缘 **46**（正好一颗按钮宽，最右那颗关闭在它右边），顶边与视口顶边齐平 |
| 子窗口 z 序 | `Static` 在最上，其下 `TAURI_DRAG_RESIZE_BORDERS`、`WRY_WEBVIEW` |
| 按钮中心谁接 | `ChildWindowFromPointEx(hwnd, 中心, SKIPINVISIBLE\|SKIPDISABLED)` → 覆盖层；系统级的 `WindowFromPoint` 也回覆盖层 |
| `WM_NCHITTEST` | **9 = `HTMAXBUTTON`** |

**一次要记下来的误读**：第一次 `WindowFromPoint` 没命中覆盖层，回的是另一个进程的窗口——那是应用窗口当时被整个盖住了（前台是 PotPlayer，上面还压着一个浏览器窗口），与本改动无关。命中测试要收窄到本窗口内部才有意义。

### 门禁

`npm run check` 通过（`check-seam` 那行现在报 `Every shape across the seam agrees: 15 pairs, 76 fields; the snap layout is aimed at "window-maximize"`）；`cargo test` 210 项；`cargo fmt --check`、`clippy -D warnings` 干净；`npm test` 86 文件 494 用例（超时放到 60 秒）。

### 没验的

**飞出菜单本身要真人把鼠标停上去看。** 探针能证明的是「系统在那个点会问到这个窗口，而这个窗口答 `HTMAXBUTTON`」——这正是文档里贴靠布局的全部触发条件，但「菜单真的弹出来」这一步只有一只真的鼠标能证。本机鼠标被远程会话夺走（仓库里早记着这条）。

## 四、代价

**每个窗口多一个 110 KB 的注入脚本。** 插件用 `js_init_script` 把它打进页面（`dist-js/inline-injection.js`，110870 字节，`@tauri-apps/api` 已经被 rollup 打了进去）。它是这个仓库里**第一段在窗口里跑的第三方脚本**：四个监听／观察器，一次对 `document.styleSheets` 的全量扫描（它顺手把 `#id:hover` 规则镜像成 `.is-hovered`——这一条我们没用上，见 §二）。

**id 是两个语言之间的一根线。** 已经由 `check-seam.mjs` 守着，但它仍然是「两处手写、必须一致」。

**中间那颗按钮的点击不再经过界面。** Windows 11 上它是插件的 `WM_NCLBUTTONUP` → `WM_SYSCOMMAND SC_MAXIMIZE` / `SC_RESTORE`；界面里的 `windowApi.toggleMaximize()` 在那台机器上不再被这颗按钮调到（别的入口照旧）。字形不受影响：它一直是后端在 `Resized` 上推的（ADR 0039），与谁执行了最大化无关。

**一个第三方依赖，随 Tauri 的内部走。** MIT、单作者、2026-05 建库、本仓库引用时 6 star。它的技术前提是 tao/wry 的窗口结构（子窗口、`WS_CAPTION` 留着、webview 铺满客户区），Tauri 换掉其中任何一样它就会失效——失效的表现是**贴靠布局不弹**，不会更糟。Windows 11（build 22000）以下与 macOS 上它是空实现：非 Windows 编译 `lib_dummy_impl.rs`，Windows 10 上 `init()` 走另一条只管理状态、两个命令都是空函数的分支。

**悬停那一笔分成了两处**（`:hover` 与 `.is-hovered`），理由在 §二。

## 它推翻了什么

**ADR 0039 §四 的第一条**：

> **最大化按钮悬停不再弹贴靠布局。** ……补它要在 Rust 侧再挂一层窗口子类、并把按钮的矩形同步过去，本轮不做。

「本轮不做」现在做了，那一条已改指本文。它猜的实现（一层窗口子类 + 同步矩形）是对的，只是子类挂在**子窗口**上、矩形由插件的注入脚本量。
