# 插件系统的形态

用户的原话：

> 我想对现有系统架构进行一个深度的修改，让它支持可以制作任意的插件，然后根据插件去扩展内容以及功能等等。

> 根据不同的人需要的场景，我需要解绑。比如我在 A 用户这，他可能希望我在影片能去某些网站爬取信息，来自动更新封面。那么这些地址是 A 自己有的，但是在另一个用户呢，他可能就希望用其他的方式，甚至是自己去其他地方手绘封面。

> 这个就是插件啊。比如 A 在自己的软件系统里面装上去能指定爬封面的插件，那他就达到了自己的目标。

本条定的是**形态**：插件是什么、它与内核的边界在哪。挂载点本身（分几处、归哪一半、怎么合并）见 [ADR 0045](0045-挂载点分两半且是封闭集.md)；干活那一半怎么跑见 [ADR 0044](0044-运行体是常驻的-WASM-实例.md)。

## 一、插件是运行时安装的独立单元

一个目录，放在应用数据目录下的 `plugins/<id>/`，里面是**插件清单**加它的两半（**插件界面**、**运行体**），两半至少有一个。装、启停、卸都是运行时的事，不重新发布应用，也不改仓库里的任何代码。

路径不是新约定：本仓库所有应用数据路径都由数据库文件的位置推出（缩略图缓存就是 `database.with_file_name("thumbnails")`），`plugins/` 与 `covers/` 照同一条规则走。

**这不是一个模块系统。** 它在磁盘上有一条明确的边界（一个目录），因此「这个插件装了什么、要卸掉它要删什么」都是能读出来的事实，而不是散在源码里的若干引用。

## 二、插件只能加料

插件能做的只有一件事：往**挂载点**上添一份自己的东西。它不能删、不能改、不能拦，没有否决权，也没有接管权。

这一条是整套设计的支点，它买到的是**爆炸半径可算**：内核的每一个动作——扫描、媒体处理、收藏、共享、更新、播放——都还是内核自己的代码在走，插件只是在这条路上被问了一句。因此「插件坏了」这件事的上界是「这次少了一样东西」，不是「这个功能不灵了」。

**被否决的：给插件否决权或接管权。** 那会把上面那句上界变成「任何插件可以让任何流程停下」，而用户对此没有任何处置手段——他看到的只是应用不动了。一个只能加的系统，用户永远可以靠「停用那个插件」回到原状，这是他手里唯一需要的那个动作。

## 三、两半的分工

- **插件界面**：参与内核界面的那一半，是一段 ESM 代码，由内核动态引入、并把 React 等基线**作为参数注入**。它挂在内核自己的页面里。
- **运行体**：干活的那一半，是一个编译到 `wasm32` 的模块，在内核进程里跑。

两半不是「前端与后端」的另一个说法。分界线是**能力**：界面那半只有界面能力（挂载点上下文、调内核那条窄通道、写状态、导航），干活那半只有工作能力（取网址、自己的数据目录、读视频信息、写日志）。**没有哪一半能同时拿到两边**，因此「写进库里的东西」与「画在屏幕上的东西」在类型上就不可能由同一次调用一起产生。

**被否决的：只允许一半。** 爬封面插件没有界面（它由右键菜单触发，见 ADR 0045），在线编辑封面插件必须有界面。只留一半，这两类里总有一类做不出来。

**被否决的：把插件界面也叫「后端」。** 在本仓库「后端」指的是 `src-tauri/`，也就是内核的 Rust 侧；用它指插件的运行体，会让「后端拒绝了这个请求」这句话在两种读法下都说得通。两半因此叫**插件界面**与**运行体**，「后端」永久保留给内核。

## 四、内核与插件之间只有一条窄通道

插件想请内核办事，只有一条命令。内核通过**调用者身份**认人——身份由创建那个上下文的闭包绑定，**不采信插件自己发来的任何身份字段**。

授予运行体的能力只有四样：取一个网址、读写自己的数据目录、写日志、读本次调用的视频信息。**不授予**：任意文件系统、直接写数据库、调度或调用内核命令、开放监听端口。

**插件永不直接写数据库。** 在数据挂载点上它只**返回数据**，由内核写。因此「插件往库里写了什么」是一条可以被审计的窄路径，而不是任意写入。

如实记下这条边界的性质：插件界面与内核**同处一个页面**，所以这是一条**约定 + 闭包**的边界，不是进程边界。真正硬的那一半是运行体——它跑在 WebAssembly 里，没有任何环境权限（ADR 0044）。

## 五、失败绝不阻塞内核

一次调用抛错、崩溃或超时：记下插件名 → 给一条**点名插件与挂载点**的通知 → 这一次调用视同插件什么都没说 → 内核照常走完。

同一个插件在**五次不同调用**上失败 → 自动停用。理由不是惩罚，是**通知会变成噪声**：一个每次渲染都失败的插件，如果每次都弹一条，用户就没有办法在这个应用里做别的事。

这条被写成不可协商：它是第二节那条「只能加料」在运行期的兑现。

## 六、为什么不是现成的方案

**cordis**（以及基于它的 `dsh-desktop`）评估过并否决。它的 `Service` 是「单实例、可被覆写」，与这里的挂载点「多贡献者 + 合并」语义错配；它的挂载点语义其实落在**事件**上，而事件是它身上最不值钱的部分——用了挂载点就等于没用上它（依赖注入 + 依赖驱动的生命周期）的主卖点；它没有权限、没有沙箱、没有插件顺序、没有逐次降级。它的加载器还是 Node 专属的。

**整体换底层（Electron + Node + cordis）** 同样否决。它买到的是「一个现成的 DI 容器」与「npm 当插件分发渠道」，代价是重写一个已发布的产品、作废一批 ADR 与门禁、丢掉轻量。而且**换底层解决不了这里唯一的真摩擦**——那条摩擦来自「运行体零环境权限」这个决定，而它在 Tauri 里就能改。

它值得借的是三条**想法**，条例见下。

## 七、从上游借来的三条

不是借代码，是借纪律：

1. **声明即认领**：一个位置由一处声明并独占，注册进没有声明过的位置在**加载期**就失败。好处是卸载时只有一条生命周期轴——声明者一倒，它声明的子位置连同其上的全部贡献递归塌缩。
2. **注册即得 disposer**：每个注册口**自己返回**清理函数，接进一个统一的收集器，**逆序执行、可异步等待**。原先把清理押在插件自己的 `onDispose` 上是个空口子——**忘记是默认值**；这条把它倒过来，要泄漏得刻意绕开 API。
3. **契约做成生成的、机器可读的目录**：见 ADR 0045。

上游其余的**不借**：它的信任模型是「信任插件 + 出事了能恢复」，与这里选的「运行体零环境权限」是两个立场，不能各取一半。

## 它推翻了什么

插件系统是新增的一层，没有推翻已落地的代码或文档。它约束的是将来：

- 内核的业务代码不得认识任何具体插件的名字——只调插件宿主一处。
- 插件的失败不得让任何内核流程停下，「扫描／媒体处理／收藏／共享／更新在插件失败时行为不变」是一条要一直成立的回归。
- 插件写入库里的路径只有挂载点返回值一条，不新开第二条。

## 实施状态

**宿主、注册口、生命周期、两侧派发、运行体、两个界面类挂载点的渲染、用户可调的插件顺序与 `plugin.settings` 的往返都已落地。** 规格见 issue #82，术语已进 `CONTEXT.md`。

- 宿主与失败降级：`src-tauri/src/plugins/` 的 `PluginHost` 常驻，按 id 认插件、把一次调用的失败降级成点名插件与挂载点的通知，内核其余代码不认识任何插件名。
- 界面一侧：`frontend/src/plugins/` 的注册口、统一收集器（逆序执行、可异步等待）与插件页；插件往界面上加东西只经由注册口。插件页画的是内核给出的状态，不再是替身端口。
- 生命周期（issue #86）：清单四条校验——必填字段、id 合法且不重复、挂载点接口版本在范围内、声明的能力在允许的四项之内，任何一条不过就列出来并标出问题、不加载，版本不合另有一条文案；从本地目录或压缩包装入，装之前先预演（落在哪里、声明了哪些能力、有哪两半）；逐个启停，停用不动目录里的内容；卸载只问一次「连同插件写进库里的内容一起删吗」，报出会影响的 `video_fields` 行数，默认保留；安全模式把启用记录改名成带时间戳的备份、恢复默认全关、插件目录一个都不动。全部经既有错误协议，两种语言都有文案。
- 不做热插拔：生命周期命令答的是盘上现在的样子，页面按这个回答重画并说明「下次启动生效」。
- 运行体（ADR 0044）：运行体就是 `WasmBody`，一个插件一个常驻的 wasm 实例，由 `plugins/loading.rs` 在启动时建起来。**该 ADR 在 #89 之前一直是「未实施」**，本条的这句曾经也这么写；两边现在都改了。
- 运行体侧的四处派发（#87 起）：`plugins/dispatch.rs` 上有 `video_fields`（链式，依次问、取第一个非空）、`plugin_settings`、`scan_completed`、`video_action`。最后一处**只问点名的那一个插件**，因为目录写的是「插件往视频的右键菜单加一个**自己的**动作」——问所有插件会让菜单项与插件脱钩，而没有插件界面的插件只有这一条路能触发自己。封面那条通路的细节（内核去下、路径进库、只有一处认识 `cover`）在[插件系统](../插件系统.md)。
- 界面侧的渲染：两个界面类挂载点都已渲染，各自都是「`DRAWN_HERE` 声明位置 + 一个内核页面读它」这一对。`app.page`——`frontend/src/plugins/PluginHostProvider.tsx` 的 `DRAWN_HERE` 声明它，`MainNav.tsx:127` 与 `PluginPageView.tsx:40` 读它，插件注册的页面进导航、有自己的路由。`video.panel`（issue #93）——同一个 `DRAWN_HERE` 也声明它，`usePluginPanels()`（同文件）读它，`VideoDetails.tsx` 把每一块画在文件自己的头部与元数据表之间，位置由面板自己定。**这一处曾经是个功能缺口而不是「位置空着」**：注册口按目录校验，注册进没有声明过的位置在加载期抛 `MountPointError`，于是声明了 `video.panel` 的插件界面整个起不来（行上写的是 `plugin.interface.start_failed`），插件装了却什么都不出。
- **插件顺序由用户调整已落地（#94）**：顺序写在 `$APPDATA/plugins/order.json`（`plugins/order.rs`），由 `Store::ordered`／`set_order` 读和写（`plugins/store.rs:147`、`:184`），启动时在遍历之后一次性盖到轮转上（`plugins/loading.rs:100`），命令 `set_plugin_order` 收整份 id 列表（`commands/plugin.rs:43`），插件页每行两个箭头改它（`frontend/src/pages/PluginsPage.tsx:244`）。注册口的 `order` 钩子（`frontend/src/plugins/registry.ts:187`）两端都接上了：`PluginHostProvider.tsx:126-127` 造一只盒子给宿主与注册口，`host.ts:350` 每收到一份答案就写进去，注册口在有人读位置时读它。关掉插件保留位置、卸载带走位置、没命名的排最后——三条规则与各自的代价写在[插件系统](../插件系统.md)的 14.6 节。
- **`plugin.settings` 的往返已落地（#91）**：值住在全局的 `plugin_settings` 表（`repository/plugin_settings.rs`，随版本 8），读与存两条命令 `list_plugin_settings`／`save_plugin_settings`（`commands/plugin_settings.rs:36`、`:69`）都带 `spaceId`，而**存的时候不用它**；已存的值随每次提问经 `PluginSettingsParams.values` 交给插件，因此保存那一刻的第二次提问同时就是交付；启动时 `settings::hand_over`（`app.rs:141`）给有已存值的插件补一次，交不成只写一行日志；逐字段的拒绝走既有错误协议，字段名在 `AppError.params.field`，界面画在那个字段的包装里（`frontend/src/plugins/PluginSettingsForm.tsx`）。三个决定——值存哪、值怎么回插件、文案留在哪——写在[插件系统](../插件系统.md)的 14.7–14.9 节。
- 示例插件两份，都在 `examples/plugins/`（都只有插件界面，是作者照抄改的样板）：`hello-page/` 只注册 `app.page`，`video-panel-demo/` 注册 `video.panel`。**为什么是两份**：两个界面类挂载点画在两个不同的地方，只有一份的话另一处在验收页里永远没有东西可画，「没有插件注册这里」就与「注册了但没画出来」分不开。见[插件系统](../插件系统.md)的 14.5 节。
