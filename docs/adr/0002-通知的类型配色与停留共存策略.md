# 通知以类型决定外观、以调用方决定停留与共存

浮动通知原先是两份近乎逐行重复的组件：成功与错误各一份，配色是各自用 Tailwind 手写的浅底加语义色描边，正文结构（标题加说明）与交互（关闭、重试、排查编号）在两处分别维护。新增一种通知需要再复制一份样式。同时完成统计不会自动消失，会一直停在右上角遮挡内容。

改造后的形态是：只保留一个通知组件，类型决定配色、图标与播报紧急度；正文与动作由调用方以子节点提供；停留多久与是否被别的通知顶掉由调用方与宿主决定。以下三处取舍是刻意选择，不是可以顺手「修正」的疏漏。

## 为何采用外层框架加子节点，而不是逐类型的包装组件

被否决的替代方案有两个。一是**每个类型一个包装组件**，由一个外壳加组合实现；二是**单一组件内部按类型分支**，用条件语句决定配色、图标与角色。

前者会让外壳同时承担两件事：它既要知道每种类型长什么样，又要为「只有部分类型成立」的属性预留位置，于是重试按钮、排查编号这类错误独有的入口会变成成功通知也能传入的参数，非法状态在类型上可表达。后者则是既有约束「避免堆叠条件分支形成职责混杂的万能组件」直接禁止的形态。

选定的做法是把类型相关的一切压进一张查找表——配色类、图标、ARIA 角色、进度条色各一项——组件本体只做查表与渲染。这样组件内部不出现按类型的分支，这条约束在单组件方案下仍然成立；而正文留在调用方手里，通知组件就不必假设一条通知里有什么。

被否决的还有「保留手写 Tailwind 配色、只是合并组件」。它保住了外观，却把「界面优先使用 daisyUI 现有组件」这条约定继续悬空，且新增类型依然要手写配色。改用原生 alert 后，外观由设计语言而非本仓库维护。代价是标题与说明整段被染成语义色，与原先的中性文字加语义色描边不同，需要视觉验收；这次验收量出的亮色可读性问题见下节。

## 为何停留策略由调用方决定而不是由类型决定

自动关闭时长是调用方传入的可选参数，**省略即常驻**，不引入 `Infinity` 或 `0` 之类的哨兵值——魔法值需要额外约定才能读懂，而「不传就是不走」在调用点上一眼可辨。

按类型决定停留是更省事的做法（错误常驻、成功 3 秒），但它无法表达真实需求：**同一种类型在不同场景下停留策略不同**。完成统计在没有失败项时该自动消失，在含失败项时必须留下——判断依据是这次扫描的内容，不是「成功」这个类型。把判断交给调用方后，通知组件不需要知道 `failures` 是什么，这个纯函数与既有的「是否播报扫描完成」放在同一模块，两者同属「一次扫描完成如何对外反馈」。

因此错误的调用点不传时长而天然常驻，也不需要在组件里为错误写例外。

## 为何共存规则给错误通知留例外

非错误通知全局只保留最新一条：新的出现时，先前那条被关闭。错误通知不受影响——它不顶掉别的通知，也不被别的通知顶掉，多条错误继续在同一容器堆叠。

理由是一条例外比两条规则便宜。错误通知正是需要用户处置的信息（读说明、复制排查编号、重试），在用户读到之前被一条成功统计挤掉，损失的是这次失败的全部上下文；而成功统计被后来的成功统计取代，损失的只是过期数字。

**必须记录一处现状：非错误互斥目前没有端到端可复现场景。** 应用当前只有一处非错误通知来源（完成统计），它只可能被自己取代。这条规则的验证只在渲染两条非错误通知的测试里完成，不代表它在真实流程中被走到过。后人看到这段代码时不应误以为该机制已在生产路径上生效。

## 为何亮色改用实心 alert、暗色保留柔和配色

视觉验收量到柔和配色在亮色主题下可读性不合格：正文 2.62:1、排查编号 1.59:1、进度条填充对轨道 1.72:1。原因是该配色的机制——用色调本身作文字色，压在 8% 同色调的底上——而亮色的 `--color-error` 亮度约 0.71，压在近白底上天然偏低；暗色主题的底本身很暗，同一个色反而过线（5.03:1）。因此亮色改回 daisyUI 默认的实心 alert，底色用色调、文字用该色调的 `-content`，对比由框架的配色配对保证；暗色继续用 `alert-soft`。放弃「两种主题外观一致」，换来两种主题都可读。

连带一处：进度条不能用 `progress-{类型}`。daisyUI 的 `.progress` 用 `currentColor` 画填充、用同色的 20% 画轨道，而实心通知的底色正是该色调，填充会与底色同色而消失。因此实心主题给进度条该类型的 `-content` 前景色，暗色柔和主题给色调本身。

改动后实测（取两种主题下各类型的计算色）：正文与排查编号 5.03–6.95:1，进度条填充对轨道 4.65/4.23/2.79/3.17:1，填充对通知底不低于 5.03:1。暗色错误通知的填充对轨道 2.79:1 仍略低于非文本的 3:1 目标，但它对通知底是 5.03:1，且条形的长度本身也表达进度，故保留。排查编号原先带 `opacity-60`，在暗色下只有 3.42:1，一并去掉。

## 取舍与影响

- **关闭旧通知必须真正调用它的关闭回调，不能只做视觉隐藏。** 通知的可见性由其所属方持有的状态决定（错误状态、完成统计状态）；隐藏而不清空状态，下次渲染会把同一条重新挂出来。
- **同一状态槽位的内容被替换时不得走互斥路径关闭「旧通知」。** 该槽位的关闭回调是无条件清空的，在写入新值之后再调用它会把刚写入的新值清掉。这类替换以**重新挂载**的形式到来：开始新操作时先清空完成统计，下一次完成才写入新值，通知因此被卸载再挂载，倒计时天然从完整时长开始。实现依赖 React 在同一提交中先运行卸载实例的清理、再运行挂载实例的副作用，使协调者不会把已卸载的自身当作待关闭对象；这一依赖由测试固定下来，改动协调逻辑时不能假定顺序无关。
- **一次扫描会发出两条完成事件，第二次是原地更新。** 扫描作业在结束时发布一次完成状态，命令入口在其返回后再发布一次，前端因而对同一个槽位连续写入两次。第二次不会重新挂载，倒计时沿用剩余量——差值只有毫秒级，因为两次发布紧邻，且两者描述的是同一次扫描。若将来要求原地更新也重置倒计时，需要一个随通知变化的标识来驱动重新挂载，现有接口形状没有这个标识。
- **非错误通知的宿主角色的变化。** 宿主从「纯堆叠容器」变为「1 条非错误通知加 N 条错误通知」，互斥协调放在宿主一侧而非通知组件内，因为它是多条通知共同渲染才成立的行为。
- **交接给既有约定的部分。** 自动关闭的暂停与进度条、类型词表与原生配色、错误常驻等规则写在[开发指南](../开发指南.md)的「通知」一节；宿主、对话框优先级与「多条错误堆叠」的既有要求保留在该节原文。[设计基线](../本地视频统一启动器-开发基线.md#6-ui-约定)的 UI 约定一节同步完成统计的自动关闭与共存规则。ADR 不重复这些内容，只记录上面的取舍。
- **已知限制：3 秒对礼貌播报偏短。** 自动关闭的完成统计使用礼貌播报，读屏会等当前内容读完才开口，可能在播报开始前就到期；悬停与聚焦暂停对此没有帮助，因为读屏用户不会去悬停。当前保留 3 秒，若后续要照顾读屏用户应提高到 5 秒量级。
- **领域术语表不新增条目。** 通知、类型配色、自动关闭属通用界面概念，不属于本项目领域术语，因此不进入 `CONTEXT.md`。
