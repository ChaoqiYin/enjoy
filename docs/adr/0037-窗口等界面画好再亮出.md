# 窗口等界面画好再亮出

用户的原话：

> 能不能等加载完主题值了才显示窗口，就可以去掉启动画面了

今天有一段「窗口已经亮了、界面一行都还没画」的窗口期：主窗口以 `visible: false` 起（`src-tauri/tauri.conf.json`），`main.rs` 的 `.setup()` 在 `initialize_backend()` 成功后调 `window.show()`——而前端这时才刚要开始读偏好（`initializeTheme()` → `initializeLanguage()` → `readCurrentSpace()`）再 `root.render()`。这段窗口期由启动加载画面盖住，那套做法记在 ADR 0035（本轮删除，故事并入本文件）。

本轮把因果倒过来：**窗口不在前端画好之前亮**，于是启动画面没有东西可盖，整段删掉。

**关键设计点：信号必须是「React 已经提交」，不是「主题值已经读出来了」。** 只等主题的话，开发模式下样式表（`style.css` 是 `main.tsx` 的模块导入，随脚本一起来）依然没到，屏幕上还是无样式白底；打包后 `index.html` 里硬编码的 `<html data-theme="dark">` 也依然会让偏好亮色的用户从深色翻到亮色。要盖住的东西在提交那一刻才消失，所以信号只能来自提交。

用户拍板的四件事：

| 项 | 取值 | 代价（见 §四） |
|---|---|---|
| 亮窗兜底 | **不做** | 前端在发出信号前挂掉 → 窗口永不出现，只剩一个没有窗口的进程 |
| 启动画面 | **一并删掉** | 兜底缺失时屏幕上没有任何东西可看 |
| ADR 0035 | **删掉**，故事并进本文件 | 它从未提交；0036 有两处引用它，一并改写 |
| 提交时机 | 改动先都放着，本轮做完一起提 | — |

## 一、改了什么

### `src-tauri/src/commands/window.rs` —— 新增 `show_window`

与 `close_window` 并列，注入 `tauri::WebviewWindow`，成功则（仅 debug）开 DevTools：

```rust
#[tauri::command]
pub(crate) fn show_window(app: AppHandle, window: WebviewWindow) -> Result<(), AppError> {
    if let Err(failure) = window.show() {
        let error = AppError::new("app.startup.failed", failure);
        native::startup_failure(&app, &error);
        return Err(error);
    }
    #[cfg(debug_assertions)]
    window.open_devtools();
    Ok(())
}
```

三处选择：

- **同步，不是 `async`**（`close_window` 是 `async`，只因为它要 `await` 共享服务的结束）。这个命令跑在主线程、与 `.setup()` 里原来的 `window.show()` 同一语境，不创建需要 await 的东西。
- **用应用自己的命令，不用 `@tauri-apps/api/window` 的 `show()`**。`scripts/check-permissions.mjs` 那张权限表的存在正是为了抓「又去够那个包」；`close_window` 与 `restart_app` 都没有 ACL 条目，本命令也不需要，`capabilities/main.json` 未动。
- **失败沿用 `.setup()` 原来的待遇**：`AppError::new("app.startup.failed", …)` 加 `native::startup_failure(&app, &error)`，并把错误回给前端（前端不据此做事，见下）。返回 `()`，所以 `check-seam.mjs` 不动。

### `src-tauri/src/main.rs`

`.setup()` 缩成三件事——初始化日志、初始化后端、失败时报告——`show()` 那一块连同它的 `return Ok(())` 一起去掉。`use tauri::Manager;` **必须保留**：`.on_window_event` 里的 `window.try_state::<app::AppState>()` 要它。

### `frontend/src/shared/WindowReveal.tsx`（新增）

```tsx
export function WindowReveal({ children }: { children: ReactNode }) {
  useLayoutEffect(() => {
    windowApi.show().catch(() => undefined);
  }, []);
  return <>{children}</>;
}
```

- **`.catch` 不是兜底**：失败已由后端在原地报告（`native::startup_failure` + `tracing::error!`），前端没有对自己窗口的权限、窗口又是不可见的，无处可报。不接就是未处理拒绝。
- **依赖数组留空**：`main.tsx` 的重试按钮会再调一次 `start()`，同位置的 `root.render` 是同一类型、不会重挂载，effect 不会第二次触发；就算触发，对已可见窗口再 `show()` 也无害。

### `frontend/src/main.tsx`

成功与 `catch` **两条**渲染路径都套 `<WindowReveal>`。`catch` 那条不是顺便：那条通知由同一个 root 画，而窗口正是被这个组件亮出来的，不套就是「永远不会出现的窗口里的通知」——恰好是最不能瞒过去的那一类失败。

### 删除

`frontend/src/shared/SplashGate.tsx`、`SplashGate.test.tsx`（均未跟踪），`frontend/index.html` 整段回退到 HEAD。`<html lang="zh-CN" data-theme="dark">` 保留——ADR 0036 已给它定了位置（读偏好之前的值，也是读失败时的值）。

`frontend/public/assets/generated/enjoy-logo-light.png` **不能删**：`BrandLogo.tsx` 与 `scripts/generate-brand-assets.py` 仍在用同一条路径。

### `frontend/acceptance/web-fixture.ts`

补一条 `case 'show_window':`。验收页导入的是**同一份 `main.tsx`**，新命令会在那里被真实调用，不补就落进 `default:` → `unimplemented(command)` → 页面顶部挂红条并抛错。

### 为什么是 `useLayoutEffect`，而理由不是「同一帧」

窗口被 ordered-out 时 WebKit 不做渲染更新（rAF 同样被门控），**隐藏期没有合成**。所以两种 hook 都不可能改变第一可见帧的内容，差别只剩调度投递次数：`useLayoutEffect` 跑在 `root.render()` 本来就必须依赖的那次提交里，`useEffect` 需要调度器第二次投递，而「隐藏视图里那次投递能不能按时到」在手头源码里没有依据。ADR 0035 §二 那段「同一帧」的论证就此退休——它描述的是启动画面被摘掉的那一帧，不是窗口出现的那一帧。

### 没有改窗口底色

本轮一度在 `tauri.conf.json` 的主窗口块加了 `"backgroundColor": "#111317"`，指望它兜住「窗口亮了、WebKit 还没合成出第一帧」的那一缝。**实测证明它做不到，配置已撤**，见 §三。

## 二、实测

装置：`screencapture -v -V <秒> -x` 录整屏（60fps），`ffmpeg` 抽帧，再按窗口矩形裁。窗口矩形由一段小程序调 `CGWindowListCopyWindowInfo` 按 PID 取最大者得到。

**为什么不用 `screencapture -l <CGWindowID>` 连拍**（ADR 0035 用的那套）：连拍只有 0.44–0.55 秒一帧，而这一缝比一帧还短，连拍分辨不了。录屏是唯一够快的。

### 正测：窗口出现的那一刻不是界面

两次独立录屏，读数**逐像素一致**（下为其中一次的抽帧统计，窗口矩形 `363 75 1194 796`）：

| 帧 | 时间 | 内容 | 均值 | 近白占比 |
|---|---|---|---|---|
| ≤743 | ≤12.38s | 桌面 | (39, 40, 50) | 3.9% |
| **744–754** | 12.40–12.57s | **空窗口，交通灯已在** | **(240, 240, 240)** | **95–97%** |
| 755–758 | 12.58–12.63s | 开始有内容 | (241, 236, 237) | 90% |
| 759–762 | 12.65–12.70s | 界面大体画上 | (194, 188, 245) | 69% |
| 763 起 | 12.72s | 稳定 | (212, 209, 242) | 74% |

**从窗口出现到界面画上约 0.18–0.25 秒**，那一段是一层近乎均匀的浅灰白，且**没有从桌面色渐变过来**（744 直接就是 239，745 起稳定）——所以它不是窗口的打开动画，是窗口的内容本身。

### 品红实验：窗口底色配置对这一缝没有任何影响

把 `backgroundColor` 从 `#111317` 改成屏幕上不可能自然出现的 `#FF00FF`，重编译重录。**整个窗口（含标题栏）品红占比 0.00%**，读数与 `#111317` 那次一致：

| 帧 | 时间 | 均值 | 品红占比 |
|---|---|---|---|
| 602 | 10.03s | (238, 238, 238) | **0.00%** |
| 606 | 10.10s | (240, 240, 240) | **0.00%** |
| 613 | 10.22s | (241, 236, 237) | **0.00%** |
| 615–627 | 10.25s+ | 界面 | **0.00%** |

配置链本身是通的，逐环查过：`tauri.conf.json` → `tauri-codegen` → `tauri-runtime-wry-2.11.4/src/lib.rs:969` 把它交给 tao → `tao-0.35.3/src/platform_impl/macos/window.rs:548-560` 在构建窗口时调 `ns_window.setBackgroundColor`。**但落点被盖住了**：那一缝显示的是 WKWebView 自己合成的结果，而 wry 那个本该让窗口背景透出来的 `drawsBackground = false`（`wry-0.57.0/src/wkwebview/mod.rs:371`）是**私有 KVC key**，其源码注释自己标着 `NOTE: Private API`。

**这条否定了 ADR 0035 §三 末尾的预测**，原文是：

> 真要在应用里消掉它，只能改窗口自身的底色（Tauri 的 `backgroundColor`），那是另一件事，本轮没做。

本轮做了。改不了。

顺带，这次实验也回答了「标题栏会不会被窗口底色染色」——整窗 0.00% 品红，没被染。

### 负测：无兜底的现场证据

`/tmp/slow-proxy.mjs` 挡在 dev server 前，只扣住 `/src/main.tsx` 一个请求 15 秒：

```
T+ 2s  进程=活着  窗口=[没有窗口]
T+ 4s  进程=活着  窗口=[没有窗口]
…
T+16s  进程=活着  窗口=[没有窗口]
T+18s  进程=活着  窗口=[420 119 1080 721]
```

代理日志坐实因果：`held  /src/main.tsx?t=…` 一行，其余模块全是 `pass`。**「进程活着、窗口不存在」这个状态稳定维持了十几秒**——这就是无兜底的全部内容：屏幕上什么都没有，应用没崩，只能从 Dock 退出。

### 装置失效，如实记

本次会话中途 macOS 的**屏幕录制权限掉了**：`screencapture -V <秒>` 不再收尾（跑满 3 分 25 秒也不写文件），`screencapture -x` 单张返回**纯黑**（不同颜色数 = 1）。此前两次录屏是在权限还在时完成的。

因此**深色系统外观下的那一缝没有读到**，§四 里与之相关的一条只能是推断，不是读数。

### 测试

`npm test` **85 文件 485 用例**全绿（基线 483：删 SplashGate 两条，加 WindowReveal 四条）。`npm run check` 七项全过，报告 32 个调用点、32 个注册处理器、27 条夹具用例。`cargo check` 无警告。

## 三、代价

**没有兜底。** 前端若在 `show_window` 之前挂掉，窗口永远不会出现，屏幕上只剩 Dock 里一个没有窗口的进程。这是用户明确选的一条（三个选项里他选了「不做兜底」），§二 的负测就是它的现场证据。相比改动前，故障从「屏幕上有一层启动画面挂着」变成「屏幕上什么都没有」——更好看，也更难判断。

**故障可见性不对称。** 后端失败仍然看得见：`native::startup_failure` 开的是一个独立的 `startup-error` 窗口加系统对话框，不依赖主窗口。前端失败则屏幕静默。

**窗口出现后仍有一缝，只是短了。** 约 0.18–0.25 秒，WKWebView 尚未合成出内容时的默认底色。它**不是零**，本轮的立论里那句「窗口的第一帧就是界面本身」是**错的**，实测当场证伪——写在这里是因为它正是那种最容易留在注释里骗下一个人的话。改动前的窗口期是前端读偏好的全长（几百毫秒到数秒），改动后是 WebKit 的首次合成，短了一个量级，但没消失。

**那一缝的颜色管不了。** 品红实验证明它不随应用侧任何配置走（§二），所以它只可能跟随**系统外观**（WKWebView 的默认底色是动态系统色）。若如此，系统外观与应用主题不一致的用户会看到一次极短的颜色闪。**这一条本轮没有读到**，因为屏幕录制权限掉了——写在这里的**是推断，不是读数**，要断言它得再量一次。

**调试入口变了。** `open_devtools()` 现在在 `show_window` 里（保住原先「先 show 再 devtools」的顺序），但 macOS 的 inspector 停靠在 webview 内部，窗口没出现时它同样不可见。debug 构建下排查「前端没起来」要走 **Safari 的「开发」菜单**（wry 在 `devtools` 为真时设 `setInspectable`）或日志文件。

**「配置传到了」和「配置看得见」是两件事。** 窗口底色这一笔最终没留下，但它是本轮最花时间的一段：链上每一环都读过了、都通，落点却被一层私有 API 的默认行为盖住。仓库里那些「加了配置却看不出效果」的改动，值得先做一次足够刺眼的否定实验（这里是用 `#FF00FF`），再决定要不要留。

## 它推翻了什么

**ADR 0035 整体，本文件取代它。** 固定深色的启动加载画面这套做法撤销，连同它的四条代价：`index.html` 里抄写色值（随文档回退消失）、亮色用户看到深浅翻转（不再有启动画面这片深色）、`html` 多一处页面底色来源（同）、启动卡住时启动画面常挂（现在变成窗口永不出现，见 §三第一条）。

**ADR 0035 §三 末尾那个预测被证伪**：改窗口自身的底色消不掉那一缝，§二 的品红实验是证据。

**ADR 0035 §三 记的两条装置教训仍然有效，并升级了**：代理扣住 `/src/main.tsx` 拉长窗口期（本轮负测用的还是它）；按窗口取图而非按屏幕矩形取图。第三条最贵的教训——**不做「去掉代理」的对照，就会把装置造出来的时序当成应用本来的样子**——本轮加了一条新的：装置本身会说谎（权限掉了以后 `screencapture` 返回纯黑而不是报错，看文件大小看不出来，只有读像素才知道），所以**每组读数都要先确认装置还在工作**。

**ADR 0036 §四 的两处依赖 0035 的地方已改写**：深浅翻转现在只关乎那一缝（§三），且只在前端渲染晚于窗口亮出时可见；启动画面已不存在。（**注意**：这个仓库从不删已落地的 ADR，0035 是唯一一个例外，因为它从未提交。）

**没有推翻的**：`index.html` 的 `data-theme="dark"` 照旧，ADR 0036 给它的位置（读偏好之前的值、读失败时的值）不变。
