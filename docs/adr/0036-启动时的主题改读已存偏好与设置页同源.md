# 启动时的主题改读已存偏好，与设置页同源

用户报的现象：设置页里「亮色」是选中态，窗口画出来的却是暗色，而且一直如此，直到手动点一次。

## 一、为什么是两处各答各的

界面上「主题是什么」有两个答案，来自两条互不相干的读：

| | 谁读的 | 读到的 |
|---|---|---|
| 设置页的选中态 | `SettingsProvider` → `get_settings` → `preferences.json` 的 `theme` | `light` |
| 窗口的颜色 | `initializeTheme()` → `localStorage['enjoy-theme']` | 什么也没有 → 兜底 `dark` |

`enjoy-theme` 这个键，全仓只有一处 `getItem`（`frontend/src/theme/ThemeSetting.tsx`），**没有一处 `setItem`**。所以那个读永远空手而归，`applyTheme(saved === 'light' ? 'light' : 'dark')` 永远走 `dark` 那一支——偏好写的是亮是暗，启动都画暗色。

**这个孤读是有来历的，不是一直如此。** `1abd1bb feat: unify persisted settings state`（2026-09-14）把「谁拥有偏好」从浏览器存储搬到后端：`ThemeSetting()` 里的 `useState(() => localStorage.getItem(key))` 换成 `useSettings().state.theme`，`change()` 里的 `localStorage.setItem(key, value)` 被删掉——而 **`initializeTheme()` 原封未动**。那个提交删掉了写，留下了读，从此这个键只读不写。（同一提交之前 `ThemePreference` 还是三态 `'system' | 'light' | 'dark'`，`ThemeSetting` 还听着 `prefers-color-scheme`；跟随后被砍掉，那一截也跟着没了。）

**为什么不能不管它。** [开发基线](../本地视频统一启动器-开发基线.md) 写着「页面静态默认深色，启动时按保存的偏好改写」。前半句由 `index.html` 的 `data-theme="dark"` 一直做着，**后半句自 9 月 14 日起就没有实现**。这一轮把它补上。

**为什么启动要自己读一次，而不是复用 `SettingsProvider`。** 它在 React 里，初始值是 `defaults`（`theme: 'dark'`），那次真正的读在 `useEffect` 里——也就是说它给出的第一个答案是默认值，第二个才是偏好。界面第一次绘制拿到的必然是前者，而那正是要修的那一刻。启动读取必须发生在 `root.render()` 之前。

## 二、改了什么

### `frontend/src/shared/api.ts` —— 新增 `readTheme()`

与 `readLanguage()` 并排，在同一个「启动前要读的东西」段落里：

```ts
export function readTheme(): Promise<SettingsState['theme']> {
  if (!hosted()) return Promise.resolve('dark');
  return settingsApi.read().then((settings) => settings.theme);
}
```

走的就是设置页那条读（`settingsApi.read()` → `get_settings`），所以两处的答案从构造上就是同一个，不会再分叉。无后端时答 `dark`，与后端给「解析不出的偏好」准备的默认值同值（`src-tauri/src/preferences/mod.rs` 的 `Preference::Theme` → `default: "dark"`），与 `readCurrentSpace` / `readLanguage` 的兜底写在同一个地方。

### `frontend/src/theme/ThemeSetting.tsx` —— `initializeTheme()` 改读偏好

`const key = 'enjoy-theme'` 与那次 `getItem` 删掉，改成 `applyTheme(await readTheme())`，失败时不抛：

**读失败就保持原状，理由是那一刻文档已经是暗色。** `index.html` 在任何脚本之前就把它声明成暗色了，而暗色也正是后端给「读不出的偏好」的答案——所以没有什么要补的，更没有理由为窗口的颜色拒绝启动。这与 `SettingsProvider` 对同一次读的 `.catch(() => {})` 是同一个取舍。

### `frontend/src/main.tsx` —— 两次启动读并行

`await Promise.all([initializeTheme(), initializeLanguage()])`。两次都是对后端的读、互不依赖，串行就是把两个往返依次记在窗口期上。

## 三、实测

**单测。** 新增 `frontend/src/theme/initializeTheme.test.ts` 两条：偏好为 `light` 时把 `light` 写进 `document.documentElement.dataset.theme`（同时断言 `invoke` 收到的是 `get_settings`，即与设置页同一条读）；读失败时不动文档。缝（`@tauri-apps/api/core` 的 `invoke`）与 `frontend/src/i18n/languageSync.test.ts` 同一套写法。

**真机。** 这台机器的 `preferences.json` 是 `theme: "light"`，两次启动之间没有改过它：

| | 窗口底色采样 | 界面 |
|---|---|---|
| 修复前（17:02 启动） | `(17, 19, 23)` | 视频库深色 |
| 修复后（17:10 启动） | `(243, 243, 243)` | 视频库亮色、红色选中项、570 个视频、24 页 |

设置页的选中态与窗口的颜色从此一致。

## 四、代价

**启动多一次后端读。** 与语言那次并行，所以没有多出一个串行往返，但「首次绘制」的前置从一次读变成了两次读的较长者。

**主题读取从「不会失败」变成「会失败」**，失败落到暗色。这是刻意选的，理由见 §二：宁可暗色，也不拿一个颜色去挡住启动。

**亮色用户会看到一次深浅翻转。** 启动那一刻的底色是深色，界面是亮色。这条代价在启动加载画面上记过，但**从这一轮起它才真的会发生**——修复前这台机器上的应用画的也是暗色，两者同色，翻转看不出来。（**它后来换了载体**：启动加载画面已在 [ADR 0037](0037-窗口等界面画好再亮出.md) 里删除，这次翻转变成窗口出现之后、WebKit 合成出第一帧之前那一缝的事，见该文件 §三。）

## 它推翻了什么

**「本轮真机实测没看到这次翻转」这句从这一轮起不再成立**：应用现在按偏好画亮色，翻转是真的。**关于启动画面本身的结论后来整体作废**——那套做法在 [ADR 0037](0037-窗口等界面画好再亮出.md) 里被撤掉了；但这条代价没有随之消失，只是挪到了窗口出现那一缝上。

**[开发基线](../本地视频统一启动器-开发基线.md) 里「页面静态默认深色，启动时按保存的偏好改写」的后半句，从「没有实现」变成「实现了」。** 前半句 `index.html` 的 `data-theme="dark"` 仍然在，而且从现在起它有确切的位置：它是**读偏好之前的那个值**，也是**读失败时的值**。

没有推翻别的成文决定。
