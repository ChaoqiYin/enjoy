# 空间之间不共享任何记录

空间是一个自洽的独立视频库：自己的扫描目录、视频记录、收藏与播放历史。同一条路径在不同空间里是两条互不相干的记录，视频表的唯一约束因此从 `path` 改为 `(space_id, path)`。用户在同一时刻只处在一个空间里，界面展示的都是当前空间的内容。

## 为何记录完全独立，而不是让文件记录全局共享、只把使用记录按空间分开

被否决的那条路是：`videos` 继续按路径全局唯一，空间只是它的一组归属，`favorite`、`play_count`、`last_played_at` 搬出 `videos` 做成按空间的表，同一文件只被 FFprobe 与 FFmpeg 处理一次。它更省重复处理，也更贴合[文件身份](0004-文件身份改用大小与修改时间.md)的现有措辞——那个术语讲的本就是文件本身，与空间无关。

否决的理由是三条连锁代价。其一，三条使用记录要搬出主表，`列表读数`、收藏切换、播放计数三处都要改成带空间条件的连接。其二，[扫描合集](0003-扫描合集的来源与过期记录的清理判据.md)的定义是「当前保存的全部视频目录的并集」，共享记录之后它必须拆成每空间一套，而清理判据会多出一种它从未处理过的情形：空间甲移除了目录丙、空间乙仍配着丙，丙下的记录**不能**删。这条依赖把两个本来互不相干的空间在存亡判定上绑在一起。其三，独立路线是机械的——加一列、改一条唯一约束、把既有的按路径读改写为按空间加路径，清理判据的形状一个字不用改。

## 为何允许同一目录配置在多个空间，而不是在添加时拦截

目录配置可以重复：用户在空间甲配了 `D:\Movies`，切到空间乙再加同一个目录是合法操作，既不报错也不提示。拦截需要在添加目录时跨所有空间查重，把原本互不相干的配置耦合起来，换来的只是一条提醒。

代价要认清：同一批视频会在两个空间各有一份记录，收藏互不相通。用户可能期望的是「两个空间共享这批视频」，得到的是「两份」。这个困惑是这条决策的已知代价，先不做处理，等它真的出现——到时的解法也更清楚，比如在添加重复目录时补一条短提示，而不是现在猜。

## 缩略图不会互相覆盖，但要接受重复生成与孤儿文件

缩略图缓存文件名是 `{video_id}-{modified_at}-{纳秒}.jpg`，不含路径，而 `video_id` 是主键自增，因此两个空间的同一条路径必然拿到两个不同的文件名，不会争同一个缓存文件。重复生成同一文件的缩略图是纯浪费，不是损坏。

既有的另一条行为同时被继承下来：缩略图缓存从不清理，记录被删或目录被移除都不会删掉对应文件。跨空间重复配置会让这类孤儿文件变多，但这不是本次引入的机制，本次也不顺手加清理——那要单独定「什么时候可以删」的判据。

## 术语表的连带改动

`空间`收窄了其余术语的作用域：扫描合集、过期视频记录、不可访问目录、增量扫描描述的都是当前空间内的情形。[CONTEXT.md](../../CONTEXT.md) 在术语表开头统一声明了这层默认作用域，不再逐条重述。`扫描合集`的定义同时从「当前保存的全部视频目录」改为「当前空间内保存的全部视频目录」，并补了一句目录可以同时存在于多个空间、各空间各自把计入自己的合集。
