# 视频卡片的悬停动效，与重新引入一个动画库

[ADR 0007](0007-抽屉滑动的位移来源与去掉-GSAP.md) 把抽屉的动画交回 daisyUI 自带的 CSS 过渡，移除了 `gsap` 与 `@gsap/react`，其中一节标题写的是「为什么不需要一个库」。本条在视频卡片上重新引入一个动画库（`motion`，13.4.0）。

抽屉的结论一条不动，本条不推翻 0007：面板仍由 daisyUI 的过渡滑动，`gsap` 不回来，抽屉的 `prefers-reduced-motion` 判断仍写在 `style.css` 里。被推翻的是把那一节标题读成通则的读法。**0007 的两条论据本身仍然成立，只是卡片去问同一个问题的答案是反的**：「供应商自带的过渡已经做了这件事」在抽屉上为真、在卡片上为假；「同一元素不能有两个位移来源」在卡片上不作禁令、改作约束。下文两节分别说明这两处为什么换了答案，再记录偏好判断落回 JS 的理由、按压的冒泡边界，以及一个已被实测推翻的兜底设想。

## 为何「供应商已经做了这件事」在卡片上不成立

0007 的依据是 vendor CSS 已经覆盖了抽屉的全部需要：`.drawer-side` 自带 `translate` 过渡、遮罩自带 `opacity` 与 `visibility` 过渡、关闭态的可交互性也由 `pointer-events: none; visibility: hidden` 自动管理。那条依据可核对，也对。

卡片没有对应的东西可指。daisyUI 5.7.32 的 `card.css` 里与 `.card` 悬停有关的全部声明只有这一条过渡：

```css
.card {
  border-radius: var(--radius-box);
  outline-offset: 2px;
  outline: 2px solid #0000;
  flex-direction: column;
  transition: outline .2s ease-in-out;
  display: flex;
  position: relative;
}
```

`transition` 的全部内容就是 `outline`。该文件里没有 `.card:hover` 选择器（出现 0 次），没有悬停位移、没有悬停阴影、没有变色；唯一与光标有关的一条是 `:has(>:is([type=checkbox],[type=radio]))` 条件下的 `cursor: pointer`，要求卡片里含受控控件，视频卡片不含。卡片这次要做的事——上浮、缩放、按按压下去——供应商一条都没有提供，因此 0007 那句「库是重复的一层」在这里没有对象。

## 为何仍然要一个库，而不是几条 Tailwind 工具类

候选有三条，都被否决。

**只用 CSS 工具类**（`hover:-translate-y-1`、`hover:scale-[1.02]`、`active:scale-[0.98]`、`hover:shadow-*`）——看起来最省，但有两处硬伤。其一，**按压边界表达不出来**：`:active` 沿祖先链上溯，按住卡片内的操作按钮时祖先卡片同样是 `:active`，整张卡跟着下陷，而这正是这次明确要求避免的。CSS 里没有「自身被按、但按的是内部按钮就不算」的写法；最接近的是 `:has(button:active)` 这类结构性补丁，它把「哪些后代算操作」编码进选择器，第一个不是 `<button>` 的可交互后代出现就失效。其二，**阴影的过渡会挤掉描边的过渡**：Tailwind 的 `transition-shadow` 写的是 `transition-property: box-shadow`，而该属性只能有一个值，它会整个覆盖 daisyUI 给 `.card` 的 `transition: outline .2s ease-in-out`，描边的出现与消退随之变成瞬时。当时把这条也算作否决理由，但手写一条同时含 `outline` 与 `box-shadow` 的 `transition` 后来还是发生了——阴影搬回 CSS 时正是这么写的（见「为何阴影最后搬回 CSS」一节），代价照旧是把供应商的声明抄成第二份。因此这一条如今不再是这条路的否决理由，它是那次搬家的已知代价；否决这条路的理由只剩其一。

**在 React 里自己维护按压状态**（指针事件翻一个布尔值，位移交给 CSS 过渡）——否决。要自己写指针捕获、`pointercancel`、指针移出元素边界，还要写「快速划过时从当前位置接管」的调度，也就是在应用层重新实现手势识别那一层。这与 0007 否决状态机、[ADR 0006](0006-抽屉开关动画与通用-Drawer.md) 否决 `setTimeout(300)` 是同一条理由的镜像。而且每次指针状态翻转都要过一次 React 渲染。

**`@keyframes`**（仓库已在通知倒计时细线上用过这一形态）——否决。它在快速划过一排卡片时每张都从关键帧起点重放，而 0007 已经记过：CSS 过渡被打断时会就地重定向，`@keyframes` 不会。

选定 `motion`。`whileHover` / `whileTap` 表达的是「目标状态」而不是「从 A 到 B 的关键帧」，`transform` 由它在自己的 rAF 里写成内联样式，不经过 React 的渲染循环，也不占用任何 CSS 属性——它解决的是上面那处硬伤：按压手势由库在元素上认领（见下文），位移因此只有一个写入方，且不动任何 CSS 属性。**它留在卡片上的理由只是 `transform`，不包括阴影**：阴影一度也交给它写，后来搬回了 CSS，理由见「为何阴影最后搬回 CSS」一节。接入形态是静态导入 `motion/react` 的 `motion`，不用 `LazyMotion` + `m` 那一层间接：仓库禁止动态导入，且这是 Tauri 桌面应用、资源从本地磁盘加载，包体积不是关键指标。依赖经镜像源安装，锁文件已提交。

## 为何「同一元素两个位移来源」这次是约束而不是禁令

0007 记录的是一个真实缺陷：daisyUI 用 `translate` **属性**、GSAP 用 `transform` 属性，两者在 CSS 里互相独立、位移量**相加**，于是面板滑过头再闪回。那条教训在卡片上仍然成立，只是这次有东西可以执行它——**同一个属性只允许一个写入方**：

```tsx
// The lift, the hover scale and the press scale are the only writers of
// `transform` here — no Tailwind `hover:translate-*`, which would add a
// second source for the same property and is the defect ADR 0007 records
// (two displacements summing, so the element overshoots and snaps back).
// The outline, the cursor and the shadow stay with CSS for the same
// reason: one writer per property.
className="card card-border bg-base-200 cursor-pointer video-card -outline-offset-2 hover:outline-base-content/30"
whileHover={hover}
whileTap={reduceMotion ? undefined : { scale: 0.98 }}
```

分工是：`transform`（悬停上浮 4 像素、放大到 1.02、按压缩到 0.98）只由动画库写；`outline`（悬停的 2 像素中性描边）、`cursor`（手型）与 `box-shadow`（悬停阴影）只由 CSS 写。卡片上不出现 `hover:translate-*` 一类的位移工具类，库也不写 `outline` 与 `box-shadow`——前者的原因见上节，后者见「为何阴影最后搬回 CSS」。卡片的描边画在自身边缘而非外侧（`-outline-offset-2`），因为虚拟网格的滚动容器按内边距盒裁剪，画在外侧的描边会在首列与首行被整条裁掉。

时长取 0.2 秒，与 daisyUI 给 `.card` 的 `transition: outline .2s ease-in-out` 对齐，使描边与位移共用一个时钟而不是各跑各的。这也正是 `style.css` 给 `.video-card` 的那条 `transition` 里 `box-shadow` 取 `0.2s` 的原因：三个属性同一个时钟。这与 0007 否决 `setTimeout(300)` 是同一条理由：把时长抄成第二份真值，改一处忘一处就会错开。

## 为何阴影最后搬回 CSS

阴影起初由动画库写（内联样式），它从 `HOVER_SHADOW` 这个写死的值来：`0 8px 16px -4px rgb(0 0 0 / 0.18)`。暗色主题下这层黑阴影落在近黑背景上几乎看不出加深（issue #37 实测亮暗之比约 0.10），而需要的是**随主题翻转的阴影色**——亮色主题用深色阴影、暗色主题用浅色光晕（`base-content` 正是这样一个随主题翻转的令牌）。

**库够不到这个颜色。** 动画库插值的是字面量：它能接受 `rgb(0 0 0 / 0.18)` 这样的常量，但接受不了 `var(--color-base-content)` 或任何语义色令牌——它要在自己的 rAF 里算出中间帧，就得先有一个数值。这不是配置问题，是那一层的输入类型问题。因此阴影必须交给能读 `var()` 的那一层，也就是 CSS：`style.css` 里 `.video-card:hover` 的 `box-shadow` 用 `color-mix(in oklab, var(--color-base-content) 18%, transparent)`，卡片上挂 `video-card` 类作为挂点。

**代价是重述供应商的 transition 声明，用户已认可。** `.card` 的 `transition` 在 daisyUI 的层里，`style.css` 里未分层的规则会赢；但 `transition-property` 只能有一个值，所以 `.video-card` 必须把 `outline` 与 `box-shadow` 写进同一条 `transition`，等于把供应商那份声明抄成第二份——供应商升级不会带着它一起改。这正是上文「只用 CSS 工具类」那条候选记过的代价，那次用它否决了整条路，这次只为阴影一项接受它。Tailwind 的 `transition-shadow` 仍然更糟：它会整个替换掉该属性，把描边变成瞬变。

**代价之外还有一条：`color-mix` 的降级要自己主管。** 构建管线会为 `color-mix` 自动加一条降级，而那条降级丢掉混合的 alpha——它把 `var(--color-base-content)` 按全强度画出来，是一条实心色带而不是阴影。因此 `style.css` 里另写了一条 `@supports not (color: color-mix(in lab, red, red))`，照仓库既有的 `@supports not (scrollbar-gutter: stable)` 那个写法，值取搬家前那个写死的黑（亮色主题下本来就该是它）。**为什么不能忽略**：WKWebView 从 Safari 16.2 才支持 `color-mix`，而 macOS 12 搭载的是 15.4——那里的用户会看到一条实心色带，这不是不可达的边角。两条 `@supports` 条件互斥，书写顺序不影响结果。

**减动效不受影响，因为挡的是位移而不是颜色。** 阴影来自 CSS 的 `:hover` 规则，与 `prefers-reduced-motion` 无关，所以在偏好为真时它照常淡入——`reducedMotion="user"` 关掉的是位移与缩放，那条划分本来就说「只关位移、保留颜色与透明度」（见上文减动效一节）。反过来说，阴影留在 CSS 也是这条划分能在实现里成立的前提：若阴影仍由库写，撤掉悬停目标就会连阴影一起撤掉。

**这一条已实测，不再是构造上的推论。** 用 `--force-prefers-reduced-motion` 让浏览器从一开始就报该偏好为真——比加载之后再用 `Emulation.setEmulatedMedia` 改更可靠：库在模块初始化时就把偏好读进一个模块级变量，之后再改媒体设置它不重读，用重载去补又会让这条测量挂在一次额外导航上。在真实网格里用真实鼠标悬停同一张卡片，亮暗两种主题下都是 `transform: none`（位移整个不发生），而 `box-shadow` 仍是 `… 0px 8px 16px -4px`、描边 alpha 仍是 0.3、光标仍是手型；同一份采样里 `matchMedia('(prefers-reduced-motion: reduce)').matches` 为 `true`，因此测到的不是一次没生效的模拟。

**为什么它是一条 `style.css` 规则，而不是组件上的一条 Tailwind 工具类。** 仓库里其余的阴影都是组件上的工具类（`shadow-xl`、`shadow-lg`、`Drawer` 那条 `shadow-[inset_…]`），这一条是例外，理由不在偏好而在那条降级：任意值工具类写得下这套阴影本身（`hover:shadow-[0_8px_16px_-4px_color-mix(in_oklab,var(--color-base-content)_18%,transparent)]`），但**写不出一条 `@supports not`**——条件声明在工具类里没有形态，而降级在这里不是可选项（见下段）。既然必有一块只能待在样式表里，把阴影的其余部分也留在同一处，胜过一半在组件类名里、一半在样式表里。代价是「阴影都写在组件上」这条惯例有了一个需要解释的例外，例外本身记在这里。

**为什么这条 `transition` 不是「第二个来源」纪律的破口，而是它的例外。** 上文「同一属性单一来源」定的是一条禁令，而这里 `transition` 确实被写了两处：daisyUI 的 `.card` 与 `style.css` 的 `.video-card`。判别依据是**这处重复能不能被消掉**：位移那条禁令防的是两份真值各自演化（0007 记的相加与回弹）；`transition-property` 只有一个值，要在描边与阴影之间共用一个时钟，重述就是唯一的写法，没有能同时满足「保住描边过渡」与「不重述」的第三条路（`transition-shadow` 已在上文排除）。因此这一处是**受限的例外**：只许出现在 `transition` 这一个属性上、只许为了与供应商的描边时长对齐而存在，且代价（供应商升级不同步）已知且记在此处；`transform`、`outline`、`cursor`、`box-shadow` 上的单一来源纪律一条不减。

**被否决的另一条路是在组件里读解析后的主题值**（把当前主题的 `base-content` 解析成具体颜色，再作为字面量交给库）。否决的理由是仓库当下没有可供组件消费的解析后主题：主题是通过 `data-theme` 属性与 CSS 令牌表达的，组件层拿不到「当前生效的那个颜色值」的响应式来源，要拿到就得自己读 `getComputedStyle`、订阅主题变化并把它接进 React 状态——为一项装饰新造一层基础设施，还得保证它与 CSS 的解析结果永远一致。相比之下，把阴影写在 CSS 里直接复用了主题机制本身，代价只有上面那一条。**这条路曾被选定过，复核后改选。** issue #37 在 06:51 有一条「选用路径二」，在把两条路的代价逐条列明之后于 08:31 改选路径一（把阴影交给 CSS），代码按路径一落地，以较晚那次为准；上面这段否决理由因此记的是复核时的结论，而不是说这条路从未被选中。

## 为何悬停余量只补在起始边，且要用负外边距抵消

上一节里「描边画在自身边缘」那句是同一处裁剪的另一个受害者，本节把那个裁剪说完整：**滚动视口的裁剪盒就是它的内边距盒**，而它的内边距从来是不对称的——末尾两边的余量早就有，起始两边一点没有。于是首行、首列的卡片正好把边缘压在裁剪边界上，悬停的上浮、缩放与阴影在那里被一起切平。

| 边 | 现有余量 | 来源 |
| --- | --- | --- |
| 上 | `0` | 没有 `padding-top` |
| 左 | `0` | 没有 `padding-left` |
| 右 | 20px | `padding-inline-end: max(0px, calc(20px - var(--native-scrollbar-width,0px)))` |
| 下 | 20px | 网格行的 `paddingBottom` |

本节引用的像素数值分两个来源。**「修复前 / 修复后」那张机制表转抄自 issue #38**（真实构建产物 + 真实指针事件），本次没有重做。**「10px 这一版」那两行是本次实测的**，不是由上一版外推：测量环境是最终构建产物在一个真实浏览器（headless Chrome）里渲染、Tauri 的 IPC 用桩喂数据，量的是 DOM 的 `getBoundingClientRect()` 与截图的像素值——它验证的是布局与绘制，不等于在桌面端窗口里走查。几何一律按**视口内容宽与列宽**记，不按窗口尺寸记：窗口尺寸不是这套几何的自变量，同一个窗口在不同根字号下列宽并不相同。

### 需要多少：两条闭式解

超出量只由两处几何决定。缩放 1.02 把每边放大 1%（放大的那 2% 分到每边），于是：

- **上侧超出** = `4px 上浮 + 1% × 卡高`
- **左侧超出** = `1% × 列宽 + 4px`（阴影 `0 8px 16px -4px` 在左右各 4px 的余晖）

末尾两侧的 20px 大于这两处需要的最坏值（7.79px），所以只有起始边要补。按列数逐档实测：

| 列数 | 列宽 | 卡高 | 上侧超出 | 左侧超出 + 阴影 |
| --- | --- | --- | --- | --- |
| 4 | 219.5 | 192.2 | 5.88 | 6.19 |
| 4 | 249.5 | 209.4 | 6.05 | 6.49 |
| 2 | 279.0 | ~220 | 6.22 | 6.79 |
| 2 | 289.0 | ~222 | 6.27 | 6.89 |
| 1 | 379.0 | 283.7 | 6.78 | **7.79** |

第一版的错在于只看了上表里 4 列那两档。**单列是可达布局**：`tauri.conf.json` 没有设 `minWidth`，窗口可以一直拉窄到内容宽小于 400。这一档由注入 `main{max-width:441px}` 量得——headless Chrome 把窗口下限卡在约 490px，进不了单列区间，但那条代码路径与真实窄窗口是同一条。单列的列宽上限是 399（再宽就落到 2 列），对应左侧超出 `1% × 399 + 4 = 7.99px`，也就是**理论上限本身已经逼近 8px**。

内部卡片不受影响：上下左右都有邻居的卡片，行距 19.68 像素、列距 20 像素，都大于阴影的延展，逐像素确认阴影正常绘制。首行首列修复前的绘制范围也有实测：4 列 249.5 那一档静止时首卡落在 `top 261.31 / left 101`，正是视口的裁剪边界；悬停后应画到 `top 255.26 / left 98.51`、阴影应画到约 `left 94`，而实测绘制竖直从 **261** 起、水平从 **101** 起——上边、左边连同左侧阴影被一起切平。

### 取多少：10px，且必须写成显式像素

取值 **10px**，对上表最坏值 7.79px 留 2.21px 余量。用显式像素而不是 rem 刻度（`pt-2` / `ps-2` 那种），是因为**要盖住的超出量由卡片尺寸（px）决定，与根字号无关**：用 rem 就等于让「需要多少」和「给了多少」分属两套单位，根字号一变，超出量不变而余量跟着变。

这不是假想的风险，第一版实现正是踩在这里。`style.css` 的 `html { font-size: 14px }` 让 `0.5rem` 在这个应用里是 **7px** 而不是 8px（`pt-2` = `calc(var(--spacing) * 2)`，`--spacing: 0.25rem`），构建产物上量到的 `padding-top` / `padding-left` 就是 7px——比单列需要的 7.79px 少 0.79px，那一档仍然被裁。这与 0007 记的「同一属性两个来源」是同一类错误，只是这次的第二个来源是根字号：卡片尺寸与根字号互不相干，把余量写在根字号的刻度上，两者就会脱钩。

上侧给 10px 也不会顶到上面那行文字：「共 N 个视频」的底边约在 y≈238，而视口盒子的顶边只会从 261.31 上移到 251.31。

### 为什么必须用负外边距抵消

单独加内边距会把整张网格向右向下推 10px，卡片与工具栏左边缘的对齐随之破掉——那是静止状态下就能看见的排版变动，而这次要修的只是悬停时的一处裁剪。等量负外边距让视口盒子在起始边上向外扩 10px，卡片位置因此逐像素不动；列数也不变，因为盒子在 `clientWidth` 上多出的 10px，正好等于它在 `paddingLeft` 上多出的 10px（同一笔账在竖直方向上是滚动高度与客户端高度同时 +10，可滚动区间不变）。滚动时内容仍在视口边界处正常被裁，不会漏出。

| | 视口盒子 | 首卡静止 | 首卡悬停绘制 | 次卡静止 |
| --- | --- | --- | --- | --- |
| 修复前 | 101..1179 / 261.31..752 | 261.31 / 101 | 从 261 / 101 起（被裁） | 370.5 / 261.31 |
| 修复后 | **93..1179 / 253.31..752** | **不变** | 从 **255 / 93** 起（完整） | **不变** |

上面这张表转抄自 issue #38，量的是**用注入的字面 8px** 时的「负外边距抵消」这条机制本身——静止位置逐像素不变、盒子在起始边外扩、悬停绘制完整。取值改成 10px 后按同一算式盒子变成 `91..1179 / 251.31..752`，**下面这两行是在最终构建产物上实测的（真实浏览器里渲染、Tauri 的 IPC 用桩，量 `getBoundingClientRect()` 与截图像素），不是由上一版外推，也不是桌面端走查**：

| 10px 这一版 | 视口盒子 | 首卡静止 | 首卡悬停绘制 | 次卡静止 | 列数 × 列宽 |
| --- | --- | --- | --- | --- | --- |
| 四列（视口内容宽 1058） | **91..1179 / 251.31..752** | **101 / 261.31** | 上边缘画在 **255**、左侧连阴影自 **93** 起 | **370.5 / 261.31** | 4 × 249.5 |
| 单列（列宽 379、卡高 283.72） | — | — | 上边缘画在 **345**（悬停上边 345.53）、左侧连阴影自 **432** 起（卡片左边 436.71） | — | 1 × 379 |

单列那一档需要 7.79px 的左侧余量与 6.78px 的上侧余量，10px 分别留出 2.21px 与 3.22px。滚动位置也复量过：内容仍在视口盒子的上边界处被裁（盒子之上的 `y=249..250` 是纯白）。两个尺寸档的静止位置、列数、列宽都与修复前逐位相同。

把取值从上一版抬到 10px，依据是「按最容易出事的布局定值」这一条，而不是按最常出现的布局。**上一版写的是 `pt-2 ps-2`，不是 8px**：这个应用里 `0.5rem` 只有 7px（`html { font-size: 14px }`，推导见上），而单列时左侧需要的余量是 7.79px，7px 不够；四列那一档虽然 7px 够用，但它恰好是最常出现的那一档。issue #38 修复前量到的绘制——四列时悬停的卡片从 `261 / 101` 起画，上边被裁 5.74px、左边被裁 2.5px——量的是「起始边一点余量都没有」时的缺口大小。**这与上面那张机制表里的 `255 / 93` 不是一回事**：那张表量的是注入字面 8px 时「负外边距抵消」这条机制本身，与这里说的是两件事。**需要量随卡片尺寸增长（每边 1%），所以取值必须按最容易出事的那个布局来定。**

**为什么余量加在这一个视口上，而不是共享的 `.scroll-viewport`。** 那个类是三个页面共用的，改它会把余量一并加给空列表状态那个滚动区域——那里没有卡片、没有悬停，多出的 10px 只是凭空的位移。余量属于「渲染卡片的那个视口」，所以写在使用它的那处：`VirtualVideos` 交给 `ScrollViewport` 的内联样式（`ScrollViewport` 的 props 是 `ComponentPropsWithoutRef<'div'>`，`style` 原样透传），内边距与负外边距由 `virtualGridLayout.hoverRoom` 同一个值推出——「负外边距必须与同轴内边距逐位相等」这条不变量因此由构造保证，不会出现只改了一边、整张网格横移而无人报警的情况。数值本身集中放在 `virtualGridLayout` 里，与列数断点和 20px 间距同一处。

**这条改动测试覆盖不到，依据是真实浏览器里的像素测量。** jsdom 不做布局、也不计算盒模型，裁剪与悬停绘制在测试里没有可断言的落点——能断言的只有 DOM 结构与类名，而这里要验的是像素。因此没有为它新增测试钩子、探针或专为测试存在的类，也不声称已被测试覆盖。判定用的测法与数值就是本节各表：在构建产物上量静止与悬停两种状态下卡片的实际绘制范围（以及视口自己的 `padding-top` / `padding-left`），与视口的裁剪边界逐像素比对。这与上文的暗色阴影、减动效分支同一分工——真机视觉走查仍未进行。

## 为何行高估算必须等于实测，以及那两个常量从哪来

虚拟网格第一屏是按**估算**行高排的，随后 `measureElement` 读数回填（`useVirtualCollection`）。估算偏大时，回填那一刻第一排以下的每一行都上移一个差值——第一排起点是 0，动的只有它下面那些行，看上去就是「列表刚显示出来就往上跳一下」。修前实测（1280px 视口、4 列）：首帧各行落在 `0 / 240.34 / 480.69 / 721.03 …`，一个采样之后变成 `0 / 226 / 452 / 678 / 904 …`，每行上移 14.34 × 行号。

两个新常量因此与 `hoverRoom` 是同一类东西：都写在 `virtualGridLayout` 里、都是显式像素、都要按列数档位量出来。方向相反——上一节的量由**卡片尺寸**决定，写 rem 会与根字号脱钩；这里的量由**文字排布**决定（正文字号、内边距、行盒），本就随根字号走。这次仍写 px，因为根字号在本仓库是 `style.css` 里写死的 `14px`，不是运行时会变的自变量；真要动它，这两个值与 `hoverRoom` 一样要重量。

| | 值 |
| --- | --- |
| 原估算：`249.5 × 9/16 + 100` | 240.34 |
| 实际行高（`getBoundingClientRect`） | 225.75 |
| 回填实际用的值（`offsetHeight`，整数） | **226** |

拆开实际行高：卡片 205.75 = 边框 1 + 图片 139.22 + 正文 64.53 + 边框 1，再加行尾间距 20。旧估算有两处偏差，加起来正好是量到的 14.6：常数 `100` 要盖的其实是 **86.53**（正文 + 两边框 + 行尾间距），多算 13.47；图片按**整列宽**算 16:9（140.34）而不是扣掉两边框后的 247.5（139.22），多 1.13。

估算因此改为按同一套几何拼出再取整：`Math.round((列宽 − 2 × cardBorder) × 9/16 + rowFooter)`，其中 `cardBorder = 1`、`rowFooter = 86.53`。**取整不是装饰**：回填读的是 `offsetHeight`，那是个整数，估算留小数就是每行留不到一个像素的差，顺着列表一直累加下去。

| 视口 | 列数 | 步长 | 实测行高 |
| --- | --- | --- | --- |
| 1280 | 4 | 226 | 225.75 |
| 1100 | 4 | 223 | 222.94 |
| 750 | 3 | 207 | 206.91 |
| 450 | 2 | 304 | 303.66 |
| 340 | 1 | 242 | 241.78 |

五个档位各量一次，修好之后**首帧位置即最终位置**，全程只采到一个样本——估算与实测相等时不会有第二次布局。

**这条测试覆盖不到，只能靠量。** jsdom 没有排版引擎，估算偏了不会让任何断言失败，只会表现成行在跳；能断言的只有 DOM 结构。因此「卡片盒子一变就要重新量」写在三处：`virtualGridLayout` 的常量旁、`VirtualVideos` 的估算处，以及开发指南那条虚拟渲染规则里（连同「估算必须等于实测、实测是整数所以估算也要取整」）。测量环境与本节其它数值相同——**最终构建产物在 headless Chrome 里渲染、Tauri 的 IPC 用桩**——验的是布局，不是桌面端观感走查。

**顺带更正一处：验收入口现在会加载视频列表。** 本次测量就是在这个入口上做的，夹具那 36 条视频进了真实网格（1280×800 的窗口里量得 20 张卡片、5 行，其余在滚动窗口外——网格是虚拟化的，挂载数不等于总数），它因此不再只是「框架与文案走查」的入口，**能承载依赖真实数据的界面验收**。`## 实施状态` 里 #37 第一遍那段据此改写，它引用的 `docs/逐项完成审查.md` 与 `docs/开发指南.md` 里同一条也一并改过。#23 记的「库查询一直停在 pending」当前不再出现，**恢复的原因没有追溯**，因此这个入口要当作会坏的东西用：打开后列表若是空的、停在「正在读取视频库…」，那就是老毛病回来了，此时它又不能作为验证手段。

## 为何 `prefers-reduced-motion` 的判断回到 JS

0007 记录过「把该偏好从 JS 移进 CSS」。本条把它挪回 JS，理由不是「偏好天然属于 JS」，而是把那条决策的依据说完整：**判断住在动画所在的那一层**。

- **抽屉**：动画全在 daisyUI 的 CSS 过渡里（`translate`、`opacity`、`visibility`），媒体查询里的 `transition: none` 直接命中被过渡的那个属性，所以判断写在 CSS。
- **卡片**：位移与缩放是动画库写的**内联样式**。内联样式在层叠里高于一切非 `!important` 的作者规则，媒体查询拦不住它。判断只能写在 JS，写在能决定「要不要给出这个目标值」的地方。

所以这不是「偏好属于谁」的立场变化，而是「谁的规则够得着那个属性」这条判据的两次应用。0007 给抽屉下的那个判断仍然有效，`style.css` 里那条媒体查询不动，本节也不是对它的反转——它是把 0007「无障碍上的取舍」里 `prefers-reduced-motion` 那一条说完整。

应用级的偏好配置先按其归属放在 `App`（开发指南规定 `App` 负责应用级提供者），一份提供者覆盖全部三个渲染卡片的页面：

```tsx
<MotionConfig reducedMotion="user">
```

这个配置不改变仓库对通知倒计时细线的立场：那条线不降级，因为它表示剩余时间而不是入场装饰。

**但只配这一层不够，这是实测结论。** 在真实浏览器里开启「减少动态效果」后悬停卡片，元素上仍然出现 `matrix(1.02,0,0,1.02,0,-4)`：库把这个配置读成「不要动画」，于是把 `transform` 目标**瞬时应用**，而不是不应用。位移照样发生，只是没有过渡，偏差在观感上更糟（4 像素与 2% 是硬跳上去的）。因此卡片自己再用 `useReducedMotion()` 读一次偏好，把位移与缩放的目标整个撤掉：

```tsx
const reduceMotion = useReducedMotion();
const hover = reduceMotion ? undefined : { y: -4, scale: 1.02 };
```

`undefined` 就是「这一项没有目标值」，位移与缩放因此整个不发生。阴影保留是刻意的，但它的保留方式变了：它现在来自 `style.css` 给 `.video-card` 的 `:hover` 规则，而不是库的悬停目标，所以撤掉目标不会连它一起撤掉——可点性提示仍在（描边、阴影、手型光标都还在），只是不再移动，`reducedMotion="user"` 只关位移、保留颜色与透明度这条划分，恰好就是「挡的是位移，不是颜色」这句要求的表达。

## 为何按压的冒泡边界不能用 `stopPropagation`

按卡片内的操作按钮（播放、收藏、打开目录、移除）时整张卡片不应跟着下陷。`VideoActions` 的容器早已用 `stopPropagation` 拦住单击与双击，让按按钮不打开详情抽屉，按同样的纪律补一个 `pointerdown` 却不生效——实测按住操作按钮时卡片照样下陷。

原因是 React 17 起把合成事件挂在**根容器**上，而不是文档里的每个元素。`pointerdown` 在按钮上冒泡时，先到达动画库绑在卡片元素上的**原生**监听，卡片的手势在那时就认领了这次按压；等事件继续冒泡到根容器、React 的处理器跑到时，已经晚了。

捕获阶段的版本实测**有效**——根容器上的捕获监听先于目标元素上的冒泡监听——但它会把事件整个截断在卡片这一层，而 `VideoMenu` 正是靠 `window` 上的 `pointerdown` 做「点外部关闭」：

```tsx
window.addEventListener('pointerdown', outside);
```

被截断之后，在卡片上按下不会关闭已打开的右键菜单。两条路都不可取：冒泡太晚，捕获太狠。

最终用的是动画库自己的手势边界：让动作容器自己声明一次按压手势，并关掉 `propagate.tap`，库据此把这次 `pointerdown` 标记为已被认领，卡片跳过已被认领的事件：

```tsx
// Motion only creates the press gesture that can claim the pointer press for an
// element that declares one, so this object stays empty on purpose: being truthy
// is the whole of its job, and the container itself does not move.
const CLAIM_TAP = {};

// …
<motion.div whileTap={CLAIM_TAP} propagate={{ tap: false }} tabIndex={-1}>
```

`CLAIM_TAP` 是空对象，它唯一的作用就是「真值」，所以刻意起了名字而不是内联，免得被当成可以删掉的残留。

`tabIndex={-1}` 是因为库会给携带手势的元素补一个 `tabindex="0"`。这条可核对：按压手势在元素没有 `tabindex` 属性时补 `target.tabIndex = 0`（`node_modules/motion-dom/dist/es/gestures/press/index.mjs:87-89`），React 侧的 `useHTMLProps` 在 `props.tabIndex === undefined` 且有 `whileTap` 时补 `htmlProps.tabIndex = 0`（`node_modules/framer-motion/dist/es/render/html/use-props.mjs:48-50`）。显式给出 `-1` 两条都不会触发，卡片内部因此不多出 Tab 停靠点，Tab 键会跳过动作容器。

这么做有副作用，规格与测试都没有覆盖：`tabIndex={-1}` 挡的只是 Tab 顺序，元素本身仍可被鼠标与脚本聚焦——点中动作容器自身的空白处，焦点就会落在它上面。而卡片的 `onKeyDown` 只对 `event.target.closest('button')` 提前返回，这个容器是 `div` 不是 `<button>`，于是焦点停在它上面时按 Enter 或 Space 会冒泡到卡片的处理器并打开详情。这与「按按钮不打开详情」的初衷相左，记在此处待验证与定夺，本次不改。

这条边界不是「多写一个 prop」，而是把冒泡纪律从「谁处理完谁喊停」改成「谁打算用这次按压就认领它」：认领是可叠加的，截断不是。

## 为何这次不必做 0006 那样的许可证盘点

0006 专门记录过 GSAP 走的不是 OSI 认可的开源许可（Webflow 收购后对所有用途免费，但许可是 GreenSock 自己的 "No Charge"，与仓库的 MIT 不同），因而构成一条需要盘点的负担。

`motion` 13.4.0 是 MIT，与仓库自身的 `LICENSE`（MIT，Copyright (c) 2026 ChaoqiYin）同类，不产生 0006 那种待盘点的项，也不需要 `docs/FFmpeg-LGPL下载-资料核对.md` 那样单列的核对材料。这与 0007 里「GSAP 的许可证负担一并消失」是同一件事的两面：那次是移除，这次是新增，两次都不留下需要单独记账的许可。

## 取舍与影响

- **暗色主题下阴影几乎不可见（issue #37）：已解决，阴影搬回 CSS。** 测法是：指针停在卡片上，取卡片下缘正下方 1..18 像素的亮度极值，与同页远处背景比较；暗色主题下阴影比背景亮，偏差是**正向**的，所以取极值而不是最小值。旧值——阴影由库写成内联的 `rgb(0 0 0 / 0.18)`——亮色 30、暗色 3，比值约 0.10，近黑背景上的黑阴影无处可暗；现值——`style.css` 里 `.video-card:hover` 的 `color-mix(in oklab, var(--color-base-content) 18%, transparent)`——亮色 28、暗色 24，比值约 0.86。18% 这个比例是 15/18/20/22% 四档扫出来的（量法同上：同一构建产物、真实鼠标，每档只改混合比重建一次）：

| 混合比 | 亮色 | 暗色 | 暗/亮 |
| --- | --- | --- | --- |
| 15% | 23 | 21 | 0.91 |
| **18%** | **28** | **24** | **0.86** |
| 20% | 31 | 28 | 0.90 |
| 22% | 34 | 31 | 0.91 |
| 旧值（固定黑，alpha 18%） | 30 | 3 | 0.10 |

选 18% 有两条依据：20% 起亮色已经重于原来的 30（踩了「亮色主题下的观感不得比现在更重」这条验收），15% 又把亮色降到 23、离旧值比 18% 更远；而 18% 恰好等于原来写死的 alpha，于是变化只剩颜色本身。**余量要一并说清楚：亮色下 28 与旧值 30 只差 2/255，那条验收是压线通过的，20% 就会翻过去**——这既是选 18% 的依据，也是这个取值最脆的地方，将来若要再调混合比，先看这一行。

取极值的窗口本身也复量过：取卡片下缘正下方 1..18、1..19、1..20 三档，读数逐档相同（亮 28、暗 +24），因此与 issue 记的「约 1–19 像素」相差的那一个像素不改变结论。issue 那句「绝对值随采样距离漂移」说的是这个量对窗口并非不敏感，只是在这三档之内不漂；本 ADR 只保留比值，正是为了不必依赖某一档窗口。机制、代价与被否决的替代见「为何阴影最后搬回 CSS」一节。原先把「改为由 CSS 承载阴影」记成不成立，那针对的是**两种机制写同一个黑色值**；搬回 CSS 之所以有效，是因为顺带换掉了颜色来源，而不只是换了个写入方。
- **`useReducedMotion()` 只在挂载时读一次。** 运行中切换系统偏好不会即时生效，这是库的行为而不是本仓库的选择。要即时生效需要自己订阅 `matchMedia` 的 `change` 事件，本次不做。
- **jsdom 不绘制动画，也不计算样式。** 测试能验证的只有它留下的 DOM 与类名——卡片仍渲染为 `article`、按压手势没有多出 `tabindex="0"`、手型光标类在卡片与文件名按钮上——看不到上浮、缩放、阴影与描边。真实观感仍须在桌面端人工确认，与通知倒计时细线、抽屉滑动同一分工。
- **卡片行为测试没有补 `matchMedia` stub，这是实测后的结论，不是遗漏。** 预期是：库读偏好靠 `matchMedia`，而 jsdom 不实现它，引入动画组件后该测试会立刻以 `matchMedia is not a function` 失败。先跑了测试，它没有崩溃，因此决定不加。原因有两条：库在 `window.matchMedia` 缺失时有守卫（`prefers-reduced-motion` 的初始化写在 `if (window.matchMedia)` 里，缺失时直接把偏好置为假），且不提供 `MotionConfig` 时库的默认配置是 `reducedMotion: "never"`，动画那一侧根本不查这个 API。`frontend/src/app/interface.test.tsx` 里至今没有 `matchMedia`；`frontend/src/app/routes.test.tsx:28` 那段 stub 属于那处用例自身——它会走到设置页，而设置页的主题解析读 `matchMedia('(prefers-color-scheme: dark)')`——与动画库无关，不是这里可以照抄的先例。
- **即使补上 stub 也覆盖不到减动效分支，这才是更要紧的理由。** stub 惯常写成 `matches: false`，那只让偏好为假，与不 stub 的结果一样；要覆盖减动效分支得让它为 `true`，而 jsdom 不派发真实指针事件、也不绘制动画，卡片的「取消位移、保留阴影」根本没有可断言的落点。**这条分支后来是在真实浏览器里实测的**（见「为何阴影最后搬回 CSS」末段）：减动效下位移整个不发生，阴影与描边照常。unit stub 仍然补不上它，而真实浏览器里的测量不是桌面端窗口走查。
- **依赖多了一项。** 新增 `motion` 13.4.0；接入形态（静态导入而非 `LazyMotion` + `m`，因而不多一层间接）见上文「为何仍然要一个库，而不是几条 Tailwind 工具类」一节。
- **动画库与应用级偏好配置分处两地。** `MotionConfig` 是应用级提供者，放 `App`；卡片自己的偏好降级放卡片，因为只有它知道哪些目标值该被撤掉。两者都读同一个偏好，但职责不同：一个负责按偏好改变动画的播放方式，一个负责决定要不要给出这次位移。
- **同一属性单一来源这条纪律现在写进了开发基线。** 它是这次唯一需要后来者遵守的约束：卡片上出现 `hover:translate-*` 或让库去写 `outline`，都会重新引入 0007 记录的那类缺陷。

## 实施状态

代码与测试已落地：`VideoCard` 的悬停与按压目标、`VideoActions` 的手势边界与 `CLAIM_TAP`、`App` 的 `MotionConfig`、卡片行为测试里的新增断言都已写入（`matchMedia` 的 stub 经实测判定不需要，见上节）。`npm test` 为 **70 passed / 5 failed**，失败 5 项均为本次改动之前既有（4 项在 `frontend/src/i18n/`、1 项在 `VideoDetails.test.tsx`），由 issue #25 跟踪，与卡片无关。`npm run check` 通过。

**本次修复（issue #38）落在滚动视口起始边的悬停余量上。** 取值 10px，集中写在 `virtualGridLayout.hoverRoom`，由 `VirtualVideos` 以内联样式给出同轴内边距，并以同一个值取负作为外边距抵消。最终构建产物上的复核数值（测量环境见本节末段）：视口盒子 `91..1179 / 251.31..752`，首卡静止 `101 / 261.31`、次卡静止 `370.5 / 261.31`，四列 `4 × 249.5`，悬停绘制上边缘 `255`、左侧连阴影自 `93` 起；单列那一档上边缘 `345`、左侧连阴影自 `432` 起。静止位置、列数与列宽都与修复前逐位相同。**这条修复验的是布局与绘制，不等于桌面端观感走查**——起始边余量在真实窗口里够不够、首行首列悬停时看起来是否完整，仍未被验证，与下段同一口径。

**本次修复（issue #37）把悬停阴影从动画库搬到了 CSS。** `VideoCard` 不再有 `HOVER_SHADOW`，悬停目标里也没有 `boxShadow`——减动效时整个目标撤掉，写成 `reduceMotion ? undefined : { y: -4, scale: 1.02 }`——卡片挂 `video-card` 类作为挂点；`style.css` 的 `.video-card` 给出 `outline` 与 `box-shadow` 共用一个 0.2s 时钟的 `transition`，阴影几何（`0 8px 16px -4px`）提为同一元素上的 `--video-card-shadow`，降级块因此只重述它要替换的那个颜色、不重述几何——构建产物里四处 `box-shadow` 声明的几何同源。把几何提出来之后重出了两张截图，与提取之前**逐字节相同**（md5 一致），因此这次提取没有改动渲染。`.video-card:hover` 用 `color-mix(in oklab, var(--color-base-content) 18%, transparent)` 画阴影。复核值（测量环境见本节末段）：阴影在亮色主题下解析为 `oklab(0.21 … / 0.18)`、暗色主题下解析为 `oklab(0.978 … / 0.18)`，确实随主题翻转；悬停时 `outline-color` 的 alpha 在 0.2s 内从 0 逐帧升到 0.30（10ms 0.004、94ms 0.15、176ms 0.296、末态 0.30），`box-shadow` 同期从 `0 0 0 0` 升到 `0 8px 16px -4px`，即那条重述供应商声明的 `transition` 没有把描边过渡破坏掉。减动效分支也在同一环境下量过：`--force-prefers-reduced-motion` 下 `transform` 为 `none`，阴影与 0.3 的描边照旧画出来（亮暗两主题各一次）。两张截图（浏览器渲染构建产物所得，**不是桌面端窗口截图**，理由与下段同一口径）：[悬停阴影亮色主题](../验收截图/悬停阴影亮色主题.png)、[悬停阴影暗色主题](../验收截图/悬停阴影暗色主题.png)。

**真机视觉验收尚未进行。** 上浮、缩放、按压下陷、快速划过一排卡片时的接管、点击操作按钮时卡片不下陷，以及暗色主题下的阴影观感，都还没有在桌面端走查过（开发指南要求界面变更附截图；本次的两张截图是浏览器渲染构建产物所得，不是桌面端窗口截图，见上段）。在真实浏览器里量过的具体值有六处，都不是对观感的走查：只配 `MotionConfig`、卡片还没补自己的偏好判断时，减动效下位移仍被瞬时应用 `matrix(1.02,0,0,1.02,0,-4)`（补上之后同一条件下是 `transform: none`，阴影与描边仍在，两种主题都量过）、「取舍与影响」第一条里那份亮度对比与四档扫档（亮色 30 / 暗色 3 → 28 / 24）、上文「为何悬停余量只补在起始边」一节里的全部几何数值、本次 #37 的过渡时间序列与两个主题下阴影的解析颜色，以及上文「为何行高估算必须等于实测」一节里五个档位上的实测行高与首帧步长。

那几处的测量环境要说清楚：**最终构建产物在一个真实浏览器（headless Chrome）里渲染，Tauri 的 IPC 用桩喂数据**，量的是 DOM 的 `getBoundingClientRect()` 与截图的像素值。它验证的是布局与绘制——那正是这条改动要管的东西——但它不等于在桌面端窗口里走查：原生标题栏、真实滚动条、HiDPI 缩放、指针与动画帧的实际观感都不在其中。#35 中「暗色主题下的阴影观感已在桌面端确认」与「按下卡片内的操作按钮时整张卡片不下陷」两条验收因此记为未达成并留证——后者在 jsdom 里根本测不到，库的手势依赖真实的指针事件与动画帧。本 ADR 记录的是设计结论与单元测试覆盖的行为，不代表已在真实界面走查过；真机视觉验收同样尚未进行。

#37 那一组（过渡时间序列与两个主题下的阴影颜色）的环境换过一次，两遍都要说清楚。**第一遍**做在构建产物的样式表上：那一遍问的是层叠与 `transition` 的最终取值，这些与卡片挂在哪个容器里无关，所以没有走真实网格——它把 `frontend/dist` 里那份 CSS 挂进一个页面，页面里是一个带 `VideoCard` 同一份类名（`card card-border bg-base-200 cursor-pointer video-card -outline-offset-2 hover:outline-base-content/30`）的卡片元素，用真实指针悬停，读 `getComputedStyle` 并逐帧采样。它判定的是层叠（未分层的 `.video-card` 是否赢过 daisyUI 层里的 `.card`）、`transition-property` 的最终取值，以及描边颜色与阴影的逐帧推进。**原先这里给的理由是「验收入口只渲染页面框架、不加载视频列表，所以只能另搭一个页面」，那个说法已更正**——该入口现在会加载夹具里的 36 条视频，理由改为上面这条与容器无关的判据，见「为何行高估算必须等于实测」一节末段。

**第二遍取代了第一遍，本 ADR 与两张截图引用的都是第二遍。** 办法是把 Tauri 的 IPC 用桩喂上 40 条视频，在**真实网格**里取 `article.card` 的第一张卡片，用**真实鼠标**触发 `:hover`（合成 PointerEvent 能触发动画库的手势，但触发不了 CSS 的 `:hover`，而阴影正是 `:hover` 给的；第一遍的桩探针还会在约 200ms 时自己把悬停态点上，得到的是已经悬停的卡片而不是静止态——第二遍因此关掉了探针），并且在悬停之前先确认卡片处于静止态（`transform: none`、`box-shadow: none`、`outline` 全透明）再逐帧采样。两遍的结论一致：层叠结果、`transition-property` 的最终取值、以及描边 alpha 与阴影共用 0.2s 这个时钟。这一遍验的仍是布局与绘制，不是界面走查。
