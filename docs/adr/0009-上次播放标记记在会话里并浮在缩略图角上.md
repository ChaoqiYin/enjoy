# 「上次播放」标记记在会话里，浮在缩略图角上

播放由系统默认播放器承接，应用看不见播放中与播放完（开发基线第 11 节），能标记的只有「上一次发起的打开是哪一个」。这一条补的是那个标记：以哪种口径判定「上一次」、长成什么样、画在哪一层。三条候选路都被否决过，下文各记一次。

## 为何记在会话里，而不是取播放历史里最新的那条

数据侧本来就有 `last_played_at`（`record_play` 在打开请求提交成功后写入），全局取最大值就是一个天然的「上一次播放」。那条路不用新增任何状态，重启后也还在，与「最近播放」页的排序同源。

否决它的理由是**口径不同**：索引里那份历史是跨次运行的记录，用于「最近播放」页；而这枚标记回答的是「我刚才播的是哪个」。取历史最大值意味着三个月前播过的视频在每次启动时都被标上，用户没有做过任何动作，标记却已经在说「上次播放」。两条口径各自成立，不必合并。

选定会话状态：应用级 `useLibrary` 持有一个 `lastPlayedId`，点播放且打开请求成功后写入，应用退出即清空。代价明确接受——重启后标记消失，而那次播放仍在「最近播放」页里。

写入的时机是 `await` 之后而不是点击当下。打开失败不增加次数、不记时间（开发基线第 11 节），标记跟同一条规则走：失败的打开只产生一条错误通知，卡片保持原样。

## 为何是浮在缩略图角上的独立元素

否决过三条，都落在同一处：**卡片高度**。虚拟网格按估算的行高分配位置再实测回填（`useVirtualCollection`），ADR 0008 那套悬停几何也挂在卡片尺寸上——多出一行就会让这些数值一起漂。

- **改卡片描边**：悬停的中性描边与键盘聚焦的描边已经占了 `outline`，再加一个写入方就是 ADR 0007 记录的缺陷。
- **改卡片底色**：卡片底色是悬停阴影所在的那层表面，叠色之后阴影与底色的关系要重新量；而且一块被染色的卡片读起来像「选中」，而它不是选中。
- **加进正文的信息行**：窄卡片那一行本来就会换行，多一枚标签可能把它挤成两行，卡片高度随之变化。
- **选定**：一个绝对定位的元素浮在缩略图左上角，脱离文档流。

脱离文档流这条是实测过的，不是推论：在这张卡上点播放之后，**同屏每一张卡片的盒、每一行的盒与滚动高度都逐位不变**。这条后来被证明只在 16:9 素材下成立，见下文「为何这枚标记必须排在卡片的最后」。标记落在距卡片盒 8 像素处，其中 1 像素是卡片自己的边框，其余 7 像素即 `top-2 start-2` 在 `html { font-size: 14px }` 下的取值；相对缩略图则是距其左上角 7 像素。悬停时卡片放大到 1.02，这一偏移随之变成 8.16 像素，标记跟着卡片一起动。

## 为何这枚标记必须排在卡片的最后（issue #46 更正）

上一节那句「同屏每一张卡片的盒、每一行的盒与滚动高度都逐位不变」是量出来的，数值也对，但**它只在 16:9 素材下成立**：当时的验收夹具是 1920×1080，两种高度在那批素材上恰好相等。库里只要有竖屏或 4:3 的视频，这枚标记就会改掉卡片的尺寸——而且不只是被播放的那一张。

**原因：角标占住了「第一个子元素」这个位置。** 初版把角标写在卡片开头，排在图片区之前。daisyUI 5.7.32 给 `.card figure:first-child` 两条声明：

```css
.card figure:first-child {
  border-start-start-radius: inherit; border-start-end-radius: inherit;
  border-end-end-radius: unset; border-end-start-radius: unset;
  overflow: hidden;
}
```

`:first-child` 只看 DOM 顺序，**绝对定位的子元素照样占位**——定位移动的是盒子，不是它的序号。角标一出现，图片区就不再匹配这条规则，代价有两项：

1. **裁剪没了。** `overflow: hidden` 一失效，图片区作为 flex item 的 `min-height: auto` 自动最小尺寸随之被释放（该属性的自动最小尺寸在 `overflow` 非 `visible` 时为零）。于是图片区多出第二个定高来源——缩略图自身的宽高比（ffmpeg 的 `scale=480:-2` 保留原始比例），而 `aspect-video` 只是它的首选值。
2. **圆角没了。** 那条 `border-*-radius: inherit` 一并失效，被播放的卡片缩略图变成直角。

图片区被撑高之后，grid 的 `align-items: stretch` 把**同一行另外三张卡一起拉伸**，行高随之改变，于是 `measureElement` 读到的高度与估算不再相等，第一排以下每一行都移动一个差值——正是「为何行高估算必须等于实测」（ADR 0008）记的那条症状。既有结论「卡片盒子的尺寸一变就要重新量」说的是常量要跟着改，这次是**盒子本身被改掉了**，而两条结论都没能拦住它。

**实测**（真实 Chrome 渲染 `frontend/dist` 里的 CSS，列宽 249.5px，16:9 的图片区应为 139.22）：

| 卡片状态 | 卡片高 | 图片区高 | 图片区 overflow | 图片区圆角 |
| --- | --- | --- | --- | --- |
| 未播放 · 16:9 | 205.31 | 139.22 | hidden | 7px |
| 未播放 · 竖屏 | 205.31 | 139.22 | hidden | 7px |
| 刚播放 · 16:9 | 205.31 | 139.22 | **visible** | **0px** |
| 刚播放 · 竖屏 | **505.92** | **439.83** | **visible** | **0px** |
| 刚播放 · 4:3 | **251.72** | 185.63 | **visible** | **0px** |

放进真实网格（4 列、1058px 内容宽、真实组件在 Vite 直接加载的源码里渲染，四张卡的缩略图依次是 480×270、480×853、480×360、480×270，被播放的是第二张）：

| 行 | 行高 | 四张卡 |
| --- | --- | --- |
| 修复前（竖屏那张被播放） | **525.92** | 505.92 / 505.92 / 505.92 / 505.92 |
| 修复前（16:9 那张被播放） | 225.31 | 205.31 × 4 |
| 修复后（竖屏那张被播放） | 225.31 | 205.31 × 4 |

**修复：角标移到卡片末尾。** 它是绝对定位，排在卡片末尾与排在开头在视觉上逐像素相同（相对位祖先仍是被播放的那张 `.card`），但图片区因此重新成为卡片的第一个子元素，上面两条声明一起回来。选这条而不是「给图片区补 `min-h-0` / `overflow-hidden`」，是因为后者只挡得住尺寸那一半：圆角仍然依赖 `:first-child`，尺寸对了而圆角静默变方，没有任何东西会报警——它会把下一次同类破坏盖住。**不新增第二份真值**这条判据在这里与 ADR 0008 给 `transition` 那处受限例外同源：那边重述供应商声明是因为没有第三条路，这边有。

**不变量因此写成了断言。** 「图片区是卡片的第一个子元素」落在 `interface.test.tsx` 里那条标记用例上，用图片区本来就带的 `aspect-video` 类作钩子（不为测试新增类，照 ADR 0008 的先例）。撤掉修复后这条断言立刻以 `expected false to be true` 失败，因此它不是装饰。jsdom 不做布局，所以它验的是 DOM 顺序这条**结构前提**，不是几何本身——几何仍只在浏览器里量得到，就是上面两张表。

**两条已核对的边界。** 一是没有第二条撑高路径：标题由 `truncate` 钉死单行，时长与按钮那一行在四个列数断点最窄的一档（4 列 @185px 列宽）与超长中文文件名下都仍是单行（实测恒为 21.00px）。二是这一类「靠 daisyUI 结构选择器撑着」的隐式依赖没有第二个落点：全仓库 `.card` 只有 `VideoCard` 一处用、`<figure>` 只有 `Thumbnail` 一处。

**`hoverRoom` 与 `rowFooter` 不需要重量。** 修复后的卡片盒与这两个常量当年被量时（无角标）逐位相同，上表修复后那一行就是证据。

## 为何取 `badge-neutral`，以及一条被实测推翻的推断

**先写下、后被推翻的那条**：初稿的理由是「`neutral` 与 `neutral-content` 两半都随主题翻转，所以压在任意缩略图上都读得清」。它由令牌名推出来，实测不成立——构建产物上 `--color-neutral` 在亮暗两个主题下都是 `oklch(14% .005 285.823)`，而 `base-100` 一个是纯白、另一个是 `oklch(25.33% …)`，翻转的只有后者。

**实测之后成立的说法**：这枚标记不随主题翻转，亮暗两主题下都是同一枚近黑底、近白字的标签，同一张缩略图上看到的完全一样；它的文字与自己的底色是 15.68:1，压在任意图片上都读得清。代价落在标记自身的**边框**上而不是文字上：压到很暗的缩略图上时那块底色不再看得出是一个盒子，文字仍然可读。这也是不把它做成半透明或染色的原因——底色一旦不透明，文字就永远落在它上面，而不是落在照片上。

## 验证与未做的部分

- **jsdom 能验的**：只有那一个 id 的卡片长出标记、其余卡片没有；标记是 `absolute` 且不在 `.card-body` 内；图片区是卡片的第一个子元素（这条是 issue #46 补的，见上文）。jsdom 不做布局，落点与遮挡在测试里没有可断言的落点。
- **真实浏览器里量过的**（构建产物渲染、Tauri IPC 用桩、真实鼠标点击卡片上的播放按钮）：只有被点的那张卡长出标记；标记距卡片左上 8 像素、字号 10.5px、圆角 7px；标记中心的像素在点击前后变过，即画在图片之上而不是被图片盖住；悬停时标记仍在且相对卡片的位置随之缩放。截图（浏览器渲染构建产物所得，**不是桌面端窗口截图**）：[上次播放标记亮色主题](../验收截图/上次播放标记亮色主题.png)、[上次播放标记暗色主题](../验收截图/上次播放标记暗色主题.png)。
- **那一遍还量到「点击前后每张卡片、每一行、滚动高度逐位相同」，这一条已被推翻并更正**：它只在 16:9 素材下成立，夹具是 1920×1080，非 16:9 的缩略图会把这枚标记变成一次尺寸变更（issue #46，机制、两张表与两张截图见上文「为何这枚标记必须排在卡片的最后」）。**夹具的 1920×1080 不是偶然，是这次漏掉的根本原因**：库里有竖屏视频时，一张卡片会涨到邻近卡片的两倍半高，并把整行一起拉走。
- **那个验收入口到今天也走不到这条分支。** `web-fixture.ts` 的 36 条视频 `thumbnail_path` 全是 `null`，它们渲染的是 `Thumbnail` 的无缩略图占位（一个 `div`，不是 `figure`），因此 `.card figure:first-child` 那两条声明根本不参与——用这个入口无论如何都复现不出 issue #46。这次的截图因此另搭了一页：Vite 直接加载源码，真实 `VideoCard` 进真实 `VirtualGrid` 一行，四张卡的 `thumbnail_path` 是四张不同宽高比的 SVG data URI（480×270、480×853、480×360、480×270），`lastPlayedId` 指向第二张；拍完即删。两张截图（**不是桌面端窗口截图**）：[修复前](../验收截图/issue46-修复前.png)、[修复后](../验收截图/issue46-修复后.png)。修复前那一张里，被播放的竖屏卡连同**同行的另外三张**一起涨成巨型卡，三张 16:9 的正文区被拉出一大片空白——「很乱」在图上就是这个样子。
- **桌面端走查尚未进行**：真实窗口里的观感、标记压在不同真实缩略图上的可读性、以及 HiDPI 下的表现都没有走过一遍。测试与上述测量只覆盖行为与几何，不代表已经在真实界面看过了。
