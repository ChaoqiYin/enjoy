# 共享服务采用只读 WebDAV

用户要在别的设备上看这台电脑上的视频，这个功能因此需要一个对外可连的服务。三个新术语的定义在 [CONTEXT.md](../CONTEXT.md)——**共享清单**、**共享服务**、**虚拟文件名**；这一篇只记取舍，不重述定义。

## 为什么是 WebDAV，而不是 DLNA、SMB 或 FTP

消费端不是我们写的，是用户家里已有的东西：电视上的 Kodi、VLC、nPlayer、Infuse，Windows 资源管理器与 Finder 的挂载。选定协议等于选定这份客户端清单。

- **DLNA／UPnP** 是直觉上最近的一个，也是被否掉的那一个。它要的不只是文件服务，还附带一套 SSDP 发现和一份 CDS 对象树，而各家电视对这两样的实现互不相同。拖动进度条在 DLNA 里不是必然支持的能力，能不能拖取决于电视那端——而「拖进度条能正常工作」是这件事的核心体验之一。代价大、结果不确定，否决。
- **SMB** 是系统级共享：账号、权限、共享目录都在操作系统那一层。应用带不走它，用户要先去系统设置里配一遍，而那正是这个功能想省掉的事。
- **FTP** 只有列举与取文件，没有结构可言，同样是明文，各家实现的兼容性也一样参差。
- **WebDAV** 是 HTTP 之上的一个小方法集。客户端到处都有；拖动进度条需要的 `Range` 是 HTTP 自带的；要自己写的只剩一张虚拟文件系统。选定。

## 为什么用现成的库，而不是自己实现协议

自研一个「够用」的 WebDAV 看起来只要几百行，也确实能过自己写的测试。过不了的是客户端：

- Windows 资源管理器会发 `Win32LastModifiedTime` 的 PROPPATCH，在 PROPFIND 的属性集上讨价还价
- Finder 挂载前会做 LOCK／UNLOCK 探测
- 各家对 `Depth` 头的取值、路径的百分号编码、目录要不要带尾斜杠的处理各不相同

这些分歧不会以协议错误的形式出现，只会以「电视上打不开」「能看见列表但播不了」的形式出现，而排查要跑到客厅去。用现成的库意味着这些坑已经有人踩过并修过。

代价是依赖，见下面「依赖代价」一节：那是体积与编译时间的代价，不是正确性的代价。

**库唯一不能替我们做的是虚拟文件系统**，它自带的本地文件系统实现把路径映射写死成「基准目录 + 请求相对路径」，没有重映射的钩子，也没有把多个目录聚合成一层的能力。因此 `share/fs.rs` 自己实现读目录、打开文件、读元数据三个接缝，客户端传来的任何路径只可能落在这张映射表里的某个真实文件上——查不到即未找到，路径穿越（`..`、绝对路径、符号链接）在查表这一步就无处可去。这是第二道安全边界，不是实现细节。

## 为什么只读

只读不是服务上的一个开关，而是**能力集**：服务不提供写入方法，因此没有任何一条路径能改到磁盘上的东西。

可写共享会连带引出一整类问题：客户端改名、删除、新建目录之后，数据库索引与磁盘上的实际情况怎么对上；WebDAV 的锁与 `If` 头要不要实现（Office 系客户端会要求）；以及在一个明文协议上给出写权限，等于谁拿到密码谁就能动用户的东西。这一版的边界是「用户名 + 密码连上就能读」，于是即使密码泄露，损失是「有人看了不该看的片子」，而不是「文件被删了」。

## 凭据，以及明文这件事

HTTP 层自己实现 Basic 认证（库不提供）：用户名固定 `enjoy`，密码随机生成一次、长期有效，存在应用偏好里与语言、主题并列。它不随空间变化，因为它是设备凭据而不是视频记录，不受[空间隔离决策](0011-空间之间不共享任何记录.md)的约束——每换一个空间就要在电视遥控器上重输一遍密码是不可接受的。密码是**四位数字**：这个字符串至少要在电视遥控器上按一次，而遥控器上每多一个要找的按键，就多一个把密码选得更差一点的理由；代价写在明处——四位就是一万种组合，它挡的是没被告知的那台设备，挡不住那台会去试的设备（一台同网段的机器把一万种走一遍是几分钟的事）。真要加强，先加失败次数限制而不是加长度：前者对按对的用户没有一点成本，后者刚好花在它存在的理由上。

**密码是明文 HTTP 传输的**：同一条链路上能看到流量的设备可以直接读到它，不必猜。这个边界是有意接受的，写在这里是为了它后来不要被当成 bug 修：

- 服务不自动开启、不常驻：没有用户在界面上的那一下，就没有端口在听，关掉应用即结束
- 但它监听的是本机**全部 IPv4 网卡**（`0.0.0.0`），不做网段限制。要判「哪个网段算局域网」得有一份网段表，而这份表在多网卡、虚拟机、VPN 的机器上极容易判错，判错的代价是一个本该连得上的电视连不上。真正的护栏是密码，以及用户随时可以按下的「结束共享」
- 于是密码挡的是「没被告知的那台设备」，不是能嗅探链路的攻击者，也不是一台直接挂在公网上的机器扫到端口的人
- 要挡住后者需要 TLS，需要证书的分发与信任，超出一个本地视频库的规模

真到了要修的那一天，正确做法是加 TLS，而不是把明文换成任何自制的混淆——混淆只会让后来的人以为传的是密文。

## 依赖代价

- **`dav-server` 0.11**，`default-features = false`：默认特性就是它自带的两套文件系统（本地与内存），本应用两个都不用——内容由共享清单拼出的虚拟文件系统提供。唯一在用的后端是应付 Finder 与资源管理器 LOCK 探测的占位锁系统，它没有开关，始终随库进来。
- **`hyper` 1、`hyper-util` 0.1、`http` 1、`bytes` 1**：本来就在依赖树里（更新下载走同一套 HTTP 栈），这一步只是把它们提升为直接依赖，不引入新的版本线。
- **`tokio`** 补三个能力：`net`（监听）、`rt-multi-thread`（两台设备各拉一部片子时不必排队）、`io-util`（把 tokio 的 socket 交给 hyper）。
- **`if-addrs` 0.15**：枚举本机网卡，界面上要告诉用户往电视里填哪个地址。这台机器在哪些网上，除了操作系统没有别的来源。
- **`getrandom` 0.3** 与已在树里的 **`base64` 0.22**：抽密码，以及拼那个认证头。

每一个依赖在 `src-tauri/Cargo.toml` 里都有自己那一段「为什么要它」的注释，此处不重复。

## 服务的生命周期，以及「谁在连」

- 服务由用户显式开启，没有任何其他操作会让它开始监听；它属于开启它的那个空间，切换空间即结束；同一时刻至多一个。
- 服务持有的是**开启那一刻的路径快照**：运行期间清单变化、磁盘文件被删改都不影响已在服务的这一份，要生效必须重启服务。界面因此必须说出这件事——用户刚加进去的视频在电视上找不到，是这条快照语义的正常结果，不说就是一个看起来没生效的操作。判定「变了没有」由后端比对（服务手里那份 vs 空间现在那份），与密码那一处的 `needs_restart` 同源：被告知用户点了什么会漏掉没人点过的变化。
- 结束时端口真的释放，不是「应该会释放」：服务跑在自己的线程和它自己的 tokio 运行时上，`close_share` 等这条线程结束才返回，测试因此可以直接对着那个端口再起一次监听。
- **「连接」不是一个能观察到的状态。** WebDAV 客户端取完它要的那一段就断开，协议层没有保持连接这回事，也没有心跳。因此设备列表的口径是「最近一分钟内请求过」，界面上照这个口径写。这条记在这里，是为了后来者不要去找那个不存在的「在线状态」字段。

## 与开发基线的关系

这一决定推翻了基线里「不部署独立 HTTP server」那句话，第 3 节已改写，边界与界面约定写在新增的第 12 节。原话要守的那件事仍然成立：**界面与后端之间不经由 HTTP**，界面走 Tauri 的 Command 与事件。这个服务是对外的，不是界面与后端之间的那条通道。

八个切片全部落地：#47 共享清单（`d423574`）、#48 服务能起来并在浏览器里验证（`bce57ab`）、#49 客户端能看到并拉取（`6503202`）、#50 密码与鉴权（`1d4f37d`，随后 `f15f5d0` 补上开启时携带空间）、#51 最近活动的设备（`9481f04`）、#52 连接地址与端口顺延（`65bff9b`）、#53 状态提示与生命周期保护（`3d7e513`）、#54 文档（本篇）。此后 #56 补上分享页的清单网格与两处提示（快照变了要重启、移除索引会一并移出清单）。

测试只开两个新接缝：虚拟文件系统的对外契约（`share/fs_tests.rs`，用临时目录里的真实文件），以及控制层配一个真实 HTTP 客户端打到真服务上（`share/control.rs`、`share/service_tests.rs`、`share/activity_tests.rs`）——只读边界真的挡住写入、`Range` 真的返回正确分片、401 的响应头客户端认不认、目录结构对不对、端口被占时真的顺延、设备活动真的被记下来。这些一条都不由我们自己假设：那是别人写的库，它对协议的理解只能端到端观察。
