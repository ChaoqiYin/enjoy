# 文件身份改由文件大小与修改时间判定

[ADR 0001](0001-增量扫描复用已有媒体处理结果.md) 的取舍里写着「MD5 判定需要读取文件内容。仅比较大小和修改时间并不能保证内容未变化，不能默认为等价规则」。本条明确推翻它：文件身份改由绝对路径与（文件大小，修改时间）的配对判定，判据不再读文件内容。

推翻的理由是代价与呈现方式。判据要求读完整文件：一个约 126 GB、由数十个大体积视频组成的真实库，本机实测磁盘顺序读约 296 MB/s，单线程「读 + 算」需 8～12 分钟。而发现阶段不发布逐文件进度，界面在这段时间里只能显示「正在扫描 · 已发现 0 个，已处理 0 个」，看上去与卡死无异；使用者在等待中按下「取消扫描」，日志里只留下一条「扫描已取消」的业务错误，无法据此判断是慢还是死。换言之，0001 认定「大小与修改时间不能保证等价」时比较的是两种判据的严谨程度；本次比较的是「一次严谨但让应用显得死掉的扫描」与「一次近似但接近瞬时的扫描」。代价换来的结果：发现阶段一个文件只做一次 stat、不打开文件，重扫一个没变过的库接近瞬时，只有新增或确实变化的文件进入处理。

## 为何判据是路径加上（大小，修改时间），而不是继续比较内容哈希

文件身份 = 绝对路径 +（文件大小，修改时间）。大小或修改时间任一变化即视为身份变化，已存的时长／分辨率／编码／缩略图作废并重算；两者都没变则跳过处理，复用已完成的结果。库里没有记录的新路径是新增而不是变化——它没有自己的派生信息可以作废。

这一对值此前只被当作写回的乐观锁令牌，现在同时就是身份判据；元数据写回与缩略图写回本就用它守卫，「媒体处理完成」的守卫现在也换用它，三处与判据同源。判据只结算一次：既有行的比较在仓储读索引时做一遍，结论以参数形式传给写入语句，SQL 不再比较第二遍（此前 Rust 记一次计数、SQL 再判一次是否作废，是两份实现），计数也由同一个结论推出。

记录的存亡判据不变，仍是 [ADR 0003](0003-扫描合集的来源与过期记录的清理判据.md) 定下的那条：路径是用户在库里的锚点，身份只决定派生出来的媒体信息还算不算数，不决定记录与使用记录的存亡。

## 为何接受同长度改写的漏判，而不是为它补一道内容校验

已知并接受一个漏判：大小与修改时间都没变、只有内容被换掉的替换不会被发现（例如解压或复制工具保留原时间戳，且新文件与旧文件同长度），该记录会继续沿用旧的缩略图与媒体信息，直到该路径上的文件下次发生大小或修改时间变化。这正是 0001 那句话担心的事，本次选择承担它：它要同时满足「等长」与「时间戳被还原」两个条件才成立，而扫描从分钟级降到秒级之后，下一次扫描窗口离被漏掉的那次变化更近。这条盲区由一条显式用例固化——断言同路径、同大小、同修改时间、内容不同时变化计数为 0，并在注释里指向本 ADR——以免将来被当作缺陷顺手修掉。

## 为何打不开的文件改由媒体处理阶段报失败，而不是在发现阶段拦下

发现阶段不再打开文件还有一个连带结果：单个文件「存在但打不开」（权限、被占用等）不再在发现阶段被识别，这类文件会被正常收录，其内容读不出改由媒体处理阶段的失败计数与通知体现，记录仍然保留。理由是判据换掉之后，「打不开」已不是发现阶段能看到的事实——发现阶段只读元数据，取不到大小或修改时间才算它的失败——要把它塞回发现阶段，就得重新打开文件，与本次改动的前提相斥。

目录级不可读与遍历读不出的子树两类语义不变：整条配置目录列不出来时整条跳过并计入「不可访问目录」；遍历中取不到元数据的子目录或文件按失败跳过并计数，其记录原样保留。[ADR 0003](0003-扫描合集的来源与过期记录的清理判据.md) 对这些情形的判据继续有效，只是「文件级失败」的来源从发现阶段移到了媒体处理阶段。

## 为何取消检查点退化为每目录项一次，而不是新增更细的粒度

暂停与取消原先挂在哈希的分块循环上：固定大小缓冲区逐块计算，每块之间检查一次。不再读内容之后，一趟发现里最细的可中断位置就是遍历的每一个目录项，检查点保留在那里。代价是粒度变粗——一个大目录里按下暂停或取消，要等到下一个目录项才生效；但发现阶段只剩遍历与一次 stat，这段等待是毫秒级的，用户感知不到差别。这项降级随本 ADR 记录，以免后人把它读成遗漏。

## 为何不做发现阶段逐文件进度，而不是补一条进度事件

发现阶段只剩遍历与一次 stat，一条配置目录可在毫秒级走完，界面现有的等待指示足以覆盖这段空白，因此不新增逐文件进度事件。0001 的动机问题（界面上数字长时间不动）由「发现阶段不再读盘」本身解决，不由进度事件解决：补一条进度事件只会让前后端各多一条只在极端慢盘上才有意义的通路。「保留全量哈希、只补进度」这条备选的否决理由见下节。

## 为何否决这四条替代路径，而不是从中挑一条

- **保留全量哈希、只补进度。** 没有解决读盘成本：界面上的数字会动，8～12 分钟的等待与磁盘损耗照旧，使用者仍会在等待中取消。
- **多线程并行哈希。** 仍要读满全盘，机械盘上并行收益有限（只快一半左右），还要引入线程池与错误聚合。
- **头尾采样哈希。** 引入非零漏判（只改中段的替换同样漏掉），却仍然要读盘，等于两头的代价都付。
- **文件系统变更日志或实时监控。** 机制重，跨卷与网络盘不可靠，且与「用户主动扫描、应用不启动目录监听器」的既有决策直接冲突。

## 取舍与影响

- **升级不重算整个库。** 存下来的大小与修改时间本来就是下一次判据要比的两个值，它们此前已在库里，因此版本 4 升级之后的第一次重扫不会因为判据换了就把整个库重算一遍。
- **两项被放弃的能力以测试与 ADR 明文固化，而不是静默消失。** 同长度改写的漏判、发现阶段不再识别打不开的文件，各有一条对应用例；后者改写自原先锁「权限不可读即在发现阶段失败」的用例。
- **内容哈希库依赖一并移除。** 判据是它最后的使用者。
- **对外契约不变。** 发往前端的视频对象只少掉那个从未被前端声明过的哈希键，序列化字段集合因此与前端类型恰好一一对齐；扫描状态契约与错误码词表不变，前端零改动。
- **跨路径的内容去重仍不在范围内。** 不同路径下内容相同的视频继续视为不同视频，这条 0001 已记录的取舍不受本次改动影响。

## 实施状态

规则已确认并实现，落地于 `0444a07`。数据库版本为 4：版本 2 与 3 携带的 `videos.file_md5` 列在版本 4 就地删除，照版本 3 删 `available` 的做法——先在 `pragma_table_info` 里探测该列是否存在，存在才删，因此「版本号没跟上、列却已经不在」的库同样能打开。升级绝不重建表，收藏、播放历史、已配置目录、缩略图路径与媒体字段都原样保留。版本 1 及更旧的清空约定保持原样，不做兼容迁移（见 [ADR 0001](0001-增量扫描复用已有媒体处理结果.md) 的实施状态）。数据库迁移用例（含新增的「版本 3 → 4」一条）独立成 `repository/migration_tests.rs` 模块。设计基线见[扫描与处理流程](../本地视频统一启动器-开发基线.md#8-扫描与处理流程)。
