## 14. 插件系统

同一个应用交付给不同的人，而每个人要的附加能力不一样。插件把这类能力从仓库里挪到运行时：装、启停、卸都不重新发布应用，也不改仓库里的任何代码。形态、运行体与挂载点的取舍见[插件系统的形态](adr/0043-插件系统的形态.md)、[运行体是常驻的 WASM 实例](adr/0044-运行体是常驻的-WASM-实例.md)与[挂载点分两半且是封闭集](adr/0045-挂载点分两半且是封闭集.md)。

**插件**是一个目录，位于应用数据目录下的 `plugins/<插件 id>/`，装着**插件清单**加它的两半——**插件界面**（参与内核界面的那半，由内核动态引入并把 React 等基线交给它）与**运行体**（干活的那半，编译成 WebAssembly，在内核进程里常驻）。两半**至少有一个**，不能都空。插件本身与它自己的数据目录是**全局的**（一个插件一份，不按空间分），而插件看到的数据始终属于某个空间。

**挂载点是封闭的六处**，插件只能往它们上面**加料**——不能删、不能改、不能拦。这六处各是什么，以及每一处的类别、形态、归属、空间、参数形状与冲突规则，只有[插件挂载点目录](插件挂载点目录.md)一处可读：它是一份**生成的、机器可读的目录**，事实来源是 `shared/plugins/mount-points.json`，两侧的类型、`npm run check` 里的 `check-plugins` 与给插件作者的文档都读它这一处，本基线因此不再抄一份。

两条理由不在目录里，写在这里：动作类与流程类挂在**运行体**上而不挂在界面上——爬封面插件没有插件界面，它的触发点就是视频上的一个动作，挂在界面上这类插件就永远触发不了自己；`video.fields` 那条冲突规则让后一个插件**补位而不是覆盖**，因此界面必须显示每个字段是哪个插件提供的，插件顺序也必须由用户可调。

**调用参数给的是完整上下文，不是一条 id**：六处**每一处**都带本次调用所在的空间——插件自己的数据目录是全局的，但它看到的数据始终属于某个空间，插件页面也是在空间内部打开的；链式那一处还带链上已经问到的字段值**及其来源插件**，因此后一个插件看到的是「前面问了谁、给出了什么」，能补位而不必重复劳动。字段的来源只在**参数**这一侧出现：结果是插件交回来的数据，来源由内核写库时补上，插件自报的身份不作数。

**能力只授予四样**：取一个网址、读写插件自己的数据目录、写日志、读本次调用的视频信息。**不授予**任意文件系统、直接写数据库、调度或调用内核命令、开放监听端口。**插件永不直接写数据库**——在数据挂载点上它只返回数据，由内核写，这是它写入库里的唯一路径。运行体在 WebAssembly 里，没有任何环境权限，能做什么完全由内核导入给它的东西决定。

**插件失败绝不阻塞内核流程。** 一次调用抛错、崩溃或超时：记下插件名，给一条点名插件与挂载点的通知，这一次调用视同插件什么都没说，内核照常走完；同一个插件在五次不同调用上失败即自动停用。清单不合规（缺字段、id 不合法或重复、声明的能力不在允许清单内）的插件**列出来但不加载**，挂载点接口版本超出内核支持范围的另说一条文案。安全模式能让应用不加载任何插件就起来（把插件启用状态那份记录改名成带时间戳的备份、恢复到默认停用全部插件、保留已安装的插件目录）。

**v1 不做网络安装，也不做市场**：安装只从本地文件夹或归档，装完重启生效。

**CSP 与资产协议范围是一对，必须同时改。** 缩略图、插件界面的入口、内核写进 `$APPDATA/covers/` 的封面**都走资产协议**，而 `default-src 'self'` 不含资产协议那个源——只设 CSP 不动范围，缩略图会整片消失、插件界面永远加载不起来。因此：`app.security.csp` 由 `null` 改为给资产协议留源（`img-src` 另需 `data:`，`--window-glyph` 是内联 SVG；`script-src` 收插件入口模块），两种平台形式都列出（`asset:` 与 `http://asset.localhost`）；`app.security.assetProtocol.scope` 从只管 `$APPDATA/thumbnails/**` 扩到插件目录与封面目录。**桌面端的开发模式不在这条注入里**：`devCsp` 未指定时确实回退到 `csp`，但窗口在 `tauri dev` 下直接加载 Vite 的开发地址——`manager/webview.rs` 的 `PROXY_DEV_SERVER` 只在 `dev` 且 `mobile` 时为真——HTML 不经 `tauri://` 协议，那份 CSP 头与 meta 都没有落脚处。真机读数（#90）：桌面 dev 下窗口里 `eval` 与跨源 `fetch` 都不触发 `securitypolicyviolation`，即策略根本没生效，因此 `connect-src` 不必带开发服务器的源，也没有单列 `devCsp` 的必要。**CSP 兑现的只有一件事**——插件自己的外部网络访问去不了；加进来的 `asset:` 只让窗口读本机上那几个目录，与这条不相干。它堵不住「插件调内核命令」，那条边界靠插件与内核之间那条**窄授权的命令**（内核通过创建上下文的闭包绑定调用者身份，不采信插件自己发来的身份字段）。具体串与范围以落地时为准。

内核里唯一认识插件的是**插件宿主**（`src/plugins/`）：读清单、装与卸、把挂载点派发给插件、把插件的失败降级掉。内核其余代码不认识任何具体插件的名字，只调它一处。前端侧的注册口与插件页在 `src/plugins/`，插件往界面上加东西只能经由注册口，每个注册口自己返回清理函数并接进统一的收集器（逆序执行、可异步等待）。第一条插件是**爬封面**，它是这套设计的第一份验收。

### 14.1 启动时的接线

应用起来时：读插件目录 → 逐个走四条清单校验并读启用记录 → 给启用的插件建运行体 → 启用。**这条路径绝不允许阻止应用启动**——任何一步失败都只写一行日志、少一个插件，应用照常起来，这正是 ADR 0044 §7 的安全模式存在的理由。落到代码上是 `app::initialize_backend` 在 `app.manage` 之前调一次 `plugins::loading::load`，而它返回 `()`：没有 `Result` 可漏。

### 14.2 插件的「数据目录」

是**插件目录下的 `data/`**，`storage` 能力读写的就是它里面的一个文件名。它跟着插件目录走，卸载时和插件一起没，不另立一份。插件的数据目录是**全局的**（不按空间分），与上面「插件看到的数据始终属于某个空间」不冲突：前者是它自己攒下来的东西，后者是内核每次交给它的。

### 14.3 封面这条通路

插件在 `video.fields` 上返回 `{"key": "cover", "value": "<一个网址>"}`，**内核去下**。分工不是随意的：插件只有自己那份数据目录的写权限，而窗口画图走资产协议、CSP 的 `img-src` 里没有远程源，图片必须落在本机上，本机上唯一能往插件目录外写的就是内核。所以插件用 `fetch` 算出**要哪张图**，内核把它下下来写进 `$APPDATA/covers/<视频 id>.<扩展名>`，再把**路径**写进 `video_fields`。**插件返回的是地址，库里存的是路径，中间的加工是内核做的**（`plugins/cover.rs`）。下载失败就**不写这个字段**，记录保持原来那张图——`save_fields` 只加不删，因此「不写」就是「保留」。

**内核只在一处认识 `cover` 这个字段名**：列表查询里对 `video_fields` 的一次左连（`key = 'cover'`，`repository/videos.rs`），把封面当成记录的一个字段带出来。**不往 `videos` 上加列**，也没有第二条写库路径——写了列就是同一个事实的第二份真相，插件再答一次它就不再对得上。

界面这一侧，**画图的地方只有一处**：卡片、紧凑行与详情面板共用同一个 `Thumbnail`，它优先画插件封面，没有才退回媒体流程做的那一帧。三个调用点各写一份判断就会各自漂移。优先级是写死的：**插件封面胜**——用户是**为这条视频**去问那个插件的，而那一帧是问之前就有的东西。

### 14.4 触发落在视频自己的右键菜单上，一次只问一个插件

菜单里每个「能干活且已启用」的插件占一项，名字取**清单里的 `name`**（用户选的是插件，不是一个内核写的动词）。`video.actions` 因此**不是**「问所有插件再收集」：目录里写的是「插件往视频的右键菜单加一个**自己的**动作」，问所有插件会让这一项与那个插件脱钩——没有插件界面的插件只有这一条路能触发自己，点错人就是彻底触发不了。

### 14.5 最小示例插件

两份，都在 `examples/plugins/` 下，作者能整个复制到 `$APPDATA/plugins/` 里直接用（目录名必须等于清单里的 `id`）：

- **`hello-page/`**：只有插件界面、只注册 `app.page` 的那一间，最小的一份。
- **`video-panel-demo/`**：同样只有插件界面，注册的是另一处界面类挂载点 `video.panel`。

两份都同时是契约目录的使用示例——注册哪个挂载点、被交给什么、要交回什么，只读[插件挂载点目录](插件挂载点目录.md)一处；验收页里挂上的是它们本体，不是另抄的一份。**为什么是两份**：界面类挂载点有两处、画在两个不同的地方，只有一个样板的话另一处在验收页里永远没有东西可画，「没有插件注册这里」与「注册了但没画出来」就分不开——而后者正是最该被看见的那种失败。

### 14.6 插件的顺序

顺序由用户排，而它**决定 `video.fields` 这条链上谁先被问**：链上取的是**第一个非空答案**，所以顺序就是「这个字段谁说了算」（ADR 0045 §3）。这是本节里唯一一条用户自己能调的规则，因此它必须两端都接上，不能只接内核。

**顺序住在自己的一个文件里**：`$APPDATA/plugins/order.json`（`plugins/order.rs`，`FILE` 在第 40 行，读在第 49 行、写在第 65 行），**不并进 `enabled.json`**。三条理由：启用记录写的是「哪些开着」，而顺序还要能说出「哪些关着」——关掉一个插件不挪它的位置（`plugins/order_tests.rs` 的 `switching_a_plugin_off_keeps_its_place`），所以关着的插件也得在顺序里占一个名字；安全模式把启用记录**改名**成备份（`Store::set_aside`），顺序若住在里面就会跟着一起被搁下，而安全模式要的是「少加载插件」，不是「用户排的次序也丢了」；顺序比它所针对的那批插件活得久，文件里留着一个已经不在的 id 不是错误，`Registry::reorder` 会忽略它（`plugins/registry.rs` 第 93 行）。

**位置的三条规则**：关掉一个插件**保留**它的位置（与运行中的轮转同一条规则）；卸载**把位置一起带走**（`plugins/store.rs` 的 `uninstall`，第 256 行起，删掉目录之后把 id 从顺序文件里滤掉）——位置是留给「还在、还会回来」的插件的，重装落回旧槽位会排出一个用户从没排过的次序；刚装进来或用户手动拷进来的目录**排在最后**（`Store::ordered`，第 147 行：顺序里没命名的按 id 排在已命名的之后）。插件的 id 只能装一份（`install` 见到同名目录即拒），因此顺序里没有重复项要处理。

**两侧都接上，中间不许缺一段。** 内核侧：`loading::load` 在**遍历之后**调一次 `host.reorder(&store.order())`（`plugins/loading.rs` 第 100 行）——遍历走的是目录列表，顺序是一次性盖上去的，否则「谁先被问」就成了读目录次序的偶然。界面侧：`list_plugins` 答的就是 `Store::ordered()`（`commands/plugin.rs`），所以页面列出的次序与内核下一次启动要问的次序是同一个；注册口读的也是这份答案——`PluginHostProvider` 造一只盒子同时交给宿主与注册口（`frontend/src/plugins/PluginHostProvider.tsx` 第 126–127 行，第 135 行交给宿主），宿主每收到一份答案就写进去（`frontend/src/plugins/host.ts` 第 350 行），注册口在有人读某个位置时读它（`registry.ts` 的 `order` 选项）。**只接内核不接界面**会得到最难查的一种不一致：用户改了顺序，而插件界面仍按旧的排。

验收读数是 `plugins/loading_tests.rs` 的 `the_order_the_user_arranged_decides_which_plugin_fills_a_field`：两个插件都答 `cover`，把第二个排到前面，链上第一个非空就来自它，且重启之后仍然如此。把 `loading.rs` 第 100 行那一句拿掉，这条用例立刻变红（读到的是 `("cover", "/first.jpg", "first")`）。

**命令只有一条，参数是整份顺序**：`set_plugin_order`（`commands/plugin.rs` 第 43 行），收整份 id 列表而不是「交换这两个」——id 是内核发出去的名字，谁装没装只有内核知道，一个它没发过的 id 会被拒（`plugin.not_found`，且拒绝发生在写文件之前，`store.rs` 的 `set_order` 第 184 行）。读当前顺序不另开命令：`list_plugins` 答的已经是它。

**「不做热插拔」这条也管顺序**：内核侧只在**下一次启动**时应用它；界面侧的红利是行与位置**立刻**重画（`refresh`），而运行中的窗口仍按启动时的顺序问插件。页面上那句「插件改动在下次启动应用时生效」对顺序同样成立。

**界面**：插件页每行在启用开关左边多一组两个箭头（上移／下移，`frontend/src/pages/PluginsPage.tsx` 第 244、254 行），首行没有上、末行没有下——两端是禁用，而不是留着不响。按一次发的是整份顺序，收到的答案直接拿去重画行：页面自己不动这两行，因为顺序是内核的事实。


### 14.7 `plugin.settings` 的值存在哪：全局一份，随插件卸载消失

- **值住在 `plugin_settings` 表**：四列 `plugin_id` / `key` / `value` / `updated_at`，主键 `(plugin_id, key)`（`repository/schema.rs:89`，随版本 8 落地）。目录里那一条只说了「内核问插件『用户必须填什么』，然后自己渲染、校验、保存」，值放在哪里是它没说的。
- **不按空间分列**，这是最要紧的一条：设置说的是**这个插件怎么干活**，不是某个空间里有什么，同一个答案在每个空间都成立，因此表既不挂 `videos` 也不挂 `spaces`（`schema.rs:48` 把这条与 `video_fields` 的方向对照写在一起）。
- **问的时候空间照样带上**：`PluginSettingsParams.space` 在目录里，ADR 0012 要求每个空间作用域命令显式带 `spaceId`，插件可以据此问出不一样的东西；`commands/plugin_settings.rs:36` 与 `:69` 都收 `space_id` 并放进 `SpaceRef`——**存的时候不用它**。
- **`plugin_id` 是裸字符串，不做外键**，理由与 `video_fields.source_plugin` 相同：插件住在磁盘上，表结构不跟着插件目录走。行随卸载消失，但那是**卸载路径故意删的**（`plugins/store.rs:273` 调 `forget_plugin_settings`），不是级联——级联要有一张父表，这里没有。
- **内核不自己发明设置项**：表里存的是值，键的集合每次问插件才知道；插件改了声明，旧键的值只是留着不再被读到（`plugins/settings.rs:106`）。

### 14.8 值怎么回到插件：问的那一次一起给，启动时先交一次

- **只有一条通路**：内核问插件「你需要什么」时，把用户已填过的值一起放进 `PluginSettingsParams.values`。没有第二条「推送设置」的调用，也没有「插件自己去读」。因此**保存那一刻的第二次提问，同时就是交付**。`commands/plugin_settings.rs:91` 的 `settings(state, space_id)` 既重画页面、又让刚保存的插件当场拿到新值——同一个函数，两件事，所以不存在「存下了但没告诉插件」的中间态。Rust 用例 `what_was_saved_reaches_the_plugin_in_the_same_call_that_saves_it` 数的就是这次调用里的 `params.values`。
- **启动时补一次**：`initialize_backend` 在 `plugins::loading::load` 之后调一次 `settings::hand_over`（`app.rs:141`，`plugins/settings.rs:89`）。理由不是对称：只有插件页打开时内核才会提问，而**从视频右键菜单干活的那类插件永远不到插件页去**，不补这一次它一辈子看不到用户的设置。它**只问有已存值的插件**——无条件问一遍会让每个没声明 `plugin.settings` 的插件每启动一次失败一次，五次失败就停用了，多问这一次的代价是插件本身（`plugins/settings.rs:84`）。**交不成也不拦启动**：返回 `Err` 只写一行 `tracing::warn`，与 §14.1 同一条规矩。
- **校验对着「画表单时那次提问」拿到的声明**，不是「拿着新值再问一次」的声明（`commands/plugin_settings.rs:77`）：用户改的是一张已经画出来的表单，被校验的答案要对着那张表单的字段。Rust 用例 `the_form_is_checked_against_the_declaration_the_plugin_gave_for_the_values_it_was_handed` 用一个「收到 `mode=advanced` 才多要一个 `token`」的插件把这条钉住。

### 14.9 逐字段的拒绝文案留在哪：错误协议里，字段名走 `params`

**没有第二套「表单错误」协议。** 文案住在 `shared/locales/{en,zh-CN}/errors.json`（`plugin.settings.required`、`plugin.settings.directory_missing`、`plugin.settings.unavailable`，两个文件各第 78–80 行），与其余错误码同一处，界面用 `errorMessage` 取——它自动被 `check-translations` 盯着，也自动跟着语言设置走。**校验为什么在内核而不在界面**：四种字段里有一种是目录，而「这个目录在不在这台机器上」只有这一侧知道；界面用平台的选择器挑一个，交出去的却是一个字符串，字符串什么都能说（`plugins/settings.rs:11`）。

**哪一个字段错了，走 `AppError` 的 `params.field`**（`plugins/settings.rs:192` 的 `required`、`:176` 的目录那一条）。界面读 `failure.error.params.field`（`frontend/src/plugins/PluginSettingsForm.tsx:67`），落点**有三种，不是两种**：点名的字段在画出来的表单里，就画在**那个字段的包装里**（`:108`）；没有字段名（比如插件在画表单与保存之间不跑了），或者点名的字段**这张表单从没画过**（内核保存时会重新问一次声明，拒绝带的是**新声明**的键，而表单手里是页面加载那次提问的声明——`commands/plugin_settings.rs` 自己写着两次声明可以不同），都画在按钮上方的 `Alert` 里（`:119`）。**没有第四种**：两处分支合起来覆盖全部失败，而且第三种是**必须**接住的——画不出来的拒绝等于没告诉用户，保存失败了而屏幕上什么都不说。走查读数（真实浏览器 + 验收夹具 `frontend/acceptance/web-acceptance.html` + 真实鼠标）：留空必填项按保存，那句 `This setting has to be filled in` 与出错的输入框**同属一个包装 div**（`sameWrapperAsField: true`），与另一个字段**不同属**（`sameWrapperAsField: false`），几何上紧贴出错字段下沿 5px；填回去再保存，这句话消失、字段画的是内核留下的值。
