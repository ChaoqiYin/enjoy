## 2026-09-20 检查更新改为主动触发

- 取消应用启动时的自动检查：更新只在用户于点设置页点击「检查更新」时查询一次，失败仍在通知区提示并保留重试入口。随之删除启动检查所弹出的「发现新版本」模态询问——它唯一的触发者就是启动检查，留下会让用户在设置页点按钮后弹出一个盖住设置页、内容重复的对话框。更新说明（发布日期与更新内容）改为内联在设置页的更新区域，「下载」按钮留在版本行上，长说明因此不会把按钮推出视口。下载完成后角落的「更新已就绪」浮动提示保留，覆盖「点了下载后离开设置页、下载在后台完成」这种情况。

- 扫描期间封锁空间操作：后端 `scan/control.rs` 的 `space_change_gate` 以 `is_running()` 一个判断覆盖所有方向——扫描槽被占即拒绝，包括暂停中，以及单文件「刷新信息」持有槽位时；四条空间命令共用一个包装函数，闸门因此不可能被某一条命令漏掉。前端把切换器与设置页的新建、重命名、删除三个操作一并置灰并给出理由，但禁用只是解释，权威在后端。这条锁**不是防竞态**：空间 id 在调用发生的那一刻从上下文读取，正在跑的任务写的就是它启动时的那个空间；锁要解决的是「用户此刻不在那个空间里」——扫描进度是应用级的，切走之后仍会看着前一个空间的进度模态框。理由记在 ADR 0012，单文件刷新留在锁内属于这条取舍的一处已知代价。

## 2026-09-26 检查更新白屏

- 缺陷：在一台装着旧版本的机器上点「检查更新」，检查到新版本后整个窗口变白，连「下载」都点不到。成因在两端各一半——`update/control.rs` 的 `describe()` 用 `update.date.map(|date| date.to_string())` 发送发布日期，而插件给的 `Update::date` 是 `time::OffsetDateTime`，它自己的 `Display` 不是 RFC 3339，实测形状是 `2026-09-26 14:34:10.0 +00:00:00`（日期与时间用空格分隔、秒后永远带 `.纳秒`、偏移量固定九字符 `±HH:MM:SS`）；`UpdateSetting` 的 `ReleaseNotes` 把该字符串交给 `new Date()` 再交给 `Intl.DateTimeFormat`，无效日期的解析结果是 `Invalid Date`，而 `format` 对无效日期抛 `RangeError: Invalid time value`，不是返回空串。前端没有任何错误边界，React 对未被接住的渲染错误会卸载整棵树，于是代价从「少一行日期」变成「整个窗口」。
- 触发条件是「检查到一个带 `pub_date` 的可用更新」，因此已是最新的构建只弹「已是最新版本」、不会白屏，而**任何落后于最新版的已安装包一点检查更新就必然白屏**。这条缺陷因此把投递修复的那条路堵死了：旧版本走不到下载，本修复无法经应用内更新送达，只能让用户手动装一次安装包。
- 两端都改：后端新增 `published_at`，用 `time` 的 `Rfc3339` 显式格式化（`Cargo.toml` 随之显式声明 `time = { version = "0.3", features = ["formatting"] }`，此前 `time` 只是 updater 插件的传递依赖，锁文件里只多了这一条直接依赖记录）；前端新增 `formatReleaseDate`，读不出日期的字符串返回 `null`，该行不渲染而更新说明照常显示；新增根级 `ErrorBoundary`（`frontend/src/shared/ErrorBoundary.tsx`，位于 `App` 的所有提供者之外），被接住的渲染错误以错误通知给出，新增错误码 `app.render_failed`（中英各一条），关闭通知即重新渲染该屏幕。边界只覆盖渲染期错误：事件回调、定时器与 Promise 拒绝不经过它，各自仍在原处处理。
- 为什么两侧测试都没拦住：测试替身一律比真实后端更正确。`UpdateSetting.test.tsx` 的 `release` 夹具与 `frontend/acceptance/web-fixture.ts` 的 `setUpdate` 都手写 `date: '2026-09-01T00:00:00Z'`，而契约只在 Rust 一侧被打破，`describe()` 又因为 `Update` 有私有字段而无法在测试里构造。新增用例改为直接钉住两端：Rust 侧 `a_published_date_is_written_as_rfc3339` 断言到字面量、`a_release_without_a_date_sends_none` 断言无日期时不给字符串；前端侧 `formatReleaseDate` 的两条（`updateFormat.test.ts`）与 `keeps the release when its date is not one it can read`（`UpdateSetting.test.tsx`）以旧的 `Display` 形式作为输入，`ErrorBoundary.test.tsx` 两条覆盖「渲染失败给出通知」与「关闭通知后重绘」。
- 全量重跑（2026-09-26，Windows）：Rust 85 项测试中 84 项通过、1 项忽略（新增 2 项），`cargo clippy --all-targets -- -D warnings` 与 `cargo fmt --check` 通过；前端 131 项测试为改动前基线、本次 136 项全部通过（以 `git stash` 摘掉本次改动的两个测试文件后重跑量得 131），新增 5 项全在其中。源码约束、翻译检查、版本号一致性检查、TypeScript 检查与生产构建均通过。
- 未覆盖的部分：
  - **真机复验未做**。上述结论来自单元测试、静态检查与生产构建；「在装了旧版本的机器上点检查更新不再白屏、并能一路走到下载与重启」这条链路没有实机跑过，修复也尚未发布，因此这次白屏的消除只有单元测试层级的证据。
  - 测试替身与真实后端之间仍无自动对齐手段：`web-fixture.ts` 的 `setUpdate` 会继续手写日期，契约再次漂移时依旧是两侧测试都测不到中间，只有真机能发现。本次没有为此加守卫。

## 2026-09-27 更新下载中断与续传改造

- 缺陷：在装了 0.1.3 的机器上点「检查更新」发现了 0.1.4，点「下载」后到 80 多 KB 弹出「更新下载失败」，排查编号 `err_1790438963863_2`。进度按 1% ≈ 894 KB 一档节流，80 KB 是回调的第一块，因此断点落在 80 KB ~ 894 KB 之间。
- 定位（同一台机器、同一网络实测）：**代理对任何持续传输都在 13~16 秒左右掐断连接**，与 GitHub 无关——GitHub 的安装包 692,664 字节 / 13.1 秒、928,768 字节 / 16.4 秒两次 `server closed abruptly`，第三次跑满 60 秒不断（14.4 MB / 240 KB/s）；非 GitHub 的 Hetzner 100 MB 在 556,800 字节 / 14.3 秒、OVH 100 MB 在 603,655 字节 / 13.8 秒同样断。直连（不走代理）不中断但恒速 6.6 KB/s。3 次里断 2 次的复现率，断点与 app 报的窗口同带。
- 排除的代码嫌疑：插件 `UpdaterBuilder` 硬编码 `timeout: None`，插件 `Config` 里根本没有 `timeout`/`proxy` 字段，**没有总超时**在掐它；reqwest 的 `system-proxy` 经 `tauri-plugin-updater` 的默认 feature 打开，`hyper-util` 在 Windows 上读注册表 `Internet Settings`，所以 app 确实走了系统的 `127.0.0.1:7897`。根因是代理断连 + **插件 `Update::download` 一次性读完、断了就从零开始**：89 MB 在这种链路上不可能送达。
- 顺带发现的可观测性缺口：`AppError::new` 写了 `tracing::error!(error_id, code, diagnostic, ...)`，但 `tracing_subscriber::fmt()` 只写 stdout，而发布版是 Windows GUI 程序、没有控制台——**编号对用户可见、对排查不可用**。本次能定位是靠网络实测绕过它。
- 改造一（日志）：`src-tauri/src/logging.rs` 同时写 stdout 与 `<应用数据目录>/enjoy.log`，超过 4 MiB 轮转为 `enjoy.log.1`（只留一代），打不开文件不阻止启动。初始化从 `main()` 移入 `.setup()`，因为路径要问 Tauri 要。
- 改造二（续传）：`src-tauri/src/update/download.rs` 自己传输——按 `Range` 续传，断了重连接着要剩下的一段；只要每次连接还能带来字节就继续，连续五次空手而归（退避 250 毫秒起、上限 2 秒）或连接次数触顶 1000 才放弃；20 秒读超时把半开连接从「挂住」变成「重连」；不设总超时，因为几十兆配慢链路时，能容纳快的那个的截止时间必然误杀慢的那个。接管的代价是校验：`src-tauri/src/update/verify.rs` 按插件同样的步骤自己验签（公钥与签名都是 base64 包着 minisign 的装甲文本，接受旧式签名），验不过整体拒绝并新增错误码 `update.verify_failed`（中英各一条），与 `update.download_failed` 分开。`DownloadTracker` 随之删除：它存在的理由是把插件回调的单块长度累加，而新回调给的已是累计值，其三条测试一并移除。
- 测试：`update/download_tests.rs` 用一个本地 TCP 服务器复现「先声明长度、发一半就断开」的连接，断言第二次连接带的是 `Range: bytes=60000-` 且拼出的字节与原文件逐字节相同；另有退避与放弃策略的纯函数用例、以及「服务器一个字节都不给」时会在 30 秒内放弃。`update/verify_tests.rs` 用 `ring` 现造密钥对做**正向**验证（照 minisign 的格式拼公钥与签名，含 trusted comment 的全局签名），并覆盖改过的载荷、另一把钥匙签的载荷、以及畸形字段三类拒绝路径——正向用例需要一把自己的钥匙，因此新增 `ring` 作为 dev-dependency。
