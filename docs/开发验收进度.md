## 2026-10-15 滚动条改由应用自绘（先跟着主题，再自己画）

- 起因：用户接着标题栏那条提出「滚动条的风格，在亮色主题和暗色主体下，也需要分别进行样式的区分」。第一版查到的根因是：滚动条由**引擎**画，而引擎问的是 `color-scheme`——主题切换写的是 `data-theme`，那个属性这个应用一处也没声明，于是它算作 `normal`、被引擎按亮色读：暗色主题下页面全暗、右侧那条滚动条还是白的（真窗口读数 `#FCFCFC` 轨道配 `#8B8B8B` 滑块）。按这个根因修的版本是两行声明（两个主题块各一次 `color-scheme`），读数也干净——但用户随即改主意：**「我希望滚动条是自己绘制的」**，并给了做法：一个类、按需挂、随主题变色、`!important` 强制覆盖。于是有了本文这一版。
- 做法：`.app-scrollbar` 一个类（`components.css`），谁滚谁挂；已经挂上的四处是页面滚动区（`ScrollViewport` 自己挂）、抽屉面板、下拉列表（`select` 的 `Content`）、表格的横向溢出。颜色取 `--muted-foreground`（静息）与 `--foreground`（悬停），两个 token 自己随 `data-theme` 翻，因此「自动随主题变色」在代码里就是这两行；指针改的正是 `background-color`，ADR 0038 那条「指针状态只许重画背景」照字面成立。车道是 `--scrollbar-width: 10px`，杆子用 2 像素透明边框内缩成 6 像素胶囊，两端箭头关掉。**不做通配规则**：车道（`scrollbar-gutter` 与 20 像素留白，`.scroll-viewport`）与画法（这个类）是两件事，要哪个挂哪个。
- **一条量出来的陷阱**：`scrollbar-color` / `scrollbar-width` 是标准属性，元素上有任何一个，引擎就丢掉它全部的 `::-webkit-scrollbar` 规则，`!important` 也拦不住——实测加一条 `scrollbar-color`，车道从 10 回到平台的 15、箭头也回来了。`check-tokens.mjs` 因此加了三条断言：`--scrollbar-width` 的值、暗色块不得重声明它、两个样式表都不许出现那两个标准属性（报错点名是哪个文件）。三条都做过红绿两向。
- 实测：验收页（无头 Chrome 155，1200×700）车道 **10**、内容宽 **1158**（上一版是 15 / 1153），杆子亮 `#64748b`、暗 `#9aa0aa`，轨道透明；悬停用 CDP 的 `Input.dispatchMouseEvent` 把指针移到那条上（无头实例里的合成事件，不碰本机桌面），杆子变 `--foreground` 的 `#edeef2`。四个挂点问过 DOM，页面、下拉列表、抽屉面板三处都带着类且车道解析为 10（表格那处没打开视图）。真窗口（WebView2 155，125%）读到同一组色 `#9AA0AA`，取证时临时把首页路由指到设置页、窗口压到 420 像素高（库是空的，空状态不溢出，那时根本不画滚动条），两处改动都已还原。
- `color-scheme` 的两行**留着**：滚动条不在它名下了（自绘），但 `canvastext`、表单控件的内部、样式表到位之前的画布底色仍在——`PageFrame.test.tsx` 记过的那次黑字 bug 就是它，注释随之改写（那句「这个应用从不设置 `color-scheme`」已不成立）。
- 文档：[ADR 0040](adr/0040-滚动条改由应用自绘.md)（新，两版过程、两版的读数与全部代价都在里面；第一稿未提交，直接改写，没有另立一条）；`docs/guides/列表与滚动.md` 的「滚动条配色」改成「滚动条自绘」；`docs/滚动条占位-资料核对.md` 补一节；基线 142 行那半句改（滚动条不再属于「引擎画的那一层」）；`docs/开发指南.md` 的节名索引随之改名。
- 门禁：`npm run check` 通过；四处类名加完之后重跑 `npm test`（超时放到 60 秒）86 文件 494 用例全绿——没有用例按类名做等值断言而被它撞到；另有 11 条 `onTaskUpdate` 的未处理错误（与 ADR 0039 记的同一类，一次也没变成失败用例）。
- 未覆盖的部分：**macOS 预期会变、但没有验**——WebKit 一旦给 `::-webkit-scrollbar` 写了尺寸就不再走覆盖式滚动条，`滚动条占位-资料核对.md` 里「传统 17 / 覆盖 0」两种模式可能并成一种，要跑一次 `scripts/check-scrollbar.swift`（两条命令各一次）才算数，本机是 Windows。**内容宽度变了 5 像素**：ADR 0019 与 ADR 0008 里那些读数是 15 像素那版量的，列数在常见宽度下不变但没有逐个宽度重数过。**真窗口里的悬停没看过**（要一只真的鼠标停在滚动条上），**表格横向滚动那处**也没打开过。
- **顺带收掉了一处既有漂移**（前两轮都只报未动）：`--native-scrollbar-width` 现在写了没人读（`ScrollViewport.tsx` 仍在量、仍在写），`guides/列表与滚动.md` 与 [ADR 0008](adr/0008-视频卡片的悬停动效与引入-Motion.md) 里仍在讲「补偿 = `max(0px, 20px - 原生槽宽)`」，而 `components.css` 从上一轮起就是平铺的 20 像素。自绘之后「原生槽宽」这个概念在这个应用里已经不存在了（车道是我们的 10 像素），于是这一轮把它收掉：`ScrollViewport` 里那段测量原生槽宽的效果（写 `--native-scrollbar-width` + `ResizeObserver`）删除——它从 ADR 0017 废掉虚拟滚动起就没有读者；`guides/列表与滚动.md` 的「滚动条占位与兼容处理」一节四处过期说法改成代码现在的样子（删掉的扣减公式、删掉的观察器、macOS 那两处读数）；`ThemeSetting.test.tsx` 里拿它当先例的那句注释跟着改。ADR 0008 的正文是历史记录，照旧不动。

## 2026-10-15 最大化按钮接回系统的贴靠布局

- 起因：用户接着上一条提出——最大化按钮悬停时没有其他应用那种 Windows 11 贴靠布局飞出菜单。第二条指令是「不要自己手搓样式实现，要去找怎么使用 tauri 提供的来激活」，并给了一个库。
- 先查了「tauri 提供的」到底是什么：`tauri` / `tao` / `tauri-runtime-wry` 三个 crate 的全部源码里 `HTMAXBUTTON` 一次不出现，没有配置项、没有 feature、没有命令；Tauri 唯一自己做的命中测试是 `undecorated_resizing.rs` 的八向缩放边框，不对外。**Tauri 真正提供的只有一个 `window.set_theme()`**——它让**原生**标题栏跟随应用主题，也就是「保留原生装饰就白拿贴靠布局」，而那要推翻 ADR 0039。用户选了插件。
- 做法：`tauri-plugin-snap-layout` 1.0.9（MIT）。它不子类化主窗口，而是造一个 `Static` 子窗口盖在按钮上、只给那个子窗口装子类，由子窗口回 `HTMAXBUTTON`——主窗口的消息链一个字节没动。这恰好是 Tauri 自己在无边框窗口上用的手法（探针列出的子窗口里就有 `TAURI_DRAG_RESIZE_BORDERS`）。它的四个依赖全都已经在树上，`Cargo.toml` 只多它自己一行。接线三处：`main.rs` 注册并 `button_id("window-maximize")`、能力文件加 `snap-layout:default`、`WindowControls.tsx` 给中间那颗按钮同一个 id。
- 悬停那一笔因此分成两处：Windows 11 上那个矩形被 shell 收走，webview 收不到鼠标消息、`:hover` 不触发，插件给按钮加一个 `.is-hovered` 类，`components.css` 里补一条 `#window-maximize.is-hovered`；按钮自己的 `hover:` 留着，它在 Windows 11 以下是活的那一条。那条 id 是两个语言之间的暗号，`check-seam.mjs` 加了一段守它（红绿两向实测过）。
- 实测：Win32 探针（不是合成输入）读到覆盖层是一个 46×32 的 `Static` 子窗口，距视口右缘 46 像素（正好一颗按钮宽，最右那颗关闭在它右边）、顶边与视口顶边齐平；子窗口 z 序里它在最上；`ChildWindowFromPointEx` 与系统级 `WindowFromPoint` 都命中它；`SendMessage(WM_NCHITTEST)` 回 **9 = `HTMAXBUTTON`**。门禁：`npm run check`、`cargo test` 210 项、`npm test` 86 文件 494 用例（超时 60 秒）、`fmt`、`clippy -D warnings` 全绿。
- 未覆盖的部分：**飞出菜单本身要真人把鼠标停上去看**——探针能证明的是「系统在那个点会问到这个窗口、而这个窗口答 `HTMAXBUTTON`」，这正是贴靠布局的全部触发条件，但「菜单真的弹出来」只有一只真的鼠标能证（本机鼠标被远程会话夺着，见既有记录）。

## 2026-10-22 媒体任务入队（#101）：扫描不再占住界面

- 起因：工单 #101 把「媒体任务迁入队列」。原来扫描、缩略图重建、单文件「刷新信息」抢同一个扫描槽：谁在跑谁占着，其余三个命令直接被拒；而占槽期间界面被一个不可关闭的进度模态框盖住，切空间、开详情、起刮削全都做不了。任务页那时只列插件任务，媒体任务不在其中，于是「跑着的这件事」在任务页里也看不见。
- 做法：三个命令改成写一行任务、立即返回任务 id，工作交给内核自己的队列拥有者（`tasks::Runner`）逐条认领，因此三者不并行但界面不被占住。暂停、继续与取消写在任务行上，再由拥有者带进正在跑的那一趟（`ScanControl::carry`）；任务行变更发 `task-changed` 事件并带任务 id。进度呈现从模态框换成页面内的一条状态条（`ScanStatusBar`）：进度、摘要、当前路径、暂停/继续/取消，窄窗口下不显示文件名。媒体任务写回它启动时的那个空间，于是空间锁（`space_change_gate`）与扫描槽一起删掉。安装闸门改成查任务表（`plugin IS NULL` 且非终态的行都算数），沿用既有错误码 `update.blocked.scanning`。
- 实测（本机，无真窗口）：Rust 464 项测试通过（新增 22 项，含命令层 13 项、队列 5 项、安装闸门 4 项），前端 624 项通过（98 个文件，新增状态条 6 项、改写页面 2 项）；`npm run check`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 全过。
- 四项验收：后台扫描不阻塞界面——命令入队即返回，状态条不盖内容，页面测试断言跑任务时页面仍可用且页面上没有对话框；结果写回原空间——任务行带空间 id，仓储测试断言写回的是发起它的那个空间；三个任务可暂停继续取消重试——动作先落行再由拥有者带进正在跑的那一趟，任务页的「继续」对运行中且带暂停请求的行同样可用；媒体任务在跑时安装被拒——安装闸门查整张任务表，既有错误码不变。
- 文档：基线三处（页面结构、空间闸门、处理流程与安装闸门）、界面原型四处（导航、空间切换器、§6 状态条、更新安装）、组件清单一处（`ScanProgress` 换成 `ScanStatusBar`）、[ADR 0012](adr/0012-空间-id-由调用方显式传递.md) 顶部与那一节、逐项完成审查一行。
- 未覆盖的部分：**真窗口没有点过**——状态条的实际观感、视频库与设置页「扫描」「建缩略图」两个按钮点下去的手感没有在真机验过；**更新安装闸门只走单元测试**，没有真机装过一次更新；**装更新期间新排入队列的任务会随退出丢掉**（查表与退出之间那道窄缝，工单定下的规则是「查表、拒绝」，没有另立闸门），这条已写进基线。
