# 滚动条占位资料核对

核对日期：2026-09-11。本文区分标准行为与项目实现建议，不代表已完成桌面端视觉验收。

## 已确认的标准行为

- `scrollbar-gutter: stable` 必须作用于实际滚动容器，属性不继承。传统滚动条模式下，当 `overflow` 为 `auto`、`scroll` 或 `hidden` 时，即使内容未溢出也会保留滚动条槽；它不负责让滚动条始终可见。[CSS 溢出规范](https://drafts.csswg.org/css-overflow-3/#scrollbar-gutter-property)、[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/scrollbar-gutter)
- 覆盖式滚动条直接绘制在内容上，`stable` 不为其预留空间。鼠标交互可改变覆盖式滚动条的外观和尺寸。规范明确说明，目前该属性没有约定覆盖式滚动条占位的解决方案。因此，不能把“未看到空白槽”直接判定为属性失效，也不能承诺 `stable` 会防止覆盖式滚动条遮住内容。[CSS 溢出规范](https://drafts.csswg.org/css-overflow-3/#scrollbar-gutter-property)
- `both-edges` 只是传统滚动条槽存在时在另一侧增加同宽槽，不能使覆盖式滚动条产生占位。[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/scrollbar-gutter)
- 根元素的 `scrollbar-gutter` 会应用到视口，但 `body` 上的该属性不会像 `overflow` 一样传播到视口。局部虚拟滚动应直接设置在虚拟列表使用的滚动元素上，不能只给外层或 `body` 添加声明。[CSS 溢出规范](https://drafts.csswg.org/css-overflow-3/#scrollbar-gutter-property)

## 系统与浏览器差异

- Safari 18.2 开始支持 `scrollbar-gutter`。WebKit 官方特别指出：覆盖式滚动条下该属性没有效果；macOS 可通过“系统设置 → 外观 → 显示滚动条 → 始终”切换为占空间的滚动条。[Safari 18.2 发布说明](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/)
- MDN 兼容数据记录：Chrome 94、Firefox 97、Safari 18.2 开始支持。判断嵌入式浏览器时，应检查运行时 `CSS.supports("scrollbar-gutter", "stable")`，不能用当前安装的 Chrome 是否支持推断桌面应用所用引擎是否支持。[MDN 兼容数据](https://github.com/mdn/browser-compat-data/blob/main/css/properties/scrollbar-gutter.json)
- macOS 的“根据鼠标或触控板自动显示”会依据输入设备决定滚动条是否隐藏：支持手势的设备通常在开始滚动前隐藏，否则显示。仅描述“用鼠标时发生”不足以证明是哪一种渲染模式，需要同时记录系统设置与运行时尺寸。[Apple 外观设置说明](https://support.apple.com/guide/mac-help/change-appearance-settings-mchlp1225/mac)
- 传统与覆盖式模式的选择、滚动条尺寸由浏览器和系统决定；`stable` 不保证切换系统模式时内容宽度完全不变。[CSS 溢出规范](https://drafts.csswg.org/css-overflow-3/#scrollbar-gutter-property)

## 项目实现与验收建议

1. 将 `overflow-y: auto` 和 `scrollbar-gutter: stable` 放在同一个实际滚动容器，确认父级高度约束正确，页面根节点不产生第二条滚动条。
2. 不支持该属性的引擎可用 `@supports not` 下的 `overflow-y: scroll` 作为传统滚动条回退：其目的在于始终预留原生槽。覆盖式模式仍然不占空间，这不是覆盖式占位方案。
3. 若产品要求覆盖式滚动条展开时也不能遮住内容，应另加明确的内容安全间距，并说明这属于应用布局策略，不是 `stable` 的效果。固定安全间距不能假设等于所有系统上的原生滚动条宽度；如补偿原生槽宽，应避免重复占位。
4. 虚拟列表的列数、内容宽度与行高测量应以占位后的可用内容尺寸为准；仅有有限挂载数量的组件测试不能证明布局没有横向挤压。
5. 真实桌面验收至少覆盖：空内容到溢出内容、传统滚动条与覆盖式滚动条、鼠标悬停展开、不同视频页面切换、窗口调整大小。记录滚动容器与卡片的实际宽度，不能仅凭 CSS 声明存在判定通过。

上述建议由已引用的标准行为推导；其中安全间距和兼容回退是工程选择，需要结合真实桌面窗口验证。

## 本次修正与实测

实际滚动容器仍采用 `stable`，共享 `ScrollViewport` 额外维护尾侧 20 像素安全区域：补偿内边距为 `max(0px, 20px - 原生槽宽)`。使用尺寸观察更新原生槽宽，虚拟网格扣除内边距后分列。该留白是应用策略，不是覆盖式模式下的 `stable` 效果。

通过 `scripts/check-scrollbar.swift` 在本机 macOS 26.5.1 的真实 `WKWebView` 中加载网页验收入口，使用进程级参数分别选择两种滚动条模式，结果如下：

| 模式 | 原生槽 | 补偿 | 内容宽度 | 页面根节点溢出 |
| --- | --- | --- | --- | --- |
| 传统 | 17 像素 | 3 像素 | 1,058 像素 | 无 |
| 覆盖式 | 0 像素 | 20 像素 | 1,058 像素 | 无 |

修正前的最小 WebKit 复现中，同一 600 像素容器只设置 `stable`，两种模式分别得到 583 和 600 像素内容宽度。模式差异已复现并通过实际页面验证补偿效果；没有声称已测试所有操作系统或物理鼠标悬停过程。
