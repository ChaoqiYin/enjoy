# 开发指南

本指南适用于所有贡献者和自动化代理。具体产品功能与软件设计参见[本地视频统一启动器开发基线](本地视频统一启动器-开发基线.md)，此处统一维护开发约束。

## 开发环境与命令

项目已配置前端和桌面开发、构建、静态检查及测试命令，具体命令见下文。环境及依赖版本遵循设计基线。

统一使用 npm 并维护锁文件；新增项目配置时，在本指南中记录经过验证的依赖安装、桌面开发、生产构建、静态检查和测试命令。引入可执行代码时，同步补充格式化和静态检查配置。

## 编码风格与命名

- TypeScript 使用两个空格缩进，Rust 使用四个空格缩进；配置自动格式化工具后统一由工具执行。
- React 组件和类型使用 PascalCase，TypeScript 函数和变量使用 camelCase，Rust 函数和模块使用 snake_case。
- 源码标识符和注释使用英文，面向用户的界面文案可使用中文；需国际化的文案按设计基线管理。

## 导入规则

- 禁止懒加载导入和动态 `import()`，包括通过 `React.lazy`、路由懒加载及其他封装间接执行的动态导入。
- 所有 `import`（含类型导入和副作用导入）必须使用静态声明，集中放在文件开头、业务声明和可执行语句之前。许可证注释及框架要求的文件级指令可位于导入之前。
- 禁止在函数、条件分支、回调或业务代码中间引入依赖，也不得通过 `require()`、动态模块加载器等方式绕过限制。
- 其他语言遵循同样原则：依赖声明置于文件或所属模块开头；Rust 的 `use` 放在所属模块顶部，不放在函数体内。
- 按外部依赖、内部模块和相对路径组织导入，类型导入明确标记。避免循环依赖，通过调整模块职责解决。

## 跨平台文件路径

- Node.js 开发脚本和构建配置统一使用 `node:path`：用 `join` 拼接路径片段，用 `resolve` 生成绝对路径，用 `dirname`、`basename`、`extname` 提取路径信息。文件路径不通过字符串拼接、分隔符替换或按 `/`、`\\` 拆分处理，也不为 macOS / Windows 编写两套拼接逻辑。
- ESM 模块位置通过 `fileURLToPath(import.meta.url)` 或 `fileURLToPath(new URL(..., import.meta.url))` 转为文件路径；依赖模块位置的路径以此为基准，再用 `node:path` 解析，避免依赖启动命令所在目录。
- 比较两个本机绝对路径时使用 `relative(base, candidate) === ''`，由 `node:path` 处理当前平台的分隔符、尾部分隔符和路径段归一化，不直接比较外部返回的原始字符串。外部输入先检查字符串类型和 `isAbsolute`；需要确认符号链接指向同一实际文件时，再用 `node:fs` 的 `realpath` 解析后比较。
- 默认使用当前平台的 `node:path` 行为；仅解析明确约定为 Windows 或 POSIX 格式的外部数据时使用 `path.win32` / `path.posix`。URL 使用 `URL` API，URL 路径、模块导入标识和工具配置中的固定路径格式遵循对应协议，不当作本机文件路径处理。
- 开发服务复用校验遵循上述规则：Vite 返回的根目录可能使用 `/`，在 Windows 上须通过 `node:path` 与本机目录比较；只接受同一项目目录且 PID 合法的服务。修改路径逻辑后，验证当前服务复用、带空格的路径及不同目录拒绝场景；跨平台运行结果须分别记录。

## 文件行数限制

- 单个文件不得超过 **500 行**，按物理行数计算，包含空行、注释和测试代码。
- 新增或修改文件均须满足限制；不得通过压缩代码、合并语句或删除必要说明规避限制。
- 接近上限时按业务职责拆分组件、服务、类型或测试模块，不按任意行数切割，也不将无关代码堆入通用工具文件。
- 文件生成流程也应遵守此限制。自动生成的依赖锁文件（`package-lock.json`、`Cargo.lock`）及 Tauri 生成的权限模式文件不受 500 行限制，必须由工具生成，不可手工压缩或拆分。源代码、测试与手写配置仍严格遵守限制。

## 架构与设计模式

- 遵循单一职责、高内聚、低耦合和依赖倒置原则，模块通过小而明确的接口协作，避免循环依赖和承担多种职责的巨型模块。
- 分离界面展示、应用流程、领域规则和基础设施访问。界面组件不直接承担数据库、文件系统或进程调用逻辑；领域规则不依赖界面框架和具体存储实现。
- 功能重合度高的部分优先抽离为公共组件进行复用。新增功能前先检查现有组件，优先复用或扩展，避免复制粘贴形成多份实现。
- 界面实现优先使用 daisyUI 现有组件，并通过组合或封装构建高阶组件，不优先从零使用 Tailwind CSS 编写组件。仅在现有组件无法满足需求时，使用 Tailwind CSS 补充布局、样式或实现必要的自定义组件。
- 重复的界面结构与交互抽为公共组件，重复的状态逻辑抽为共享 Hook，重复的业务能力抽为公共服务或模块。通过明确的参数和组合表达差异，避免堆叠条件分支形成职责混杂的万能组件。
- 复用应基于一致的业务语义和行为，不能仅因外观相似强行合并；公共能力放在各使用方共同依赖的模块中，不反向依赖具体页面。
- 根据实际变化点选择设计模式：使用适配器封装外部工具与平台接口，使用仓储封装持久化访问，存在可替换算法时使用策略模式。
- 通过构造参数或显式参数注入依赖，使核心逻辑可独立验证；避免隐藏的全局可变状态和隐式依赖查找。
- 设计模式必须解决具体的职责分离、依赖隔离或扩展问题。不要为了套用模式增加无实际用途的接口、继承层级或抽象工厂。
- 新增模块时明确职责、公开接口、依赖方向及错误处理边界；涉及产品架构变化时同步更新设计文档。

## 按钮样式

- 操作按钮默认使用 daisyUI 的 `btn btn-outline` 配合语义颜色，保留必要的尺寸和形状修饰。视频库与设置页的目录管理按钮统一复用 `DirectoryActions`，样式由组件固定管理，页面不覆盖颜色、尺寸或变体。减少无颜色修饰的默认灰色按钮。同类操作在页面、卡片和弹窗中保持一致。
- 添加、开始扫描、播放和重试使用 `btn-primary`；目录访问和清除筛选使用 `btn-info`；收藏及单视频缩略图重建使用 `btn-secondary`。目录管理区域采用下述统一主色规范。
- 移除类入口使用 `btn-error`，最终移除确认使用 `btn-error`；暂停使用 `btn-warning`，继续使用 `btn-success`。
- 关闭和取消使用 `btn-neutral`；顶部导航使用 daisyUI 的 `tabs tabs-border`，路由链接使用 `tab`，当前页增加 `tab-active text-primary`。保留导航链接语义及 `aria-current`，不使用操作按钮样式。
- 卡片及其他页面中的纯图标操作统一使用 `btn btn-outline btn-xs btn-square` 配合语义颜色，图标为 14 像素，成组间距为 `gap-1.5`；复用公共 `Tooltip`，保留无障碍名称、收藏选中态及禁用状态。视频详情中的操作复用同一 `VideoActions` 图标模式，目录条目的移除操作遵循同样规格。
- 视频库与设置页的“添加目录”“扫描”“建缩略图”保持相同的较大规格：`btn btn-primary btn-soft btn-md`、18 像素图标及 `gap-3`。文字已说明用途，不提供 `Tooltip` 或原生 `title` 提示，不随卡片按钮一起缩小。`LibraryHeader` 继续统一预留标题及操作槽高度。
- 其余有文字的操作按钮使用 `btn-sm`，若附带图标则使用 14 像素图标；设置页、弹窗、错误反馈和扫描控制保持相同规则。语义颜色适配亮色和暗色主题。

- 弹窗中的文字操作按钮统一使用 `btn btn-soft btn-md`，与页面目录操作保持一致；添加与确定使用 `btn-primary`，取消与关闭使用 `btn-neutral`，删除使用 `btn-error`，扫描暂停与继续分别使用 `btn-warning`、`btn-success`。按钮组使用 `items-center gap-3`，附带图标使用 18 像素；此规则优先于上述弹窗 `btn-sm` 约定。

## 通知

- 所有页面、设置保存、目录操作及启动失败统一使用浮动通知，不将错误信息直接插入页面容器占用布局空间。
- 所有通知复用公共 `Toast`，外观由类型决定。类型词表覆盖 `success`、`error`、`info`、`warning`，对应 daisyUI 原生 alert：亮色主题用实心的 `alert-{类型}`，暗色主题在其上叠 `alert-soft`。`dark` 变体在本仓库跟随 `data-theme`（见 `style.css` 的自定义变体），不是系统偏好。柔和配色用色调本身作文字色，压在亮色的近白底上只有 2.6:1 左右，故只在暗色保留。类型到配色、图标和 ARIA 角色的映射用查找表表达，组件内不按类型分支；词表可以包含暂无调用点的类型，但不为其创建组件。
- 倒计时画在通知外框自己的底边上，是一条通栏细线，不放进正文。正文里一条与内容等宽的横条读起来是「任务进度」，而通知报告的不是进度，是它自己的剩余时间；落到外框上，正文保持纯文字，收缩的线属于通知本身而不属于它的内容。这条线用外框自己的前景色（`bg-current`），因此亮色取该类型的 `-content`、暗色柔和主题取色调本身。它不是 daisyUI 的 `.progress`：`.progress` 用 `currentColor` 画填充、用同色 20% 画轨道，而实心通知的底色正是该色调；改画在底边上后连 `progress-{类型}` 也不需要了。细线靠一个 `absolute inset-0 overflow-hidden rounded-box` 的包裹层裁掉圆角，裁剪不能加在通知本体上——`overflow-hidden` 会连带吃掉关闭按钮的焦点轮廓。
- 配色类必须写成完整字面量，不得用模板拼接（如 `alert-${type}`）。Tailwind 只生成能看到字面量的工具类，拼接出来的类不会产生任何样式。
- 细线的收缩交给浏览器，不逐帧写宽度：整条线按通栏宽度绘制，用 `transform: scaleX()` 从 1 缩到 0，动画时长取剩余时间、缓动 `linear`、`fill-mode: forwards`（少了它会到期与通知消失之间弹回满宽），`@keyframes` 放在 `style.css`，只有时长与暂停随运行时变化。原先的写法是每个 tick 由 React 写一次宽度：3 秒的完成统计只走 30 步、每步约 15 像素，看到的是一级级台阶；而且每步都要等主线程，扫描刚结束时轮询、列表与缩略图正在占它，迟到的 tick 按时间戳一次性补上，台阶还会忽大忽小。`transform` 动画由合成器执行，主线程忙不影响它，也不再每步触发一次重排。暂停与计时器共用一个状态：悬停或聚焦时把 `animation-play-state` 置为 `paused`，线停在原处、移开从剩余线长处继续，与「悬停暂停、移开从剩余时间继续」是同一件事。不要因 `prefers-reduced-motion` 关掉它：这条线不是入场装饰，它表示通知还剩多久。
- `Toast` 只负责外层框架：容器、类型图标、关闭按钮、子节点插槽，以及给定时长时的倒计时与那条细线。正文（标题、说明、排查编号、重试按钮）及各自回调由调用方以子节点提供，因此通知组件不含只有部分类型成立的属性。业务错误由 `ErrorNotice` 把结构化错误翻译为子节点后交给 `Toast`。
- `error` 使用 `role="alert"`，其余类型使用 `role="status"`。错误通知不自动隐藏，保留重试和关闭操作，直到用户处置。保留本地化、按钮无障碍名称与免被读屏重复播报的处理。
- 是否自动关闭由调用方决定：传入 `autoCloseMs` 才倒计时，省略即常驻，不使用 `0` 或 `Infinity` 之类需要额外约定才能读懂的哨兵值。完成统计传 3 秒；统计含失败项时改为不传，转常驻，因为失败计数正是需要被读到、也最容易被计时器抢走的部分。判断该传什么的纯函数与「是否播报扫描完成」放在同一模块，二者同属「一次扫描完成如何对外反馈」这一职责。同一份统计里的「N 个目录当前不可访问」只参与「是否播报」，不参与时长判断：它是本次扫描范围的一项事实，统计的是仍然存在、本次却列不出内容的配置目录（整条目录已不存在的情形按其中的视频都已消失清理，不进这一项），不是要用户处置的失败，因此不延长停留时间。
- 倒计时在鼠标悬停或键盘聚焦时暂停，移开后从剩余时间继续而不是重新计时；焦点在通知内部控件之间移动不解除暂停。给定时长时显示随剩余时间收缩的细线，整条指示器必须 `aria-hidden`：暴露出来的倒计时会让读屏反复播报一个用户没有要求听的计时器，这也是不用 `<progress>` 的原因之一。指示器画在哪、怎么取色见上一条。
- 非错误通知全局只保留最新一条：新的出现时先前那条被关闭，且关闭必须真正调用它的 `onClose`。通知的可见性由其所属方持有的状态决定，只做视觉隐藏会在下次渲染时把同一条重新挂出来。错误通知豁免：既不顶掉别的通知，也不被别的通知顶掉，多条错误继续堆叠。同一状态槽位的内容被替换（连续两次扫描完成）时不得走互斥路径关闭「旧通知」——该槽位的关闭回调是无条件清空的，在写入新值之后调用它会清掉刚写入的内容。这类替换以重新挂载的形式到来（开始新操作时先清空完成统计，下一次完成再写入），通知因此从完整时长重新计时；互斥只作用于不同来源的实例。
- `useNotificationHost` 将通知通过 Portal 挂到右上角 `toast toast-top toast-end` 容器，多条错误在同一容器堆叠；非错误通知的互斥协调也在宿主一侧，宿主因而最多持有 1 条非错误通知加 N 条错误通知。宿主按**位置**注册：同一位置共用一个容器，位置与宽度写在容器上，由调用方选择用哪个位置——通知用右上角（`end`），短提示用顶部居中（`center`，见「短提示」一节）。存在原生对话框时，宿主移入当前打开的对话框，关闭后回到页面根部，避免通知被顶层弹窗遮挡或无法操作。
- 通知出现、关闭、切换语言或重试不得推动标题、筛选栏和视频内容；卸载时清理宿主及观察器。
- 视频详情复制路径的结果与通知分处两地：成功是顶部居中的短提示，失败是右上角常驻的错误通知。这不是疏忽，两者的区别见「短提示」一节。

## 短提示

- 短提示用于**动作的结果用户看不见**的情形：点击已经生效，但界面上没有任何东西因此改变，不给提示这一下就像没点。全应用目前只有一处——视频详情复制路径，剪贴板不可见，因此它是唯一的调用点。结果本身看得见的动作不需要它：播放与打开所在目录由系统窗口弹出确认，收藏由心形填充与 `aria-pressed` 确认，移除索引后卡片消失，添加目录后列表项就地出现，切换主题整页变色。判断一个新动作该不该加提示，依据是它的结果可不可见，不是它有没有被点击。
- 短提示**不是通知**，不共用通知的任何部件，也不进入「非错误通知全局只保留最新一条」那条互斥：它与正在显示的完成统计可以同时在屏，各自独立。二者的区别是**要求**而不是外观——通知是要读、要处置的信息，短提示只回答「刚才那一下生效了」。同一个动作的成功与失败因此分处两地，用户对两者的义务不同，位置不同是刻意的。
- 位置是顶部水平居中（`toast-center`，不是屏幕正中央），宽度按内容收缩（容器 `max-content`，上限 `min(20rem, 90vw)`）。居中是为了离视线近，不是为了打断；因此时长只有 1 秒，也没有倒计时细线——一条 1 秒内排空的线是闪烁而不是信息。外观用**不带色修饰**的 `alert`（底色 `base-200`、文字 `base-content`），这是 daisyUI 设计好的中性配对，亮暗两主题都成立，不需要通知那套 `dark:alert-soft` 修正。部件只有一个实心对勾图标加一句话，没有关闭按钮，也没有类型词表——这类提示只有一种语气。
- 短提示必须**静默**：整块 `aria-hidden`，不使用 `role`。它没有可供读屏用户处置的内容，播报一次「已复制」也不比剪贴板本身多给任何信息。代价明确接受：这一秒内点到它，既不会有结果也不会有播报。
- 短提示**要吞掉落在它矩形内的点击**，而不是放行给被它盖住的控件——放行会让用户点中一个自己看不见的按钮。这是定位元素的默认行为，**不要为此加 `pointer-events-none`**。由此得到一条硬约束：承载它的容器宽度必须恰好等于可见内容，顶部居中容器的 `max-content` 不能省，也不能沿用通知容器那行 `w-[min(32rem,100vw)]`，否则会在提示两侧各多吞一块看不见的空白。被吞掉的那次点击不产生任何副作用，也不关闭提示。
- 入场动画要关掉：daisyUI 给 `.toast > *` 加了 0.25 秒的 `scale` 与 `opacity` 动画，对 3 秒的通知无妨，对 1 秒的短提示要吃掉四分之一的生命，用 `animate-none` 盖掉。工具类能压住 daisyUI 组件类：后者的层嵌在 `utilities` 内部，Tailwind 工具类落在更深的层。
- 停留时长由 `Hint` 自己持有（`HINT_MS`），因为它是一条与内容无关的固定规则，不像完成统计那样要按本次扫描有没有失败项分岔。状态仍由应用级 `useLibrary` 持有、由页面框架渲染，因此复制后立刻关闭详情抽屉不会把提示一并带走——它所属的是这次复制，不是弹出它的那个组件。
- 剪贴板拿到的是界面显示的那条路径，即经 `displayPath` 处理后的形式，不是索引里存的原样字符串。两者指向同一个文件，但用户要的是眼前这一条。
- 验证宿主按位置注册（短提示与通知各占一个容器、互不干扰）、静默（无 `role`、无 `data-notice-countdown`、无按钮）、1 秒后自动关闭且只关一次、`animate-none` 生效，以及短提示出现时正在显示的完成统计**不被关闭**。
- 验证页面外渲染、多错误堆叠、关闭和重试回调、对话框开启/关闭、自动关闭与悬停/聚焦暂停、倒计时指示器的动画与静默、非错误互斥与错误豁免，以及现有语言切换和未知错误回退测试。测试倒计时须使用假定时器，并在每个用例后先卸载再恢复真实定时器；仓库未开启全局注入，`afterEach` 中的顺序不能颠倒。jsdom 不执行动画，用例只能钉住细线声明的动画（时长、缓动、`fill-mode`、暂停态）以及「时间流逝时没有任何一步被写进去」；细线真的在走、悬停真的停在原处、移开真的从剩余处继续，仍须在真实引擎里验一次。
- 驱动通知必须用 `focusin`/`focusout` 与 `mouseover`/`mouseout`：React 把 `onFocus`/`onBlur` 接在原生 `focusin`/`focusout` 上，并由 `mouseover`/`mouseout` 合成 `onMouseEnter`/`onMouseLeave`，因此 `focus`、`blur`、`mouseEnter`、`mouseLeave` 四类事件不会触发任何处理函数，测试会静默通过而什么都没测到。同理，不要在假定时器启用期间使用异步等待查询。

## 下拉选择框

- 按 daisyUI 官方结构将 `select` 类直接加在原生 `<select>` 上，由组件负责边框、箭头、焦点与禁用样式；不把 `select` 类放在外层标签后再对内部控件设置 `border-0` 或 `outline-none`。
- 带前置图标时，外层仅负责定位；装饰图标设置 `aria-hidden` 与 `pointer-events-none`，控件通过内边距留出图标位置。可访问名称设置在实际 `<select>` 上。
- 原生选项菜单的外观受浏览器与系统影响，不通过破坏标准控件结构强行模拟。官方参考：https://daisyui.com/components/select/。

## 路由与页面组合

- `App` 负责应用级提供者、全局顶部导航及路由配置；导航下方通过 React Router 渲染 `src/pages/` 中的独立页面。页面内容由页面组件组合，不在 `App` 内按路径条件拼装。
- 视频库、收藏、最近播放页面分别嵌入 `LibraryHeader`，通过参数适配标题、操作按钮和筛选状态；共同行为复用 `useVideoPageView`、`VideoPageContent` 和 `PageFrame`。设置页单独组合自身内容。
- `LibraryHeader` 的标题与操作插槽统一设置最小高度，无操作按钮时仍保留空插槽；桌面及窄屏下，同一窗口宽度的页面切换应保持标题区、筛选栏和视频数量的纵向位置一致。
- 共享的查询、扫描及事件订阅由应用级 `LibraryProvider` 持有；页面消费上下文，不重复调用 `useLibrary` 创建订阅。页面自身的菜单和弹窗状态随页面卸载清理。
- 新增或调整路由后，验证直接访问、导航切换、对应页面操作入口和状态保留策略；未知路径明确回到视频库。

## 日志与故障排查

运行时诊断同时写 stdout 与 `<应用数据目录>/enjoy.log`（Windows 上是 `%APPDATA%\com.enjoy.launcher\enjoy.log`，与 `enjoy.db` 同级）。日志由 `src-tauri/src/logging.rs` 打开：超过 4 MiB 时轮转为同目录的 `enjoy.log.1`，只保留一代；打不开文件不阻止启动，退回只写 stdout。`RUST_LOG` 仍可覆盖级别，默认 `info`。

界面上的错误提示只显示业务文案与一个排查编号（形如 `err_1756000000000_2`），编号背后的原文只在这份日志里——`AppError::new` 会写一行 `tracing::error!`，带 `error_id`、`code` 与 `diagnostic`。拿编号在这份日志里搜，就能看到真实原因。发布版是 Windows GUI 程序、没有控制台，这个文件因此是唯一能看到它的地方。

新增失败路径时确认它能被这个编号查到：错误走 `AppError`，把底层原因作为第二个参数传进去（`AppError::new(code, source)` 接受任何 `Display`），不要只写一个码。

## 发布

自动更新仅面向 Windows 发布。发布由标签触发：改 `package.json`、`tauri.conf.json` 和 `Cargo.toml` 三处版本号（`npm run check` 强制它们一致），提交后打 `vX.Y.Z` 标签并推送。`.github/workflows/release.yml` 在 `windows-latest` 上构建 NSIS 安装包、签名并生成 `latest.json`，创建为**草稿** release；核对产物后再手动发布，`releases/latest` 从那时起才指向它。因此首个版本必须手动安装，自动更新自第二个版本起生效。

构建机需要两个仓库 secret：`TAURI_SIGNING_PRIVATE_KEY` 放私钥内容，`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 放它的口令。私钥只生成一次——`npm exec tauri signer generate -- -w ~/.tauri/enjoy.key`——公钥内容写入主配置的 `plugins.updater.pubkey`。**私钥丢失后，已发布的客户端永远无法再收到更新**：它们带着旧公钥，签不出能被接受的新包。私钥须离线备份并排除在版本库之外。

内置媒体工具不入库，流水线从仓库 `ffmpeg-tools` 标签的发布附件取 `ffmpeg.exe` 与 `ffprobe.exe`。该标签的附件需先手工上传一次，之后每次发布复用同一对，发布产物因此可复现。

## 独立网页验收

运行 `npm run dev -- --host 127.0.0.1`，在浏览器打开 `http://127.0.0.1:5173/acceptance/web-acceptance.html`。此入口使用同一 React 页面、Tauri 官方模拟通信及固定测试数据，适合页面框架、弹层和错误文案验收；不连接真实数据库，也不替代 Rust 或系统集成测试。生产构建仍仅使用 `frontend/index.html`。

该入口会把夹具里那 36 条视频渲染进真实网格，因此依赖真实数据的走查（筛选、排序、卡片与详情）也可以在这里做。此前记录的「视频列表不加载」（#23）在 2026-09-26 已不成立，但恢复原因未追溯——打开后列表若是空的、停在「正在读取视频库…」，那就是老毛病回来了，此时它又不能作为验证手段。它走桩通信，验的是界面行为，后端与系统集成仍由 Rust 测试和桌面端承担。

可在浏览器控制台执行 `window.enjoyAcceptance.setScan('processing')`、`setScan('paused')` 或 `setScan('cancelled')`（后两者同样通过 `window.enjoyAcceptance` 调用），发送对应扫描状态。`window.enjoyAcceptance.setUpdate('available'|'ready'|'none'|'unsupported')` 覆盖检查结果能渲染的四种形状，须先点一次「检查更新」。

更新的下载流程也可以在这里走：夹具的 `install_update` 把命令的 promise 挂住并推一条进度，直到 `control_update` 按暂停或取消把它兑现——真实下载只在结束时作答，不这样做的话，一段只在传输运行时才出现的暂停与取消按钮根本走不到。因此点「下载」会停在进度上，此时可按「暂停下载」看到暂停态与「继续下载」，按「取消下载」则清空。第二次「下载」开的是新的一次传输而不是接着上一次的断点，这一点与后端不同。

点击播放固定返回系统打开失败业务错误，以验证本地化提示和重试入口。当前夹具只支持验收所需命令，未支持的命令会报错，不应据此判断生产后端失败。


## 标志与应用图标

原图及 1024 像素图标源图放在 `assets/brand/`，页面仅使用 `frontend/public/assets/generated/` 内裁切后的标志资源，避免原图留白影响导航尺寸。执行 `python3 scripts/generate-brand-assets.py` 生成页面标志和 1024 像素图标源图；该脚本依赖 Python Pillow，仅生成资源时需要。

再运行 `npx tauri icon assets/brand/app-icon.png --output /tmp/enjoy-brand-icons`，将生成目录中的 `32x32.png`、`128x128.png`、`128x128@2x.png`、`icon.png`、`icon.icns`、`icon.ico` 复制到 `src-tauri/icons/`。配置中的图标列表包含 macOS、Windows 和 Linux 使用的格式。运行 `npm exec tauri build -- --debug --bundles app` 验证 macOS 应用包；本次构建已确认 `Contents/Resources/icon.icns` 存在。


## VS Code 启动

在 VS Code 的“运行和调试”下拉菜单选择配置并按 F5：

- `前端开发：Vite`：执行 `npm run dev`，启动 Vite 开发网页服务，默认地址为 `http://127.0.0.1:5173/`。
- `桌面端开发：Tauri`：执行 `npm run desktop`，启动 Tauri 开发环境。Tauri 会依据 `tauri.conf.json` 的 `beforeDevCommand` 检查并启动或复用 Vite 服务，再由桌面窗口加载 `devUrl`。

这两个配置只负责启动开发脚本，不负责启动 Chrome 或打开网页验收入口。网页和桌面端可以同时运行并共享同一个 Vite 服务；需要停止共享服务时执行 `npm run dev:stop`。打包时执行 `npm exec tauri build`，页面从 `frontendDist` 指定的内置 `frontend/dist` 加载。


## 视频内容虚拟滚动

修改视频库、收藏、最近播放的布局或渲染逻辑时，必须遵守以下约束。产品范围参见[开发基线](本地视频统一启动器-开发基线.md)，滚动条的标准行为及兼容性依据参见[滚动条占位资料核对](滚动条占位-资料核对.md)。

### 滚动区域边界

- 应用采用固定视口高度，父级通过 `min-height: 0` 等约束将剩余高度交给内容区，页面根节点不产生纵向滚动条。
- 全局导航、页面标题、操作按钮、筛选工具栏及视频数量放在滚动容器外。仅下方视频网格滚动，视频数量不得随内容滚出视野。
- 设置页内容和空状态使用各自的滚动容器。局部滚动不得带动整个窗口或形成重复的纵向滚动区域。

### 虚拟渲染与测量

- 单个视频卡片统一复用 [VideoCard](../frontend/src/features/library/VideoCard.tsx)，页面不复制卡片布局或直接处理滚动范围。
- 通用虚拟集合逻辑统一复用 [useVirtualCollection](../frontend/src/shared/useVirtualCollection.ts)：接收数据、稳定标识、列数和估算行高策略，返回可见行数据、偏移、总高度、上下占位和测量接口。Hook 不依赖路由或视频领域，内部统一处理尺寸观察及缓冲行；展示组件按返回的数据渲染。
- 视频数据读取由应用级 `useLibrary` 统一执行，页面通过 `useVideoPageView` 复用筛选、排序及滚动重置标识。筛选与目录选项按数据变化缓存；各页面只传入集合标识，不重复维护分页、请求或滚动状态。
- 所有视频页面仅使用卡片网格，不提供列表视图或其切换按钮；统一复用 [VirtualVideos](../frontend/src/features/library/VirtualVideos.tsx)，使用 `@tanstack/react-virtual`，仅挂载可见行及前后各 3 行缓冲；挂载数量应随可见区域大小变化，而非随视频总量增长。缩略图随可见项挂载，保留延迟加载。
- 虚拟网格内容统一复用 [VirtualGrid](../frontend/src/shared/VirtualGrid.tsx)，列数断点和 20 像素行列间距集中维护于该模块的 `virtualGridLayout`。内容宽度达到 800 像素时每行 4 个，600、400 像素分别为 3、2 个，更窄为 1 个；页面不单独定义网格排版。同处还集中维护卡片边框与行内与宽度无关的那部分高度（`cardBorder`、`rowFooter`）：卡片高度等于图片（按列宽减两边框后的 16:9）加上这部分，估算行高据此拼出，卡片盒子的尺寸一变就要重新量。<strong>估算值必须与实测值相等，否则会看见行在跳</strong>——实测读的是 `offsetHeight`（整数），所以估算也要取整；差一点不是报错，而是首屏按错误的行高排一遍，实测回填时第一排以下的每一行都移动一个差值。
- 网格按实际可用内容宽度分列。计算宽度时扣除原生滚动条槽及容器内边距，不直接将窗口宽度或未扣除内边距的 `clientWidth` 用作内容宽度。
- 估算行高只用于初始化，实际行高必须测量。窗口尺寸、列数或语言变化后重新测量，兼容长文件名、按钮换行和缩略图状态变化，避免重叠、裁切及异常行间空白。
- 使用稳定的视频标识作为虚拟项身份；按网格行分组时使用该行首个视频的标识。通过网格总高度和虚拟行偏移确保末项可达。
- 虚拟滚动的顶部偏移只包含滚动容器内部的前置内容。视频数量已在容器外，不能再计入偏移；移动前置元素时同步更新偏移与测试。
- 切换页面、筛选条件或排序时重置内容滚动位置。滚动时关闭右键菜单；播放、收藏、详情及键盘等交互在虚拟化后仍须有效。
- 当前视频索引一次读取，用于本地筛选和排序；虚拟滚动优化的是界面节点及缩略图挂载，不代表后端分页或索引按需读取。引入分页时另行更新数据接口与设计基线。

依赖通过 `npm install @tanstack/react-virtual --registry=https://registry.npmmirror.com --no-audit --no-fund` 安装并更新锁文件。

## 滚动条占位与兼容处理

- 视频内容、空状态及设置页统一复用 [ScrollViewport](../frontend/src/shared/ScrollViewport.tsx)。将 `overflow` 与 `scrollbar-gutter: stable` 设置在实际滚动元素上；只给外层或 `body` 设置该属性不能替代局部容器配置。
- `stable` 为传统滚动条预留原生槽，但不会为 macOS 覆盖式滚动条占位，`both-edges` 也不解决覆盖式占位。不能仅凭属性声明或 `CSS.supports` 返回成功判定问题解决。
- 共享样式位于 [style.css](../frontend/src/style.css)。尾侧安全区域以 20 像素为目标，补偿内边距按 `max(0px, 20px - 原生槽宽)` 计算。原生槽宽为容器 `offsetWidth - clientWidth - 左右边框宽度`，由 `ResizeObserver` 观察尺寸变化并更新。
- 传统模式使用原生槽加差额补偿，覆盖模式补足安全留白，避免滚动条展开遮挡内容。原生槽超过 20 像素时保留完整系统槽宽，补偿为零；20 像素是应用布局策略，不是所有平台的原生滚动条宽度。
- 占位规则由共享容器统一维护，各页面不另加重复的固定右内边距。观察器卸载时必须清理，补偿更新不得造成持续的尺寸观察循环。
- 不支持 `scrollbar-gutter` 的引擎通过 `@supports not` 回退为 `overflow-y: scroll`。该回退仅解决传统滚动条槽，覆盖式模式仍需安全留白。
- 应用不得通过修改用户系统滚动条偏好解决布局问题。

## 滚动功能验证

修改上述逻辑后，运行 `npm run build`、`npm run check` 和 `npm test`。虚拟滚动回归测试使用 1,203 条视频数据，覆盖网格的有限挂载、滚动替换可见项、末项可达及筛选后位置重置。模拟布局测试不替代真实窗口布局验证。

真实窗口验收须覆盖：空内容与溢出内容切换、不同视频页面切换、窗口缩放、长文件名、传统与覆盖式滚动条、鼠标悬停展开。记录容器和内容的实际宽度，检查固定区域不移动、内容不被遮挡、卡片无重叠及异常空白、根节点不产生额外滚动。无法完成的场景须明确说明。

macOS 下先启动 `npm run dev`，再分别执行以下命令。脚本用原生 `WKWebView` 加载实际网页验收入口，断言原生槽与补偿间距之和为 20 像素，并输出内容宽度。滚动条偏好仅通过测试进程启动参数传入，不修改用户系统设置。

- `swift scripts/check-scrollbar.swift http://127.0.0.1:5173/acceptance/web-acceptance.html -AppleShowScrollBars Always`
- `swift scripts/check-scrollbar.swift http://127.0.0.1:5173/acceptance/web-acceptance.html -AppleShowScrollBars WhenScrolling`

既有本机验证中，两种模式均测得内容宽度 1,058 像素；传统模式槽宽 17 像素、补偿 3 像素，覆盖模式槽宽 0 像素、补偿 20 像素。该数值是当时窗口尺寸下的证据，不是所有窗口的固定宽度要求。脚本的 20 像素断言适用于原生槽不超过 20 像素的环境；更宽的系统槽按原生宽度验收。该检查不替代物理鼠标接入和悬停展开的人工检查。
