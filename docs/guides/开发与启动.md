# 开发与启动

《开发指南》第 1 份，共 6 份；索引见[开发指南](../开发指南.md)。

## 开发环境与命令

项目已配置前端和桌面开发、构建、静态检查及测试命令，具体命令见下文。环境及依赖版本遵循设计基线。

统一使用 npm 并维护锁文件；新增项目配置时，在本指南中记录经过验证的依赖安装、桌面开发、生产构建、静态检查和测试命令。引入可执行代码时，同步补充格式化和静态检查配置。

## VS Code 启动

在 VS Code 的“运行和调试”下拉菜单选择配置并按 F5：

- `前端开发：Vite`：执行 `npm run dev`，启动 Vite 开发网页服务，默认地址为 `http://127.0.0.1:5173/`。
- `桌面端开发：Tauri`：执行 `npm run desktop`，启动 Tauri 开发环境。Tauri 会依据 `tauri.conf.json` 的 `beforeDevCommand` 检查并启动或复用 Vite 服务，再由桌面窗口加载 `devUrl`。

这两个配置只负责启动开发脚本，不负责启动 Chrome 或打开网页验收入口。网页和桌面端可以同时运行并共享同一个 Vite 服务；需要停止共享服务时执行 `npm run dev:stop`。打包时执行 `npm exec tauri build`，页面从 `frontendDist` 指定的内置 `frontend/dist` 加载。

## 前端工具链

网页入口、源码、静态资源、Vite / Vitest / TypeScript 配置及网页验收夹具统一位于 `frontend/`。Tauri 原生工程位于同级的 `src-tauri/`。根目录保留共享 npm 工具链与统一命令，以下命令均在仓库根目录执行。

统一使用 npm 11，提交 `package-lock.json`。已验证：

- `npm install --registry=https://registry.npmmirror.com --no-audit --no-fund`：安装依赖（当前环境官方源出现 TLS 错误，使用镜像源成功）。
- `npm run build`：TypeScript 检查及 Vite 生产构建，输出到 `frontend/dist`。

已配置 `npm run dev`（Vite）、`npm run desktop`（Tauri 开发）与 `npm run format`（Prettier）；桌面运行及界面交互仍需进一步验证。前端 API 类型集中于 `frontend/src/shared/api.ts`，页面后续通过该模块调用 Rust 命令，避免自行拼装协议。

目录选择采用 Tauri 官方 `tauri-plugin-dialog`，前端使用对应插件包。主窗口权限配置位于 `src-tauri/capabilities/main.json`，逐条列出界面真正用到的授权：核心默认集、订阅事件（含「有人要关窗」与「窗口是否最大化」这两条后端消息）、对话框、在文件管理器中显示文件、打开网页，以及**一条窗口授权**（`core:window:allow-start-dragging`，见下）；目录扫描仍由 Rust 命令执行。**界面不碰自己的窗口**：关闭窗口用不用得着问用户、要不要拦下、由谁来关，都是后端一件事（`src-tauri/src/closing.rs`，[ADR 0015](../adr/0015-关窗的决定在后端而界面只回答确认.md)），界面只负责把问题画出来、把答案用一条命令发回去。自绘标题栏那三个按钮同样走应用自己的命令（`commands/window.rs`，[ADR 0039](../adr/0039-窗口标题栏改由应用自绘.md)），一次也不调 `@tauri-apps/api/window`；**唯一一条窗口授权是拖动区要的**，而它不是界面的调用——Tauri 注入的脚本读元素上的 `data-tauri-drag-region`、自己发 `plugin:window|start_dragging`，所以 `check-permissions.mjs` 读不出它，那条权限由脚本里单独一段源码扫描来守。添加目录弹窗使用原生 HTML 对话框管理焦点，目录列表在添加流程内支持去重和移除；扫描范围由后端读取已保存的目录决定，前端不再组合目录列表，因此去重只属于添加这一步。

## 窗口何时出现

主窗口在 `src-tauri/tauri.conf.json` 里以 `visible: false` 创建，**后端不再亮它**：`main.rs` 的 `.setup()` 只做日志与 `initialize_backend`，初始化失败走 `i18n/native.rs` 的 `startup_failure`（一个独立的 `startup-error` 窗口加系统对话框，不依赖主窗口，所以后端故障仍然是屏幕上看得见的）。主窗口由前端在「要画的东西已经画上去」之后经 `show_window` 命令亮出：`frontend/src/shared/WindowReveal.tsx` 用一个 `useLayoutEffect` 调 `windowApi.show()`，成功与启动失败**两条**渲染路径都要经过这个组件，否则窗口根本不会出现，被藏起来的失败通知也就等于没告诉用户。

**信号取的是「React 已提交」，不是「主题已读出」。** 读主题只是通往「画好」的一步；在它之后亮窗，开发模式下样式表（随 `style.css` 模块导入）还没到，屏幕上仍是无样式的白底。所以窗口期从「前端读偏好的全长」缩到「WebKit 首次合成的那一缝」——**实测约 0.18–0.25 秒**（见 ADR 0037 §二），短了一个量级，但没有消失。启动加载画面随之删除；ADR 0037 里记着它试过什么、量到什么、为什么撤。

**标题栏也在这条链上。** 窗口装饰已关闭（`tauri.conf.json` 的 `decorations: false`），顶上那条 32px 由界面自己画（`frontend/src/app/TitleBar.tsx`，[ADR 0039](../adr/0039-窗口标题栏改由应用自绘.md)），于是它与页面其余部分**同一次提交**落到屏幕上：不需要为它单独等什么，也不会比内容早半拍出现，主题切换照旧一行 token 就能带上它。代价是这一版没有任何原生标题栏可以兜底——`show_window` 之前，窗口连一条边也没有。

三条要记住的代价：

- **没有兜底。** 前端若在 `show_window` 之前挂掉（模块加载失败、启动期未捕获的错），窗口永远不会出现，屏幕上只剩 Dock 里一个没有窗口的进程，唯一出路是从 Dock 退出重开。后端失败仍然可见，**只有前端失败是屏幕静默的**。
- **没有窗口内的调试入口。** `open_devtools()` 现在在 `show_window` 里（保住原先「先 show 再 devtools」的顺序），而 macOS 的 inspector 停靠在 webview 内部——窗口没出现时它同样不可见。debug 构建下排查「前端没起来」要走 **Safari 的「开发」菜单**（debug 构建把 web view 设成可检查）或日志文件，不能指望窗口里那个面板。
- **那一缝的颜色管不了。** 窗口自身的底色（`tauri.conf.json` 的 `backgroundColor`）本来是用来兜住它的，**实测做不到**：把值改成屏幕上不可能自然出现的 `#FF00FF` 重测，整窗品红占比 **0.00%**（那次读数是在装饰尚未关闭时取的，所以「整窗」里含 macOS 那个当时的原生标题栏）。配置链每一环都通（`tauri-runtime-wry` → tao → `ns_window.setBackgroundColor`），落点却被盖住——那一缝显示的是 WKWebView 自己合成的结果，而 wry 那个本该让窗口背景透出来的 `drawsBackground = false` 是私有 KVC key。所以配置没有保留，那一缝是一层随系统外观的默认底色。否定实验的读数见 ADR 0037 §二。

界面画哪个主题，由 `initializeTheme()` 在渲染前读一次决定：读的是**已存偏好**（`readTheme()` → `get_settings`，与设置页同源，所以页面选中什么启动就画什么），读不出才落回 `index.html` 声明的那层深色。它曾经读的是 `localStorage['enjoy-theme']`——一个自从偏好搬到后端（`1abd1bb`，2026-09-14）就再没人写的键，于是无论设置页选了什么，启动一律画暗色。见 [ADR 0036](../adr/0036-启动时的主题改读已存偏好与设置页同源.md)。

## 日志与故障排查

运行时诊断同时写 stdout 与 `<应用数据目录>/enjoy.log`（Windows 上是 `%APPDATA%\com.enjoy.launcher\enjoy.log`，与 `enjoy.db` 同级）。日志由 `src-tauri/src/logging.rs` 打开：超过 4 MiB 时轮转为同目录的 `enjoy.log.1`，只保留一代；打不开文件不阻止启动，退回只写 stdout。`RUST_LOG` 仍可覆盖级别，默认 `info`。

界面上的错误提示只显示业务文案与一个排查编号（形如 `err_1756000000000_2`），编号背后的原文只在这份日志里——`AppError::new` 会写一行 `tracing::error!`，带 `error_id`、`code` 与 `diagnostic`。拿编号在这份日志里搜，就能看到真实原因。发布版是 Windows GUI 程序、没有控制台，这个文件因此是唯一能看到它的地方。

新增失败路径时确认它能被这个编号查到：错误走 `AppError`，把底层原因作为第二个参数传进去（`AppError::new(code, source)` 接受任何 `Display`），不要只写一个码。
