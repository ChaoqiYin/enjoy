# 列表与滚动

《开发指南》第 4 份，共 6 份；索引见[开发指南](../开发指南.md)。

## 视频列表布局与渲染

修改视频库、收藏、最近播放、共享的布局或渲染逻辑时，必须遵守以下约束。列表的条数、筛选、排序与分页见[后端分页决策](../adr/0016-后端分页承担筛选排序与分页.md)，三态视图见[列表三态视图决策](../adr/0017-列表三态视图与废除虚拟滚动.md)，滚动条的标准行为及兼容性依据参见[滚动条占位资料核对](../滚动条占位-资料核对.md)。

### 滚动区域边界

- 应用采用固定视口高度，父级通过 `min-height: 0` 等约束将剩余高度交给内容区，页面根节点不产生纵向滚动条。
- 全局导航、页面操作按钮、筛选工具栏及视频数量放在滚动容器外。仅下方视频列表滚动，视频数量不得随内容滚出视野。
- 设置页内容和空状态使用各自的滚动容器。局部滚动不得带动整个窗口或形成重复的纵向滚动区域。

### 列表渲染

- 列表一次只取一页。筛选、排序与分页都由后端执行（[ADR 0016](../adr/0016-后端分页承担筛选排序与分页.md)），每页 24 条（`features/library/listing.ts` 的 `PAGE_SIZE`），页面不持有全量数据，也不在本地筛选。
- **不引入虚拟滚动**。一页只有 24 条，浏览器自己排布即可。`@tanstack/react-virtual` 及其估算行高、缓冲行与配套几何纪律已整体废除（[ADR 0017](../adr/0017-列表三态视图与废除虚拟滚动.md)），依赖也已从 `package.json` 移除，不要再为「挂载节点数」做优化。
- 三态视图（网格 / 列表 / 表格）由 `features/library/VideoBoard.tsx` 按 `viewMode` 分派，形态词表与默认值在 `features/library/listing.ts`（`ViewMode`、`DEFAULT_VIEW_MODE`），按页面记忆在 `features/library/libraryView.ts` 的 `viewModes`。单个视频卡片统一复用 [VideoCard](../../frontend/src/features/library/VideoCard.tsx)，页面不复制卡片布局。缩略图的按下即播放由两种画出缩略图的视图（卡片与列表行）共用 [picturePress](../../frontend/src/features/library/picturePress.ts) 这一份处理，两边都不复制这段规则；表格视图没有缩略图，那里的播放仍由 `VideoActions` 承担（[ADR 0042](../adr/0042-缩略图整块按下即播放.md)）。
- 视频卡片的盒子集中在 [videoCardBox](../../frontend/src/features/library/videoCardBox.ts)：只剩图片区的比例类名（`pictureClass`）与起始边悬停余量（`hoverRoom`、`hoverRoomStyle`）这些浏览器算不出来的量；行高估算随虚拟滚动一并删除。
- 视频数据读取由应用级的库接口统一执行（页面经 `useVideos`，`useVideoPageView` 在其上组装查询），页面通过 `useVideoPageView` 复用筛选、排序、视图模式与滚动重置标识，不重复维护请求状态。
- 切换页面、筛选条件或排序时重置内容滚动位置。滚动时关闭右键菜单；播放、收藏、详情及键盘等交互在三态下都须有效（网格卡片与列表行的缩略图整块即播放目标，有媒体任务运行时该区域认领按下但不播放）。缩略图随列表项挂载，保留延迟加载。
- 网格按实际可用内容宽度分列：`VideoBoard` 的网格用 `repeat(auto-fill, minmax(min(240px,100%),1fr))`，列数由浏览器按**网格自身的宽度**算定——页面内边距与滚动条预留都已从那个宽度里扣掉，因此不直接将窗口宽度或未扣除内边距的 `clientWidth` 用作内容宽度。240 像素是下限而非定宽，列宽吃掉余量；用 `auto-fill` 而非 `auto-fit`，否则末页不满一行时卡片会被拉宽、尺寸与满页不一致；`min(…,100%)` 是窗口可被拖到 240 像素以内的护栏。内容列不再有宽度上限（`PageFrame` 的 `max-w-7xl` 已去掉），窗口变宽即继续加列。取舍与各尺寸实测见 [ADR 0019](../adr/0019-视频网格按内容宽度分列.md)。
- 表格视图的文件名列有最小宽度（`VideoTable.tsx` 的 `min-w-[14rem]`）。八列里只有它与路径列会截断，其余是 `whitespace-nowrap`、按内容取宽；不给它下限时浏览器把它压到最小内容宽度（本机实测仅 90 像素，比时长、编码、大小各列都窄），而余量被别的列按比例吃掉。窗口窄于表格的最小宽度时由 `Table` 外层的 `overflow-x-auto` 横向滚动；拖拽调列宽**不做**，没有可复用的开关（`shared/ui/table` 是纯样式化的 `<table>`，`radix-ui` 不含 resizable table）。

## 滚动条占位与兼容处理

- 视频内容、空状态及设置页统一复用 [ScrollViewport](../../frontend/src/shared/ScrollViewport.tsx)。将 `overflow` 与 `scrollbar-gutter: stable` 设置在实际滚动元素上；只给外层或 `body` 设置该属性不能替代局部容器配置。
- `stable` 为传统滚动条预留原生槽，但不会为 macOS 覆盖式滚动条占位，`both-edges` 也不解决覆盖式占位。不能仅凭属性声明或 `CSS.supports` 返回成功判定问题解决。
- 共享样式位于 [components.css](../../frontend/src/components.css)。尾侧留白是**固定 20 像素**（`padding-inline-end`），不做差额扣减：`clientWidth` 已经把滚动条扣掉了，而这条留白是从内容盒量到内边距盒，滚动条在它外面——所以眼见的那道缝就是这个数，与滚动条在做什么无关。曾经写的 `max(0px, 20px - 原生槽宽)` 会把整个差额花在滚动条上（15 像素的槽下，卡片离它只剩 5 像素），那一版早已删掉；量原生槽宽的那个 `--native-scrollbar-width` 也没有读者了，连同 `ScrollViewport` 里的 `ResizeObserver` 一起删除（ADR 0040）。车道宽自 2026-10-15 起是本应用自己的 `--scrollbar-width`（10 像素，见下一节），因此「原生槽」这个词在本仓库已无所指。
- 20 像素是应用布局策略，不是任何平台的原生滚动条宽度；它也不再需要按槽宽补偿——槽宽是我们自己定的。
- 占位规则由共享容器统一维护，各页面不另加重复的固定右内边距。
- 不支持 `scrollbar-gutter` 的引擎通过 `@supports not` 回退为 `overflow-y: scroll`。该回退仅解决传统滚动条槽，覆盖式模式仍需安全留白。
- 应用不得通过修改用户系统滚动条偏好解决布局问题。

## 滚动条自绘

- 滚动条由本仓库画，不由引擎画：**`.app-scrollbar` 一个类**（`components.css`），谁滚谁挂。已经挂上的四处是页面滚动区（`ScrollViewport` 自己挂）、抽屉面板、下拉列表、表格的横向溢出。要新增一个会滚的容器，挂这个类就是全部——**不要**改 `.scroll-viewport`，那是车道（几何），这是杆子（画）。
- 颜色取自主题，因此**没有第二处要跟着改**：静息 `--scrollbar-thumb`、悬停 `--scrollbar-thumb-hover`，两个 token 在两个主题块里各声明一次、自己随 `data-theme` 翻。轨道透明，车道里透出来的是页面本身。指针只改颜色，而颜色是 `background-color`——「指针状态只许重画背景」照字面成立。**这一对是专给杆子的**（亮 `#a3a3a3` / `#737373`、暗 `#5f646d` / `#8f949c`，都是中性灰）：它一开始借的是 `--muted-foreground` / `--foreground`，而那是**文字**的两档墨，用户看过成品之后要求换掉（「暗色滚动条都需要更暗，亮色的需要更灰」）。
- 车道宽是 `--scrollbar-width`（10 像素），**这是这个仓库自己的数**，不是平台给的：它决定内容列有多宽（实测内容宽 1153 → 1158），`check-tokens.mjs` 钉着它，ADR 0019 与 ADR 0008 里那些内容**宽度**读数是 15 像素那一版量的，同一个窗口下今天要比它们再宽 5 像素。杆子用 2 像素透明边框内缩成 6 像素胶囊，箭头按钮关掉。
- **两条会静默出事的写法**（前一条 `check-tokens.mjs` 守着，后一条只有这条注释与 ADR 0040 看着）：一是 `scrollbar-color` / `scrollbar-width`——标准的两个属性，元素上有任何一个，引擎就会丢掉它全部的 `::-webkit-scrollbar` 规则，`!important` 也拦不住（实测车道回到 15、箭头回来）；二是悬停那条要用 `background-color` 而不是 `background` 简写，简写会把 `background-clip` 重置成 `border-box`，胶囊变成填满车道的方块。规则里每条声明都带 `!important`：防的是将来某处再写一条 `::-webkit-scrollbar` 时，谁赢由特异度和顺序决定，而输的那条不会报错。
- `color-scheme` 的两行（`style.css`，两个主题块各一次）**与滚动条无关了**，别删：它管的是引擎自己画的另外几样——`canvastext`、表单控件的内部、样式表到位之前的画布底色。少一处就有一个主题里那些东西按亮色解析（暗色下原生 `<dialog>` 的文字曾是黑的）。它由 `check-tokens.mjs` 断言成「一对」，因为失败是静默的、且一次只落在一个主题里。
- macOS 上自绘滚动条**预期会从覆盖式变成占位式**（WebKit 一旦给 `::-webkit-scrollbar` 写了尺寸就不再走覆盖式），两种模式的差别与验收脚本见[滚动条占位资料核对](../滚动条占位-资料核对.md)。这一条本机（Windows）验不了。

## 滚动功能验证

修改上述逻辑后，运行 `npm run build`、`npm run check` 和 `npm test`。后端筛选、排序与分页由 `repository/listing_tests.rs` 覆盖，前端三态视图、视图模式记忆与分页控件由 `features/library/VideoBoard.test.tsx`、`features/library/libraryView.test.ts` 与 `shared/ui/pagination.test.tsx` 覆盖。模拟布局测试不替代真实窗口布局验证。

真实窗口验收须覆盖：空内容与溢出内容切换、不同视频页面切换、窗口缩放、长文件名、传统与覆盖式滚动条、鼠标悬停展开。记录容器和内容的实际宽度，检查固定区域不移动、内容不被遮挡、卡片无重叠及异常空白、根节点不产生额外滚动。无法完成的场景须明确说明。

macOS 下先启动 `npm run dev`，再分别执行以下命令。脚本用原生 `WKWebView` 加载实际网页验收入口，断言尾侧留白为 20 像素、`scrollbar-gutter` 为 `stable`、且没有横向滚动，并输出槽宽与内容宽度（它断言的是留白本身，不是「槽加补偿」的某个和——那条旧断言脚本自己的注释里记着为什么被换掉）。滚动条偏好仅通过测试进程启动参数传入，不修改用户系统设置。

- `swift scripts/check-scrollbar.swift http://127.0.0.1:5173/acceptance/web-acceptance.html -AppleShowScrollBars Always`
- `swift scripts/check-scrollbar.swift http://127.0.0.1:5173/acceptance/web-acceptance.html -AppleShowScrollBars WhenScrolling`

既有本机验证中，两种模式均测得内容宽度 1,058 像素；传统模式槽宽 17 像素，覆盖模式槽宽 0 像素。该数值是当时窗口尺寸下的证据，不是所有窗口的固定宽度要求。该检查不替代物理鼠标接入和悬停展开的人工检查。**内容宽度那一项此后不再是一个固定数**：内容列的宽度上限已去掉（[ADR 0019](../adr/0019-视频网格按内容宽度分列.md)），内容宽度随窗口变化，原记录的 1,058 像素正是那道上限留下的痕迹。**槽宽那一项也已经是旧的**：自绘之后车道是 10 像素，且 macOS 上两种模式预期会合流（见下一节末条）。该脚本真正验证的是原生槽与补偿之和为 20 像素，这一条与窗口宽度无关，未受本次改动影响。
